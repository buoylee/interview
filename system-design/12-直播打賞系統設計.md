# 直播打賞系統設計：高併發、資金一致性與即時互動

> 生產級業務案例 · 內部平台幣模型 · 不包含程式碼
>
> 核心結論：**不是建立「前臺真相」與「財務真相」兩套互不相干的資料，而是先提交唯一的權威送禮交易，再由這個事實派生即時展示、主播收益、榜單、風控與結算。**

返回索引：[生產級分布式系統 master 索引](./README.md)。

理論前置：[並發正確性與長任務協調](./11-並發正確性與長任務協調.md)。

## 1. 文檔定位

### 1.1 要解決的問題

直播平臺的送禮同時具有兩種看似衝突的要求：

1. **互動要即時**：用戶連續刷禮物時，主播和觀眾要在很短時間內看到動畫、連擊與榜單變化。
2. **資金要正確**：用戶不能重複扣款、餘額不能變成負數、主播收益不能多記或漏記，故障後還要能對帳、修復與審計。

真正困難的不是單次正常請求，而是下面這些情況同時存在：

- 同一用戶快速連點或多端同時送禮。
- 熱門直播間在短時間形成巨大流量尖峰。
- API timeout 後，客戶端不知道交易是否已經提交。
- 服務在資料庫 commit 前後 crash。
- Outbox relay、消息代理或 consumer 故障。
- 消息重複、亂序、晚到或長時間 backlog。
- 熱門主播成為收益寫入 hot key。
- 充值發生退款、拒付或欺詐，但平台幣已被消耗。
- 自動修復與人工操作互相競爭。
- 機房故障、主從切換、跨區域複製延遲。

本文固定沿著以下推理鏈設計：

~~~text
業務不變量
→ 權威事實
→ API 成功邊界
→ 本地原子事務
→ 可靠事件傳播
→ 派生展示與收益
→ 高併發擴展
→ 故障恢復
→ 對帳、審計與人工收口
~~~

### 1.2 已固定的業務模型

本文只討論以下模型：

~~~text
外部支付充值
→ 用戶獲得平台幣
→ 用戶在直播間消耗平台幣送禮
→ 平臺依規則計算主播獎勵／收益
→ 主播收益由 pending 轉為 available
→ 最後進入 payout
~~~

送禮熱路徑不直接呼叫信用卡、App Store、銀行或其他外部支付渠道。充值與送禮是兩條不同流程。

### 1.3 非目標

- 不提供 SQL、Java、Go 或具體框架程式碼。
- 不假設平台幣等同法幣，也不把送禮描述成用戶直接向主播轉帳。
- 不替財務、法務或稅務團隊決定會計科目、牌照、KYC、AML、稅務與地區性法規。
- 不宣稱 TikTok、Twitch、YouTube 或其他平臺一定使用本文的內部表結構與中間件。
- 不以「用了 Kafka」「用了 Redis lock」或「exactly-once」作為端到端資金正確性的證明。

## 2. 決策摘要

### 2.1 推薦方案

本文採用「A 的生產版」：

1. API 只有在**用戶餘額扣減、送禮交易、帳戶 movement、清算事實與 Outbox**於同一本地事務提交後，才回覆成功。
2. 直播動畫、連擊、房間榜單與統計由 GiftCommitted 事件異步驅動。
3. 主播 pending 收益由同一 GiftCommitted 事件異步、冪等地入帳。
4. 主播 available 與 paid 由風控、調整與結算流程推進。
5. 所有跨服務偏差由 reconciliation 發現，以追加 adjustment／reversal 的方式修復。

### 2.2 為什麼不是全部同步

若要求用戶扣款、主播入帳、平台分成、排行榜與百萬客戶端推送全部完成才回覆，會把：

- 多個資料庫分片；
- 熱門主播帳戶；
- 消息代理；
- WebSocket gateway；
- 慢客戶端與斷線客戶端；

都放入同一條同步成功路徑。這不會帶來真正的端到端原子性，只會放大延遲、鎖等待、故障面與不可用範圍。

### 2.3 為什麼也不是全部異步

若 API 只把命令放入 queue 就宣稱送禮成功，則回覆時可能尚未檢查餘額；後續發現餘額不足時只能反悔。這種語義可以用於明確顯示 PROCESSING 的產品，但不符合本文「點擊後立即得到確定成功／失敗」的基線。

### 2.4 不可妥協的邊界

~~~text
API 回覆 SUCCESS
⇒ 用戶平台幣已被原子扣減
⇒ gift_id 對應的送禮交易已持久化
⇒ 同一 idempotency key 不會再次扣款
⇒ GiftCommitted 的 durable Outbox fact 已存在
~~~

API 成功不代表：

- 所有觀眾都已看到動畫；
- 榜單已更新；
- 主播收益頁已刷新；
- 主播已經可以提現；
- 外部銀行已經收到款項。

## 3. 參考工作負載與服務目標

以下數字是本文用來檢查架構是否能擴展的**參考設計包絡**，不是任何平臺的公開內部指標，也不是不可修改的業務承諾。

| 維度 | 參考包絡 |
|---|---:|
| 全平臺 gift command 峰值 | 100,000 commands/s |
| 短突發 | 30 秒內達平時峰值的 3 倍 |
| 最熱直播間 | 10,000 gift units/s |
| 全平臺長連線 | 10,000,000 |
| 單一熱門直播間觀眾 | 1,000,000 |
| 單用戶正常上限 | 由風控與產品配置限制，不以無界連點為合法負載 |
| 禮物 command | 可以包含 quantity，因此 command rate 與動畫 unit rate 不一定相同 |

參考 SLO：

| 路徑 | 參考目標 | 邊界 |
|---|---|---|
| 送禮交易 API | 月可用性 99.99%，正常負載 P99 小於 200ms | 餘額不足、風控拒絕等業務結果不算系統錯誤 |
| GiftCommitted 發布 | 正常狀態 P99 小於 1 秒 | 以 outbox committed_at 到 broker append 計算 |
| 房間展示 | 已連線健康客戶端 P99 小於 1 秒 | 不保證離線、弱網或已過載客戶端必達 |
| 主播 pending 入帳 | P99 小於 5 秒，極端 backlog 必須有 aging 告警 | 超時不等於資金丟失；由 durable event 重放 |
| 對帳差異發現 | 高風險差異分鐘級，完整批次日級 | 依固定 cutoff／watermark 避免誤報 |
| 已知重複扣款、無依據增發 | 零容忍 invariant | 這是正確性要求，不是可用 error budget 抵銷的普通 SLO |

容量推導使用：

~~~text
在途工作 L = 到達率 λ × 停留時間 W

backlog drain time
= backlog
÷（consumer 可持續處理率 - 新到達率）
~~~

若 consumer 可持續處理率不高於新到達率，增加 queue retention 只能延後故障，不能完成清空。

## 4. 術語與三種不同的「錢」

### 4.1 平台幣

用戶充值後獲得的內部虛擬單位。它有自己的 balance、movement、有效期與促銷規則，不應直接使用浮點數。

### 4.2 Gift face value

一次送禮消耗的平台幣數量。它是送禮交易的輸入事實，不一定等同主播可以取得的現金。

### 4.3 主播獎勵／收益

平臺根據 gift、合約、活動、風控與地區規則計算的 creator reward。它可能使用另一種 reward unit 或 settlement currency。

因此不能直接寫成：

~~~text
用戶少 100 coin
= 主播一定多 70 元
~~~

正確做法是保存一筆可審計的 allocation fact：

~~~text
gift_id
+ source coin amount
+ gift catalog version
+ reward rule version
+ creator reward amount and currency
+ platform share／adjustment
~~~

不同單位各自守恆；跨單位轉換靠版本化規則與 allocation 記錄解釋，不能把兩種單位混進一條簡單加總公式。

### 4.4 pending、available、paid

- **pending**：已產生收益事實，但仍受風控、退款、拒付或結算等待期影響。
- **available**：已符合提現條件，可被 payout 預留。
- **paid**：出款流程已有可核驗的成功事實。

這三個狀態不能由 UI 顯示文字決定，必須由收益帳本、狀態機與外部出款結果推進。

## 5. 業務不變量

### 5.1 用戶錢包不變量

1. 可用平台幣餘額不得因合法送禮交易小於零。
2. 同一 user_id + idempotency_key 只能產生一次扣款效果。
3. 同一 idempotency key 若綁定不同 room、gift、quantity 或金額，必須回覆 conflict，不能沿用舊結果。
4. 每次餘額變化都必須有 immutable movement 解釋。
5. balance snapshot 必須可以由期初餘額與 movements 重建。
6. 促銷幣、付費幣、不可退款幣或有期限幣若規則不同，必須分 bucket 記錄，不能只保存一個無法解釋的總數。

### 5.2 送禮交易不變量

1. 每筆成功送禮只有一個穩定 gift_id。
2. COMMITTED gift 必須有且只有一組對應的用戶扣款事實。
3. 用戶扣款、gift transaction、movement、清算事實與 Outbox 必須同時 commit 或同時 rollback。
4. gift transaction 必須快照 creator、room、gift catalog、unit price、quantity、rule version 與 committed time。
5. 已提交交易不能刪除或改寫成從未發生；退款、撤銷與風控調整使用 reversal／adjustment 表達。

### 5.3 主播收益不變量

1. 同一 gift_id 對同一收益規則只能產生一次正常 allocation。
2. allocation 必須引用 GiftCommitted 與 reward_rule_version。
3. 重複消息只能重複返回既有結果，不能重複增加 pending。
4. reversed gift 必須有可追蹤的反向或調整 entry。
5. creator balance snapshot 必須能由 earning entries、holds、adjustments 與 payouts 重建。
6. pending 不能直接 payout；只有 available 可以被一次 payout reservation 消耗。

### 5.4 事件與展示不變量

1. 正式付費動畫只能由 server-confirmed GiftCommitted 觸發。
2. 未提交、已拒絕或餘額不足的請求不得進入公共房間廣播。
3. 同一 gift_id 的重送不能重複累加財務統計。
4. 展示重複或丟失不能改變財務結果。
5. 榜單、房間流水與動畫都是可重建 projection，不是資金 source of truth。

### 5.5 結算與修復不變量

1. 同一 available earning 只能被一個有效 settlement／payout batch 預留。
2. 外部 payout timeout 必須保留 UNKNOWN，不能直接當作失敗重新出款。
3. 所有人工修復必須使用穩定 repair id、expected version、審批與 audit trail。
4. 修復不得直接覆蓋 immutable 歷史；必須追加補記、沖正或調整。
5. 關閉差錯案件前必須重新執行 invariant check。

## 6. 一致性分級

| 對象 | Source of truth | 一致性模型 | 可接受的暫時狀態 | 修復方式 |
|---|---|---|---|---|
| 用戶可用餘額 | Funds Core primary shard | 同步強一致、read-your-write | 不接受負數或重複扣款 | 同 key 查詢、adjustment、對帳 |
| Gift transaction | Funds Core | 同步強一致、immutable | commit outcome unknown 時查 gift_id／key | 查詢後回同一結果 |
| Outbox | 與 gift 同庫同事務 | durable、至少一次 relay | 短暫 unpublished | relay 重送、aging alarm |
| 房間動畫 | Realtime projection | 低延遲最終一致 | 延遲、合併、部分客戶端漏看 | 短期 replay／重連，不影響資金 |
| 房間榜單 | Materialized view | 最終一致 | 短時間落後或近似 | 從 gift log 重建 |
| 主播 pending | Creator Earnings Ledger | 業務 exactly-once effect、跨服務最終一致 | allocation backlog | 冪等重放、clearing reconciliation |
| 主播 available | Earnings／Settlement | 狀態機強約束 | hold、調整、風控等待 | adjustment、人工審核 |
| Payout | Payout order + provider fact | 外部結果可能 UNKNOWN | 查詢／回調／帳單未收斂 | provider query、對帳、manual |

「業務 exactly-once effect」不表示 broker 只投遞一次；它表示 consumer 即使收到多次相同 event，也只能提交一次收益效果。

## 7. 方案比較與選型

### 7.1 方案 A：同步扣款與送禮事實，異步收益

API SUCCESS 時已完成：

- 用戶扣款；
- gift transaction；
- wallet movement；
- operational clearing fact；
- GiftCommitted Outbox。

尚未要求完成：

- 主播 pending projection；
- 動畫與榜單；
- available／paid。

優點：

- 同步路徑只競爭付款用戶自己的 wallet shard。
- 熱門主播不會成為所有送禮請求的同步寫入點。
- 展示、收益、風控和統計可以獨立擴容與重放。
- 故障後有 gift transaction 與 clearing 可以證明平臺欠哪個下游動作。

代價：

- 需要 Outbox、consumer idempotency、backlog 管理與 reconciliation。
- 主播收益頁會短暫落後。
- 需要清晰的 pending／available 語義。

### 7.2 方案 B：同步扣款與主播 pending 入帳

API SUCCESS 前同時完成付款方扣款與主播 pending entry。

若所有帳戶由同一個可水平擴展的 Ledger transaction boundary 擁有，方案 B 可以成立；它並非錯誤。但若付款方 wallet、主播收益與平台收入位於不同分片或服務，就需要：

- 集中式 Ledger；
- 將整筆 posting 路由到同一交易分區；
- XA／2PC；
- 或同步 coordinator。

這會增加同步延遲、跨分片協調與熱門主播寫入壓力。即使選 B，WebSocket 廣播仍必須在 commit 之後異步進行，不能納入財務事務。

### 7.3 方案 C：整筆送禮異步

API 只 durable accept command，稍後才檢查餘額並扣款。

它適合明確呈現 PROCESSING 的產品，或不可避免的離線工作流；不適合作為本文的默認送禮語義。系統不得在過載時偷偷從 A 降級成 C，同時仍向用戶顯示「成功」。

### 7.4 最終決策

本文選 A，原因不是「異步一定比同步高級」，而是本業務真正需要同步保護的是付款方 wallet 與 gift truth；主播展示、收益入帳和 payout 有不同延遲與故障模型。

## 8. 高層架構

充值支路先把外部渠道成功事實轉成平台內部幣，之後送禮不再依賴外部支付：

~~~text
Client
  → Recharge Service
  → External Payment Provider
  → callback／query／statement
  → Recharge Order
  → Funds Core CreditWallet
~~~

送禮主路徑：

~~~text
Client
  │
  ▼
API Gateway / Auth / Rate Limit
  │
  ▼
Gift Command Service
  ├── Gift Catalog / Room Context
  ├── Risk pre-check
  │
  ▼ route by payer user_id
Funds Core / Wallet Shard
  ├── Idempotency Record
  ├── Wallet Balance + Movement
  ├── Gift Transaction
  ├── Operational Clearing Fact
  └── Outbox
          │
          ▼
     Outbox Relay / CDC
          │
          ▼
     Canonical Gift Event Log
       ├──────────────┬────────────────┬─────────────────┐
       ▼              ▼                ▼                 ▼
Realtime Router   Creator Earnings   Analytics/Risk   Reconciliation
  │                  Ledger             Projection       Evidence
  ▼                    │
Room Sequencer         ▼
/ Lane Router      pending → available
  │                    │
  ▼                    ▼
Regional Fanout     Settlement / Payout
Gateways                │
  │                     ▼
  ▼                 External Provider
Viewers
~~~

### 8.1 組件責任

| 組件 | 擁有的資料／責任 | 明確不負責 |
|---|---|---|
| API Gateway | 認證、粗粒度限流、request size、路由 | 不判斷資金餘額 |
| Gift Command Service | 解析 room、creator、gift catalog、quantity、風控上下文 | 不直接更新 wallet |
| Recharge Service | 外部 payment order、request／callback／query、provider evidence、充值冪等 | 不以單次 timeout 推斷支付失敗 |
| Funds Core | operational balance、movement、gift transaction、idempotency、outbox | 不等待 WebSocket、MQ 或 payout |
| Outbox Relay／CDC | 將 committed outbox 可靠追加至 event log | 不重新計算業務決定 |
| Event Log | 保存事件、partition、retention 與 delivery progress | broker offset 不是業務完成事實 |
| Realtime Service | 房間路由、去重、連擊、動畫、榜單 projection | 不計算可提現收益 |
| Creator Earnings | allocation、pending、holds、available、adjustments | 不相信前端動畫計數 |
| Settlement／Payout | cutoff、預留 available、出款狀態、provider evidence | 不任意改寫 earning history |
| Risk Service | 交易前決策、交易後偵測、帳戶限制 | 不擁有資金事實 |
| Reconciliation | 比對權威來源、建 case、觸發 repair workflow | 不直接修改 wallet 或 ledger |
| Admin／Audit | maker-checker、權限、操作記錄 | 不提供無審計的後門改餘額 |

### 8.2 服務拆分原則

Funds Core 可以在程式碼層分成 wallet、gift transaction、idempotency 等模組，但只要本文要求它們同一 transaction commit，就必須由同一資料所有權邊界支持。不能為了「微服務純度」把它們拆到不同資料庫，再假裝一次 RPC 等同原子提交。

## 9. 概念資料模型

以下是責任模型，不是 SQL schema。

### 9.1 Wallet Account

保存：

- user_id；
- coin bucket／currency；
- available balance snapshot；
- account status；
- version；
- home shard／home region；
- updated_at。

balance snapshot 用於低延遲授權，但必須由 immutable movement 解釋。

### 9.2 Wallet Movement

每次充值、送禮消耗、退款、促銷、過期或人工調整都產生 movement：

- movement_id；
- account_id；
- business_type；
- business_id，例如 gift_id；
- amount 與 direction；
- coin unit；
- rule／reason；
- resulting balance；
- created_at。

已提交 movement 不刪除。修正使用反向 movement 或 adjustment movement。

### 9.3 Gift Transaction

至少快照：

- gift_id；
- payer user_id；
- room_id；
- room session id／epoch；
- creator_id；
- gift catalog id 與 version；
- unit price；
- quantity；
- total coin amount；
- reward rule version；
- idempotency key 與 intent digest；
- risk decision reference；
- status；
- committed_at；
- reversal reference。

gift_id 是所有下游效果的共同業務識別。

### 9.4 Idempotency Record

保存：

- caller／user scope；
- idempotency key；
- intent digest；
- gift_id；
- durable outcome；
- response snapshot；
- retention deadline。

同 key、不同 intent 必須 conflict。只保存 key 而不保存 intent 與結果，無法正確處理晚到或錯用 key。

Retention 必須長於客戶端最大重試窗口、離線重送窗口、事件 replay 週期與業務爭議期。財務 effect 的去重證據不能在仍可能收到合法晚到請求時提前過期。

### 9.5 Outbox Event

保存：

- event_id；
- aggregate_type 與 aggregate_id；
- aggregate version；
- event type；
- schema version；
- immutable payload；
- committed_at；
- relay state、attempt 與 last error。

relay state 是傳播進度，不是 gift 是否成功的真相。

### 9.6 Consumer Inbox／Processed Event

財務 consumer 至少以 consumer_name + event_id 建立唯一處理記錄，並與本地 earning effect 同事務提交。若先 ack broker 再寫業務，crash 可能漏帳；若先寫業務再 ack，重送必須由 inbox 吸收。

### 9.7 Creator Earning Entry

保存：

- earning_entry_id；
- gift_id；
- creator_id；
- source coin amount；
- reward amount 與 settlement currency；
- reward_rule_version；
- state；
- hold／adjustment reason；
- available_on；
- settlement／payout reference。

同一正常 allocation 的 gift_id 必須唯一。調整 entry 引用原 entry，不覆蓋原金額。

### 9.8 Settlement、Payout 與 Reconciliation Case

Settlement batch 保存 cutoff／watermark、納入的 immutable entry 集合、總額與狀態。

Payout order 保存 provider request id、idempotency key、attempt、callback、query 與 statement evidence。

Reconciliation case 保存 difference、來源、嚴重度、owner、repair command、審批與重驗結果。

### 9.9 Accounting Journal 與單位內守恆

Operational balance 解決低延遲授權；Accounting Journal 解決獨立重建、財務分類與審計。兩者職責不同，必須對帳。

每個 journal posting batch：

- 使用整數最小單位，不用浮點數；
- 固定 currency／coin unit；
- 保存 business id、posting id、rule version 與 occurred time；
- 同一單位內借貸合計平衡；
- posted entry 不覆蓋，修正使用 reversal／adjustment；
- 客戶視角的 DEBIT／CREDIT 不應與正式會計科目的借貸方向混為一談。

參考業務事實：

~~~text
充值：
provider confirmed amount
→ recharge order
→ user coin credit movement
→ coin liability／journal posting

送禮：
user coin balance - gift amount
→ gift-consumed／operational clearing fact

收益：
gift_id + reward_rule_version
→ creator pending payable in settlement currency
+ platform／subsidy／fee entries
~~~

平台幣與 settlement currency 不同時，兩邊分別在各自單位內平衡；中間以 allocation fact 關聯 source amount、target amount、匯率／獎勵規則與 rounding policy。不能用一個跨單位加總假裝守恆。

若 operational movement 與 Accounting Journal 由同一 Funds Core 資料邊界擁有，可以和 gift 一起 commit；若正式 Journal 是獨立 Ledger Service，則由 GiftCommitted 冪等 posting，gift transaction／movement 是已提交義務，journal lag 由 clearing 與 reconciliation 暴露。不能用跨服務 RPC 成功與否冒充同一本地事務。

本文的 operational clearing 不是一個可由主播提現的總餘額，也不是法律意義上的 escrow。它表示「平台幣已被合法消耗，但收益 allocation／journal 等下游責任尚未有匹配事實」。推薦按 gift_id 保存或計算 clearing position，而不是讓 Creator Earnings 回頭修改 Funds Core 的 gift 狀態；兩個 immutable facts 由 reconciliation 配對，可避免再引入反向 dual write。

### 9.10 Recharge Order

充值訂單至少保存：

- recharge_id 與 client idempotency key；
- user_id；
- provider request id 與 provider transaction id；
- amount、currency、coin package／promotion version；
- local state；
- request、callback、query 與 statement evidence；
- wallet credit business id；
- chargeback／refund reference。

同一 provider transaction id 不得綁定兩個互相衝突的充值訂單；同一 recharge 只能產生一次 wallet credit。

Provider transaction id 的唯一性由 Recharge Service 的權威去重邊界保證；若資料需要分片，按 provider + provider transaction id 做確定性路由或使用專門 registry。Funds Core 只負責同一 recharge_id／CreditWallet command 不重複入帳，不能單靠某個 user shard 的局部 unique constraint 宣稱 provider id 全域唯一。

### 9.11 核心狀態機

不同責任使用不同狀態機，不把全部狀態塞進 gift 一個欄位：

~~~text
Recharge:
CREATED → SUBMITTED → CONFIRMED → CREDITED
                    ↘ UNKNOWN → CONFIRMED／FAILED／MANUAL
CONFIRMED／CREDITED → REFUNDED／CHARGEBACK_ADJUSTED

Gift:
COMMITTED → ADJUSTED／REVERSED

Revenue allocation:
NOT_POSTED → POSTED → HELD／ADJUSTED

Creator funds:
PENDING → AVAILABLE → RESERVED_FOR_PAYOUT → PAID
       ↘ HELD／ADJUSTED

Payout:
CREATED → RESERVED → SUBMITTED → SUCCEEDED
                              ↘ UNKNOWN → SUCCEEDED／FAILED／MANUAL
~~~

Gift 是否已提交、收益是否已 posting、錢是否可提現是三件不同的事；任何一個 downstream 狀態都不能反向改寫原 gift 從未發生。

## 10. 充值前置流程與送禮同步主路徑

### 10.1 外部充值

充值不在送禮 hot path，但它決定平台幣是否有可信來源：

1. Client 以穩定 recharge idempotency key 建立充值訂單。
2. Recharge Service 保存 provider request id、amount、currency、coin package 與 promotion version。
3. 對外支付呼叫不放入 Funds Core transaction。
4. provider timeout 進 UNKNOWN；不直接建立第二筆充值，也不把 timeout 當成失敗。
5. 只有驗簽通過，且 provider transaction id、amount、currency、merchant／account 與原充值 intent 完全匹配的 callback、主動 query 或 provider statement 證明成功後，Recharge Service 才發出穩定 CreditWallet command。
6. Funds Core 以 recharge_id／provider transaction id 冪等地在同一本地事務：
   - 增加正確 coin bucket；
   - 追加 wallet credit movement；
   - 保存 recharge credit result；
   - 寫 WalletCredited Outbox。
7. 重複 callback、query 或 command 返回既有 credit result。
8. provider success 但 wallet 尚未 credit 由充值對帳補發同一 CreditWallet command。
9. chargeback／refund 使用 adjustment 或 reverse movement，不能刪除原 credit 與已發生 gift。

充值成功的 API／callback 只代表 provider 結果；用戶平台幣可用則必須再由 Funds Core 的 CREDITED fact 證明。兩者若短暫分歧，Recharge Order 保持 CONFIRMED／CREDIT_PENDING，直到 credit 或人工收口。

### 10.2 客戶端送禮請求

客戶端為每個使用者意圖產生穩定 idempotency key。網路 timeout 或重連後只能以同一 key 重試，不能因為沒收到回覆就建立新 key。

客戶端只提交 gift catalog id、quantity、room context 與 key。價格、creator、分成率與可提現金額都由服務端決定。

### 10.3 入口控制

Gateway 先完成：

- session／token 驗證；
- request size 與 quantity 上限；
- user、IP、device、room 維度 rate limit；
- 已封禁帳戶與灰度版本控制；
- admission control。

限流不能替代 wallet invariant，但可以在流量到達資料庫前拒絕明顯濫用與過載。

### 10.4 解析可信業務上下文

Gift Command Service 從服務端來源解析：

- room 是否仍 active；
- room session id／epoch 與允許送禮的 grace policy；
- creator 是否有資格收禮；
- gift catalog 與價格版本；
- 活動、地區與用戶資格；
- reward rule version；
- 風控上下文。

不得相信客戶端傳來的 amount、creator_id、discount 或 revenue share。

Room Context 必須帶可驗證的 session version／expiry。直播關閉與送禮 commit 競爭時，由明確產品規則決定「以 Funds Core commit time 為準」或「必須在指定 room epoch 仍 active」；不能讓不同服務各自用本地時間猜測。

### 10.5 風控

同步 pre-check 在開啟 Funds Core transaction 之前完成。高價值或高風險交易可 fail closed；低價值交易可依明確政策使用本地限額與有時效的 risk decision。

transaction 內只做本地、可原子判斷的硬限制，例如：

- account status；
- 每日已用限額；
- 餘額；
- gift quantity；
- risk decision 是否過期或不匹配。

不得在持有 wallet row lock 時等待遠端 Risk RPC。

### 10.6 路由

依 payer user_id 路由至 wallet home shard。這使所有會消耗同一用戶餘額的命令進入同一權威分片；房間與主播不是財務熱路徑的 sharding key。

### 10.7 Funds Core 本地事務

一個短事務完成：

1. 建立或競爭 idempotency record。
2. 若 key 已存在，驗證 intent digest：
   - 相同 intent：返回既有結果；
   - 不同 intent：返回 conflict。
3. 驗證 account status、版本、限額與 coin bucket。
4. 以原子條件更新扣減可用餘額；條件不成立則不產生 gift。
5. 追加 wallet movement。
6. 建立 COMMITTED gift transaction。
7. 建立 operational clearing／consumed fact。
8. 建立 GiftCommitted Outbox。
9. 保存成功 response snapshot。
10. commit。

事務內不得包含：

- HTTP／RPC；
- MQ send；
- WebSocket broadcast；
- 大型報表查詢；
- 圖片或動畫處理；
- 外部支付；
- 人工等待。

### 10.8 API 回覆

成功回覆至少包含：

- gift_id；
- committed status；
- committed_at；
- 扣款後餘額；
- display queued／pending 語義；
- 客戶端用於查詢的 request id。

付款用戶自己的畫面可以在收到 server success 後立即播放本地效果；對整個房間的正式廣播仍由 GiftCommitted 事件觸發。

回覆同時攜帶 balance version／commit token。若隨後的餘額查詢可能落到 replica，查詢層必須：

- 路由回 primary；
- 或等待 replica 至少追上該 version；
- 或直接在短時間內以 API 回覆的餘額作 read-your-write 顯示。

不能讓剛扣款成功的用戶因 replica lag 又看到舊餘額，進而重複操作或誤以為沒有扣款。

主播收益頁則明確顯示 as-of time／projection lag；它不宣稱與 GiftCommitted 同 transaction 更新。

### 10.9 commit outcome unknown

若資料庫 commit 成功但連線在回覆前中斷，server 或 client 都不能把 timeout 直接當成失敗：

1. 以 user scope + idempotency key 查詢。
2. 若存在成功結果，返回同一 gift_id 與餘額。
3. 若確定不存在，才允許以同 key 重新執行。
4. 若權威資料庫本身不可查，回覆 PROCESSING／UNKNOWN 或暫時不可用，不產生第二個 key。

## 11. Outbox 與事件傳播

### 11.1 為什麼不能直接「commit 後 send」

兩個順序都會留下窗口：

~~~text
先 commit DB，後 send
→ commit 後 crash，事件遺失

先 send，後 commit DB
→ DB rollback，但下游已看見事件
~~~

因此 gift transaction 與 Outbox 在同一本地事務提交。Relay 或 CDC 只傳播已提交 fact。

### 11.2 至少一次與冪等

Relay 在以下情況會重送：

- send 成功但 ack 遺失；
- relay commit publish state 前 crash；
- broker leader 切換；
- 人工 replay。

所以「消息只送一次」不是本文依賴的 invariant。每個 consumer 都要以 event_id／gift_id 在自己的本地 effect 邊界去重。

### 11.3 Canonical event envelope

GiftCommitted 至少攜帶：

- event_id、event_type、schema_version；
- gift_id；
- user_id、creator_id、room_id；
- gift catalog version；
- quantity、source amount、coin unit；
- reward rule version；
- committed_at；
- source shard／region；
- trace／correlation id。

事件只攜帶下游需要的最小資料，避免把敏感支付資訊與 PII 廣播至所有 consumer。

### 11.4 Ordering

本文不要求所有 gift 全域 total order：

- 用戶餘額順序由 payer wallet shard 仲裁。
- 同一 gift 的重複由 gift_id 去重。
- 同一用戶連擊可用 user combo sequence。
- 房間展示只要求產品定義的局部順序，不要求百萬觀眾看到完全相同的跨用戶全序。
- 財務 allocation 只要求每個 gift 合法提交一次；不依賴 broker 全域順序。

若使用 partitioned log，相同 key 的順序只在同一 partition 內成立。更換 key、repartition 或多 topic fan-out 後，consumer 仍要靠 business version 與狀態機判斷。

### 11.5 Poison event

無法解析或永久違反 schema 的事件不能無限阻塞整個 partition，也不能直接丟棄：

1. 保存原 event 與錯誤。
2. 進 quarantine／case。
3. 告警並隔離後續影響。
4. 修正 consumer 或資料後以同 event_id replay。
5. 財務 consumer 的跳過必須有審批與對帳證據。

## 12. 即時展示路徑

### 12.1 展示是 projection，不是 source of truth

Realtime Service 只消費 GiftCommitted。它可以保存：

- 房間最近事件；
- 用戶 combo state；
- 禮物動畫 priority；
- room total projection；
- top-gifter leaderboard；
- 客戶端重連 cursor。

這些資料都能從 canonical gift log 重建。任何房間計數與 wallet／earning ledger 不一致時，以財務交易為準。

### 12.2 熱門直播間

若以 room_id 作為唯一 partition key，一個超熱房間會壓在單 partition 上。本文不要求房間所有禮物存在全域嚴格順序，因此可以：

- 依 room_id + lane 分多條展示 lane；
- 對同一用戶／combo 維持局部順序；
- 高價值禮物使用高優先級 lane；
- gateway 以短窗口合併相同用戶的連擊；
- room total 使用分片 counter，定期 merge；
- 只在需要時產生可見 frame，而不是每個 gift unit 向每個觀眾單獨發消息。

如果產品堅持房間全域嚴格順序，就必須接受單一 sequencer 的天然串行上限，或使用可水平擴展但仍有共識成本的排序服務。這是產品語義換容量，不是中間件配置可以免費消除的代價。

### 12.3 階層式 fan-out

不能讓每個 GiftCommitted 直接對一百萬 WebSocket 逐一寫入。推薦：

~~~text
room event
→ room aggregator
→ regional fanout node
→ connection gateway
→ subscribed clients
~~~

同一 frame 在 gateway 內共用序列化結果與 buffer；慢客戶端有獨立 bounded queue，不能拖住整個房間。

### 12.4 展示降級順序

過載時按以下順序降級：

1. 保留 GiftCommitted 與財務 consumer。
2. 保留高價值禮物與付款用戶 ack。
3. 合併連擊動畫。
4. 降低普通禮物動畫幀率。
5. 延後榜單與分析。
6. 丟棄過期且已無產品價值的展示 frame。

禁止的降級：

- 繞過餘額檢查；
- 先播放公共付費動畫再嘗試扣款；
- 因 MQ backlog 直接刪除財務事件；
- 用 Redis counter 反向補算正式收益。

### 12.5 客戶端語義

- sender 收到 SUCCESS 後可立即看到本地確認。
- 其他觀眾看到的是 server broadcast。
- client 以 gift_id／display event id 去重。
- 重連可按短期 cursor 補最近事件，但不保證補播所有已失去時效的動畫。
- UI 顯示的房間流水應標成即時統計，不冒充可提現餘額。

## 13. 主播收益與結算

### 13.1 收益入帳

Creator Earnings consumer 收到 GiftCommitted 後：

1. 以 event_id／gift_id 建立 inbox dedup。
2. 載入或驗證 immutable reward_rule_version。
3. 計算 creator reward、platform share、活動補貼與必要 hold。
4. 追加 creator pending earning entry。
5. 追加 allocation／accounting entries。
6. 更新可重建的 pending snapshot 或 bucket。
7. 寫 EarningsPosted Outbox。
8. inbox、entries、snapshot 與 outbox 同一本地事務提交。
9. commit 後才 ack broker。

若 consumer crash，broker 可重送；唯一 gift_id 與 inbox 使第二次處理返回既有結果。

### 13.2 熱門主播 hot key

不應在每個 gift 上同步更新一個無法分片的 creator_total row。可用：

- immutable earning entries；
- creator_id + bucket 的 balance buckets；
- gift_id hash bucket；
- 時間窗口 partition；
- 異步 materialized balance；
- settlement cutoff 時關閉舊 bucket 並彙總。

主播 UI 的即時估算可以讀 projection；真正 payout 則從固定 cutoff 的 ledger entries／closed buckets 計算。

Bucket 化會提高結算與查詢複雜度，因此只在量測證明單帳戶成為瓶頸後使用。未達 hot-key 壓力時，單帳戶短事務更簡單。

若使用 gift_id hash bucket，每個 gift 必須依確定性函數只落入一個 bucket，並在該 bucket 內對正常 allocation 建立唯一約束；不能以隨機重試重新選 bucket，否則會繞過去重邊界。

### 13.3 pending 到 available

pending entry 經過：

- 最短等待期；
- 充值拒付／退款風險；
- 帳戶與內容風控；
- creator eligibility；
- 合約與活動規則；
- 稅務／合規 hold；
- adjustment；

才能轉成 available。狀態推進使用 expected state／version，晚到的舊命令不能把 hold 中的資金變成 available。

### 13.4 Settlement cutoff

結算批次必須保存固定：

- cutoff time；
- source watermark；
- rule version；
- eligible entry set 或可重建選擇條件；
- batch id；
- total by currency；
- created／approved／reserved／paid 狀態。

不能在一個長查詢期間一邊讀變動資料、一邊把新 entry 混入同一批次。

### 13.5 Payout

Payout 至少分為：

~~~text
AVAILABLE
→ RESERVED_FOR_PAYOUT
→ SUBMITTED
→ SUCCEEDED

失敗分支：
SUBMITTED → UNKNOWN → SUCCEEDED／FAILED／MANUAL
~~~

外部 provider timeout 後：

- 不直接釋放 reservation；
- 不換新 idempotency key 重付；
- 優先按 provider request id 查詢；
- 使用 callback、query 與 provider statement 收斂；
- 無法證明時保持 UNKNOWN，進 manual review。

### 13.6 退款、拒付與 reversal

用戶充值可能在平台幣已消耗後發生 chargeback。系統不能刪除原 gift：

- 對用戶追加 adjustment／negative position 或限制帳戶；
- 未 available 的 creator pending 可依政策 hold／adjust；
- 已 available／paid 的收益需要 reserve、future offset 或平台承擔；
- 所有處理引用原 recharge、gift 與 earning entry；
- 高風險情況進人工案件。

具體誰承擔損失是商業與法律決策，架構只保證事實可追蹤、規則版本可證明、調整不破壞歷史。

## 14. 高併發、分片與熱點

### 14.1 財務分片鍵選 payer user_id

送禮同步 invariant 是「同一用戶可用餘額不得被重複消耗」，因此 payer user_id 是自然的 wallet sharding key：

- 不同用戶可以並行。
- 同一用戶的衝突落在同一 shard／row。
- 熱門 room 或 creator 不進入同步扣款 partition。
- read-your-write 可以由 home shard 返回。

### 14.2 同一用戶的並發

同一用戶多端快速送禮時，原子條件扣減決定成功者。可配合：

- per-user ordered admission；
- 很短的 row lock；
- account version；
- bounded retry；
- 單用戶 rate limit。

增加 worker 不會提高同一 wallet 的合法並行度，只會增加 lock wait／conflict。真正可擴展的是 user key 之間的並行。

### 14.3 Combo 與 quantity

若產品允許一次 command 表達 quantity：

- 財務只提交一筆 total amount；
- gift transaction 保存 unit price 與 quantity；
- 展示層依產品節奏展開或合併動畫；
- idempotency 仍以整個 command 為單位。

這能降低 DB TPS，但會改變「中途停止 combo」的產品語義。只有客戶端明確確認 quantity 時才能使用，不能由 server 擅自把多次獨立點擊合成一筆不可撤銷交易。

### 14.4 Cache 邊界

可以 cache：

- gift catalog；
- room metadata；
- display projection；
- risk rules；
- leaderboard；
- wallet balance 的只讀提示。

不能用 cache 授權扣款。正式餘額判斷必須在 Funds Core 權威寫入邊界完成。Redis lock 也不能替代資料庫內的 balance predicate 與 unique constraint。

### 14.5 邏輯分片與搬遷

使用足夠數量的 logical slots，再映射到 physical shards，可降低擴容時的搬遷範圍。Reshard 流程要有：

- slot ownership epoch；
- 單一 active writer；
- copy watermark；
- 校驗 count、movement hash 與 balance；
- cutover fence；
- 回滾條件；
- 搬遷後對帳。

雙寫不是默認答案；若使用 dual write，必須定義哪一邊是權威、失敗後如何補齊以及何時停止舊 writer。

### 14.6 Queue、backpressure 與公平性

監控不只看 queue depth，還要看：

- oldest event age；
- per-partition lag；
- per-room／creator lag；
- consumer service rate；
- replay traffic；
- retry ratio；
- deadline misses。

恢復 backlog 時保留新流量與修復流量的 quota，避免滿速 replay 再次壓垮 Funds Core、Ledger 或 fanout。

### 14.7 Bulkhead

至少隔離：

- gift commit；
- recharge callback；
- realtime fanout；
- creator earnings；
- payout；
- reconciliation／repair；
- analytics。

榜單或分析故障不得吃光 gift commit 的 DB connections、thread pool 或 broker quota；payout 也不能被熱門直播間的事件洪峰餓死。

## 15. 故障矩陣

| 故障 | 不能接受的結果 | 在線保護 | 恢復與證明 |
|---|---|---|---|
| client 重複點擊／timeout retry | 重複扣款 | user-scoped idempotency key、intent digest、unique boundary | 查同 key 返回原 gift_id |
| 同 key 不同 payload | 把兩個意圖當一筆 | intent mismatch conflict | audit 安全事件，不產生新扣款 |
| 同用戶併發且餘額只夠一筆 | 兩筆都成功、餘額負數 | 權威 shard 原子條件扣減 | movement 與 balance 重建 |
| Funds Core commit 前 crash | 留下半筆 gift | 同一本地 transaction | rollback 後同 key 重試 |
| commit 成功但 response 丟失 | client 用新 key 再扣一次 | 保存 durable result | 同 key 查詢並返回原結果 |
| DB primary failover | split-brain 雙寫 | 單 writer、term／epoch、quorum policy | 驗證 committed position 與 fencing |
| Outbox relay crash | 已扣款但下游永遠不知道 | gift 與 outbox 同事務 | 掃描 unpublished、重送 |
| send 成功但 relay ack 丟失 | duplicate event | event_id 穩定 | consumer inbox 去重 |
| broker 重複投遞 | 重複主播入帳 | inbox + earning effect 同事務 | 查 processed event 與 gift_id |
| broker 亂序／晚到 | 舊狀態覆蓋新狀態 | state version、合法 transition | 重讀權威狀態；拒絕晚到 transition |
| display consumer 落後 | 動畫延遲 | projection 與財務隔離 | replay／coalesce；不補扣款 |
| display 重複 | 重複動畫／榜單多算 | display id 去重、榜單按 gift_id | 從 canonical gift log 重建 |
| earnings consumer crash | 用戶已扣但主播未入帳 | durable event、clearing aging | 冪等 replay；reconciliation 建 case |
| poison event | partition 永久阻塞或財務事件被丟 | quarantine + durable case | 修正後同 event_id replay |
| 熱門主播帳戶過載 | earnings backlog 無界增長 | append entries、bucket、quota | 擴容 consumer；監控 oldest age |
| reward rule 部署變更 | 同一 gift 被不同規則計算 | gift snapshot rule version | 依原版本重算與對帳 |
| chargeback 發生於 gift 後 | 平臺損失無法追蹤 | recharge-gift lineage、pending hold | adjustment、reserve、manual |
| payout timeout | 重複出款 | stable provider id、UNKNOWN state | query／statement 對帳，不盲重試 |
| 人工與自動修復競爭 | 重複 adjustment／payout | MANUAL state、repair fence、same business key | maker-checker、重新對帳 |
| consumer schema 不相容 | 大量事件失敗 | versioned schema、向後相容 rollout | rollback consumer、replay |
| region 故障 | 舊區域恢復後雙寫 | home region、writer epoch、failover fence | 比對 replication watermark、全量對帳 |

## 16. 對帳閉環

### 16.1 對帳不是備用功能

在線協議負責盡量防止錯誤；對帳負責證明不同 source of truth 能互相解釋。沒有 reconciliation，就不能證明異步收益最終「不多不少」。

### 16.2 對帳層次

#### Wallet 對帳

~~~text
wallet balance snapshot
= opening balance
+ posted credits
- posted debits
+ adjustments
~~~

每個 COMMITTED gift 必須有一筆匹配 amount、coin unit 與 gift_id 的 debit movement。

#### Gift／Outbox 對帳

- 每個 COMMITTED gift 必須存在 GiftCommitted Outbox。
- 每個 outbox 必須是已提交 gift 的事件。
- 長時間 unpublished 必須進 case。
- broker ack 只能證明傳播，不證明每個 consumer 已完成業務 effect。

#### Earnings 對帳

- 每個符合收益資格的 gift 必須有一筆正常 allocation。
- 每個 gift_id 不得有兩筆正常 allocation。
- allocation 必須使用 gift 快照的 rule version。
- reversed gift 必須有 matching adjustment。
- pending snapshot 必須能由 entries 重建。

#### Clearing 對帳

clearing 的核心作用是暴露「已從付款方提交，但下游責任尚未收斂」的量與 age。非零不一定是錯誤，但長時間 aging 必須可定位至 gift_id 與 consumer outcome。

#### Settlement／Payout 對帳

- batch total 等於 cutoff 內 eligible entries。
- available reservation 只能被一個 payout order 消耗。
- provider success 必須有本地 paid entry。
- 本地 paid 必須能在 provider callback、query 或 statement 找到。
- amount、currency、fee、provider reference 不一致必須建 case。

#### Recharge 對帳

外部 provider statement、recharge order、wallet credit movement 與 accounting entry 必須互相解釋。送禮系統不能假設充值永遠不會 chargeback。

### 16.3 Cutoff 與 watermark

跨服務對帳若直接比較「此刻」的資料，會把正常傳播延遲誤判為差異。每次對帳必須固定：

- source watermark；
- committed time cutoff；
- event／entry version；
- 允許的 propagation grace period。

只有超過 grace period 仍不一致才建正式 difference。

### 16.4 Difference 到 Close

~~~text
Difference Detected
→ Classified
→ Case Created
→ Repair Proposed
→ Approved
→ Idempotent Repair Command
→ Reconciled Again
→ Verified
→ Closed
~~~

Reconciliation Service 只發現與編排修復，不直接改餘額。真正 adjustment 由擁有資料的服務以正常命令、unique key、expected version 與 audit record 執行。

### 16.5 對帳頻率

| 對帳 | 建議節奏 |
|---|---|
| outbox aging、earnings lag、clearing aging | 近即時／分鐘級 |
| gift ↔ wallet ↔ earning cross-check | 小時級增量 |
| balance reconstruction sampling | 持續抽樣 + 日級完整批次 |
| recharge／payout provider statement | 按 provider 帳單節奏，至少日級 |
| settlement batch close | 每批次必驗 |
| 歷史全量 invariant scan | 依資料規模週期執行並保存結果 |

## 17. 風控、安全與合規邊界

### 17.1 威脅模型

- 盜號後快速消耗平台幣。
- 客戶端竄改價格、quantity、creator 或活動規則。
- 重放請求與多端併發。
- 機器人刷榜、洗量、關聯帳戶自送禮。
- 充值欺詐、盜刷與後續 chargeback。
- 主播與用戶串謀套現。
- 管理員越權改餘額或提前放行 payout。
- 日誌、事件或分析平臺洩露 PII。

### 17.2 必要控制

- TLS、短期 session、設備與風險信號。
- server-side catalog、creator、price 與 rule resolution。
- user／device／IP／payment instrument／creator 關聯風控。
- 高價值交易二次確認、step-up authentication 或更嚴格限額。
- payout 前 KYC／eligibility／sanction 等檢查由適用地區政策決定。
- 管理操作 least privilege、RBAC、maker-checker、不可變 audit。
- 敏感資料加密、KMS、secret rotation、PII 與事件資料分離。
- metrics label 不放 user_id、gift_id 等高基數或敏感資訊。
- audit／ledger retention 與刪除政策由法務和合規共同決定。

### 17.3 風控降級

- 高風險／高價值路徑：Risk unavailable 時 fail closed。
- 低風險小額：只有在業務批准的本地限額、規則版本與最大曝險內才可降級。
- post-risk 可以 freeze creator pending，但不能偷偷刪除已提交 gift。
- 風控模型更新不能重寫歷史交易；以 rule／model version 解釋當時決策。

### 17.4 合規聲明

平台幣是否可退款、gift 是否構成價值轉移、creator reward 如何納稅、何時需要 KYC／AML 或資金牌照，均依地區、合同與產品政策而異。本文只提供技術控制面，不構成法律或會計意見。

## 18. 可用性、多區域與容災

### 18.1 資料分級

| 資料 | 容災策略 |
|---|---|
| wallet、movement、gift transaction、idempotency | 最高保護，primary + 同步多 AZ，PITR、跨區域複製 |
| creator earning、settlement、payout | 同等財務級保護 |
| canonical gift event | 多副本、足夠 retention，可 replay |
| room animation buffer | 可丟失短期資料，可由 event 重建 |
| leaderboard／analytics | projection，可重建 |

### 18.2 單一 wallet writer

每個 wallet logical slot 只有一個 active home region／writer epoch。全球入口將付款命令路由至 payer home region；commit 後 GiftCommitted 可以跨區域傳到 room 所在地。

不要在沒有 consensus／fencing 的情況下讓兩個 region 同時接受同一 wallet 的寫入。網路分區時寧可該 wallet 暫時不可送禮，也不能在兩邊各花一次相同餘額。

### 18.3 Region failover 的兩種誠實選擇

1. **跨區域同步共識，追求 financial RPO 0**：寫延遲與成本較高。
2. **home region 同步多 AZ、跨區域異步**：正常延遲較低，但 region 災難時不能假裝 RPO 0；必須根據 replication watermark 決定安全 failover，必要時 fail closed 並等待恢復／對帳。

本文推薦第二種作為一般大型平臺基線，再由業務對 region 級 RPO 的價值決定是否升級成跨區域同步共識。

### 18.4 降級模式

Funds Core 不可用時：

- 不回覆虛假的 SUCCESS；
- 不先廣播公共付費動畫；
- 不自動切換成只入 queue 的 C 語義；
- 返回明確 retryable unavailable／processing only if durable status 可查。

可以繼續：

- 觀看直播；
- 普通聊天；
- 非財務互動；
- 顯示已提交事件；
- 延後榜單與 analytics。

### 18.5 備份與演練

- 定期 full backup + continuous log／PITR。
- 備份必須加密、隔離權限並測試 restore。
- Restore 後重跑 balance、gift、outbox、earning 與 payout invariants。
- 定期演練 shard failover、region isolation、event replay、reconciliation repair。
- RTO 不是「主庫切過去」的時間，而是服務恢復且 invariant 驗證通過的時間。

## 19. 可觀測性與告警

### 19.1 Gift API

- request rate、success、business reject、system error。
- P50／P95／P99／P99.9。
- idempotency hit、in-progress、intent conflict。
- insufficient balance 與 risk reject 分開計數。
- shard route error。

### 19.2 事件傳播

- outbox unpublished count 與 oldest age。
- relay attempt／failure。
- broker append latency。
- partition lag 與 skew。
- duplicate rate。
- poison／quarantine count。
- schema version mismatch。

### 19.3 展示

- GiftCommitted 到 room frame latency。
- room lane backlog。
- hot room event rate。
- fanout connections、send queue saturation。
- slow client disconnect。
- animation coalesced／dropped／expired。
- leaderboard projection lag。

### 19.4 財務

- recharge provider-confirmed-but-not-credited count 與 oldest age。
- duplicate provider transaction conflict。
- recharge UNKNOWN 與 chargeback rate／amount。
- gift-without-movement count。
- gift-without-earning beyond grace period。
- duplicate earning conflict。
- clearing amount 與 oldest age。
- pending／available／paid totals by currency。
- balance reconstruction differences。
- payout UNKNOWN age。
- reconciliation difference count、amount、severity 與 case age。

### 19.5 Tracing 與 logging

gift_id、event_id、idempotency key hash、shard、rule version 與 trace id 應能串起：

~~~text
API
→ Funds Core commit
→ Outbox relay
→ Event Log
→ Room display
→ Earnings
→ Settlement／Payout
→ Reconciliation
~~~

gift_id 適合放在 trace／structured log，不適合作為 metrics label。日誌要遮罩 token、支付憑證、PII 與敏感風控信號。

### 19.6 告警優先級

| 級別 | 例子 |
|---|---|
| P0 | 重複扣款、無依據增發、split-brain writer、重複 payout |
| P1 | clearing／earning 大額差異、payout UNKNOWN 大量累積、Funds Core 大面積不可用 |
| P2 | outbox／consumer lag 超 SLO、熱門房間顯著延遲 |
| P3 | analytics／榜單落後、普通動畫降級 |

財務 invariant 告警不能被普通可用性 error budget 靜默。

## 20. 過載保護與容量驗證

### 20.1 Admission control

系統應在最前端按 user、room、device、region 與 operation 限流；當 Funds Core 飽和時，入口減少新工作，而不是讓 request 在所有層無界排隊。

### 20.2 有界資源

以下資源都必須有上限與拒絕策略：

- HTTP in-flight；
- DB connection pool；
- per-shard transaction queue；
- relay batch；
- consumer concurrency；
- per-room lane；
- WebSocket send buffer；
- retry budget；
- replay throughput；
- repair worker。

### 20.3 Retry policy

- 只重試可安全冪等的 command。
- exponential backoff + jitter。
- 限制 attempt 與總 deadline。
- 4xx business reject 不重試。
- timeout 後先查 idempotency outcome。
- replay 與新流量使用不同 quota。
- 全局 retry budget 防止各層獨立重試形成放大。

### 20.4 壓測必須包含的形狀

- 均勻 user key。
- 單 hot user 多端併發。
- 單 hot room。
- 單 hot creator。
- 3 倍突發。
- display fanout 乘數。
- earnings consumer 停止後恢復。
- outbox replay 與正常流量同時存在。
- DB failover 期間的 timeout／retry。
- poison event。
- region route 失敗。

平均 QPS 測試不能代表熱門房間與 hot key。

### 20.5 容量通過條件

- 財務 invariant 全部通過。
- P99 沒有跨過不可恢復的飽和拐點。
- queue oldest age 能在事故後按預期 drain。
- retry 沒有造成二次過載。
- fanout 降級不影響 gift commit。
- 失敗注入後 clearing 與 reconciliation 能收斂。

## 21. 發布、Schema 與規則變更

### 21.1 Event schema

- 每個事件有 schema version。
- 新增欄位先讓 consumer forward-compatible。
- 先升 consumer，再升 producer。
- 不復用已發布欄位表達新語義。
- 破壞性變更使用新 event type／version。
- 保留可 replay 舊事件的 consumer 或 migration。

### 21.2 Database expand-contract

先新增可空／有默認值的資料結構，完成 backfill 與雙讀驗證，再切換寫入與刪除舊欄位。Schema migration 不在熱門 transaction 中執行長時間 blocking DDL。

### 21.3 Gift catalog 與 reward rule

- catalog、price、promotion、creator contract、reward rule 都要版本化。
- gift transaction 保存當時版本與必要 snapshot。
- 新規則只影響新 gift，除非有明確、可審計的追溯調整。
- rule rollout 使用灰度、shadow calculation 與差異報告。
- shadow 結果不能直接入正式 ledger。

### 21.4 Consumer rollout

- canary consumer 先讀鏡像／shadow topic。
- 比對新舊 allocation 結果。
- 設定 kill switch。
- 發現差異先停新版本，不刪 canonical event。
- 回滾後可從 checkpoint／event id replay。

## 22. 測試與正確性驗證

### 22.1 Invariant／Property 測試

生成任意順序的：

- gift request；
- duplicate；
- timeout；
- reversal；
- chargeback；
- earning posting；
- payout；
- repair；

每一步後檢查 wallet、gift、movement、earning 與 payout invariants。

### 22.2 併發測試

- 餘額只夠一筆時同時送兩筆。
- 相同 idempotency key 相同 intent。
- 相同 key 不同 intent。
- 多端同 user。
- hot creator earning bucket。
- settlement 與 adjustment 競爭。
- auto repair 與 manual repair 競爭。

### 22.3 Crash point 測試

在下列邊界注入 crash：

- idempotency 建立後；
- balance 更新前／後；
- gift／movement／outbox 寫入間；
- DB commit 後回覆前；
- broker send 後 relay state 更新前；
- earning commit 後 ack 前；
- payout request send 前／後。

每個 crash point 都要得到可解釋結果：未發生、已發生、可安全重試或 UNKNOWN。

### 22.4 消息測試

- duplicate；
- reorder；
- delay；
- partition pause；
- consumer restart；
- poison event；
- schema old/new mix；
- replay historical events。

### 22.5 對帳演練

人工製造：

- gift 缺 earning；
- duplicate earning；
- balance snapshot 偏差；
- outbox 卡住；
- payout provider success 但本地 UNKNOWN；
- recharge chargeback；

驗證 Difference → Case → Repair → Review → Close 能完成，且修復後 invariant checker 通過。

### 22.6 上線 Gate

1. 核心 invariant 測試通過。
2. 故障矩陣每一列有自動化或 runbook 證據。
3. 代表性峰值與 hot-key 壓測通過。
4. Outbox、consumer、clearing、payout UNKNOWN 告警可觸發。
5. Backup restore 與 event replay 演練通過。
6. 權限、maker-checker、audit 查詢通過。
7. Reconciliation 能發現並修復預置差異。
8. Rollback、kill switch 與 schema compatibility 通過。

## 23. 生產 Runbook 摘要

### 23.1 Outbox oldest age 上升

1. 判斷 Funds Core commit 是否正常。
2. 檢查 relay、DB scan、broker append 與 partition skew。
3. 限制 replay 速率，保留新流量 quota。
4. 不刪 outbox。
5. 恢復後按 committed_at replay 並驗證下游 lag。

### 23.2 Creator earning lag 上升

1. 檢查 consumer lag、hot creator、poison event、rule service。
2. 保護 GiftCommitted retention。
3. 擴容非 hot partition；hot key 採 bucket／quota。
4. 監控 clearing amount 與 age。
5. 恢復後執行 gift ↔ earning 對帳。

### 23.3 熱門直播間 fanout 過載

1. 不影響 Funds Core。
2. 啟用 combo coalescing、lane 擴展與動畫 priority。
3. 降低普通動畫幀率與榜單刷新。
4. 斷開持續超限的 slow clients。
5. 保留 canonical event，不用前端丟失反推財務補償。

### 23.4 發現重複扣款疑似案件

1. 升級 P0，停止相關版本／路徑。
2. 按 user、idempotency key、gift_id、movement 找權威事實。
3. 禁止直接 update balance。
4. 建 reconciliation case。
5. 經 maker-checker 發 adjustment。
6. 全量掃描相同 defect pattern。

### 23.5 Payout UNKNOWN

1. 保持 reservation。
2. 停止同 business key 的新 attempt。
3. 查 provider request、callback、query、statement。
4. 無 terminal evidence 時進 manual。
5. 成功／失敗確認後再推進本地狀態。

### 23.6 Region failover

1. 停止舊 writer admission。
2. 確認 ownership epoch 與 replication watermark。
3. fence 舊 region。
4. 只在安全點啟用新 writer。
5. 對 wallet、movement、gift、outbox、earning 做增量對帳。
6. 舊 region 恢復時只能作 follower，不能自行重新接收寫入。

### 23.7 Recharge confirmed 但 wallet 未入帳

1. 驗證 callback／query／statement 簽名、amount、currency 與 provider transaction id。
2. 確認 Recharge Order 已進 CONFIRMED／CREDIT_PENDING。
3. 以原 recharge_id 重送同一 CreditWallet command，不建立新充值單。
4. 查 Funds Core processed command／movement；若已入帳只補回結果。
5. 修復後重新執行 provider ↔ recharge ↔ wallet credit ↔ journal 對帳。

## 24. 常見錯誤方案

### 24.1 「先播動畫，再扣款」

錯。公共付費動畫只能由 committed gift 觸發；否則展示會創造不存在的交易事實。

### 24.2 「最後按動畫次數算主播收益」

錯。動畫可合併、丟失、重送或過期；收益只能按 gift transaction／ledger 計算。

### 24.3 「Redis balance 快，所以直接在 Redis 扣」

若 Redis 是不可重建、無 durable ledger 的唯一資金真相，故障與修復風險不可接受。Cache 可以加速讀取，不能繞過權威 movement 與 transaction。

### 24.4 「加分布式鎖就一致」

鎖只協調 contender，不會自動完成 wallet movement、gift、outbox、earning 與 payout 的原子或恢復責任。鎖過期後的 stale writer 仍需 resource-side version／constraint。

### 24.5 「Kafka exactly-once，所以收益不會重複」

Broker 的投遞與 producer transaction 保證不能自動涵蓋另一個資料庫中的 earning effect。consumer 仍需 inbox／dedup、local transaction 與 reconciliation。

### 24.6 「Queue 可以無限削峰」

當 arrival rate 長期高於 service rate，queue 只會把事故轉成 backlog 與資料過期。必須 admission control、backpressure、capacity 與降級。

### 24.7 「資料庫主從切換後直接重試」

commit outcome unknown 時直接換新 key 重試可能重複扣款。先查原 idempotency key 與 gift result。

### 24.8 「人工直接改一個 balance 數字」

這會破壞 movement／ledger 可重建性。人工只能發受審批的 adjustment command，並重新對帳。

## 25. 何時考慮演進到其他方案

### 25.1 演進到同步 creator posting

只有在以下條件同時成立時重新評估方案 B：

- 專用 Ledger 能在一個明確 transaction boundary 原子 posting 多腿分錄；
- hot creator 不會形成不可接受的同步瓶頸；
- API 延遲與可用性仍符合 SLO；
- 業務／法規確實要求 API success 時 creator pending 已正式過帳。

即使如此，房間廣播和 payout 仍保持異步。

### 25.2 Combo reservation

若同一用戶的高頻 combo 使 wallet row 成為瓶頸，可以設計短期 reservation／budget：

- 先原子預留一個有上限的 coin budget；
- combo 在 reservation 內消耗；
- expiry 後釋放未用額度；
- confirm／release 冪等；
- 全程可對帳。

這會增加 reservation state、expiry 與回收複雜度，不作第一版預設。

### 25.3 跨區域同步 Funds Core

只有 region 級 RPO 0 的業務價值高於跨區域寫延遲、成本與運維複雜度時，才引入跨區域共識。多活名稱本身不能證明不會 double spend。

## 28. 面試版完整回答

> 我會先把直播送禮拆成三個不同邊界。第一個是資金寫入邊界：用戶平台幣扣減、wallet movement、gift transaction、clearing fact 和 Outbox 必須在付款用戶所在 shard 的同一本地短事務提交；API 只有 commit 後才回覆成功，同一 idempotency key 只能產生一次扣款。第二個是即時互動邊界：GiftCommitted 經 Outbox 可靠發布，房間服務用 WebSocket、lane、連擊合併與階層式 fan-out 做毫秒到秒級展示；動畫、榜單是可重建 projection，不是財務真相。第三個是收益與結算邊界：Creator Earnings 按 gift_id 冪等地記入 pending，經風控與 adjustment 後變 available，再由 payout 狀態機出款。熱門流量按 payer user_id 分片，避免熱門主播進入同步扣款 hot path；熱門房間只在展示層做 lane 與降級。消息可能重複、亂序、延遲，所以不宣稱端到端 exactly-once，而是用本地 transaction、Outbox、consumer inbox、immutable ledger、狀態機與 reconciliation 證明不重複扣款、收益不多不少。最後用故障矩陣、hot-key 壓測、region failover、backup restore 與 Difference → Repair → Verify 演練驗證方案。

## 30. 最終結論

生產級直播打賞不是在「強一致」與「高併發」之間二選一，而是把不同責任放到正確邊界：

~~~text
同步強一致：
用戶扣款 + gift truth + movement + clearing + outbox

可靠異步：
GiftCommitted 傳播 + creator pending + risk + analytics

低延遲最終一致：
動畫 + combo + leaderboard + room counters

財務收口：
pending → available → paid
+ reconciliation
+ audited repair
~~~

真正的核心不是 MQ、Redis 或某個框架，而是：

1. API success 到底證明了什麼；
2. 哪個 durable fact 是唯一 source of truth；
3. 重複、亂序、timeout 與 crash 後如何回到同一結果；
4. 熱點與過載時哪些功能可以降級、哪些 invariant 絕不能放鬆；
5. 最後如何以 ledger、provider evidence 與 reconciliation 證明錢沒有多、沒有少、也沒有重複。
