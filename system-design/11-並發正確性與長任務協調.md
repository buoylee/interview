# 並發正確性與長任務協調

## 問題背景

高併發系統中的錯誤，很少只是「兩個請求同時進來」。真正困難的是：任務執行時間可能拉長，worker 會 crash，網路會 timeout，請求與消息會重複，跨服務操作會部分成功，而系統仍要維持業務不變量（business invariant）。例如，同一付款不能重複產生業務副作用、同一批報表不能混入兩個版本、庫存不能被重複消耗、舊事件不能覆蓋新狀態。

只問「要用 MySQL lock、Redis lock、queue，還是 Saga」會把工具當成問題。正確起點是先說出哪個錯誤絕不能發生，再找出能夠原子保護它的最小邊界。

## 本章定位與閱讀契約

本章不是 lock、Saga 或 queue 百科；它負責辨認問題、選型與解釋 failure boundary（失敗邊界），機制細節交給深度專題。全章固定沿著這條推理鏈前進：

```text
業務不變量
→ 保護對象
→ 一致性邊界
→ 競爭程度
→ 故障模型
→ 選擇機制
→ 證明與修復
```

閱讀任何方案時，都要追問：原子邊界在哪裡、邊界外會發生什麼、失敗後以什麼為單位恢復，以及如何證明不變量仍成立。機制名稱不能代替這四個答案。

### 穩定術語

| 術語 | 本章固定含義 |
|---|---|
| **業務不變量（invariant）** | 所有合法執行與恢復路徑都必須成立的業務條件；先描述禁止的結果，不先指定工具。 |
| **保護對象** | 真正不能被並發破壞的資料、可消耗資源、有效 owner、aggregate 狀態或流程結果。 |
| **一致性邊界** | 一組變更能被同一原子機制共同提交或拒絕的範圍；邊界之外沒有隱含的 ACID 保證。 |
| **競爭程度** | 多個 contender 同時修改同一保護對象的頻率與集中度；它決定等待、衝突與重試成本。 |
| **故障模型** | 設計明確承認的 crash、timeout、duplicate、late result、partial success 與 unknown outcome。 |
| **選擇機制** | 為特定 invariant、邊界、競爭與故障組合選出的約束、原子更新、鎖或 durable protocol。 |
| **證明與修復** | 以提交結果、不可變事實、審計與對帳證明結果；發現偏差後能重試、補償或人工修復。 |

## 非目標

- 不提供 SQL、Java、Go 或框架實作範本。
- 不重寫 InnoDB、Redis、queue、Saga、TCC 或 durable workflow 的底層教程。
- 不把 framework capability、消息投遞語義或單一鎖，宣稱成端到端業務正確性。
- 不假設一套方案適合所有問題，也不推測供應商未公開的內部實作。

## Part A · 先從不變量出發

### 五類經常被混稱為「鎖」的問題

| 問題類型 | 真正要保護的東西 | 典型錯誤 | 錯誤工具直覺 |
|---|---|---|---|
| **互斥執行** | 同一任務的有效 owner | 同一任務由兩個 worker 重複產生副作用 | 「取得一把鎖」就等於舊 owner 永遠不能再寫入 |
| **穩定批次** | 同一批輸入的成員與值，且都屬於同一業務版本 | 長任務前半讀到舊值、後半讀到新值，產出混合版本 | 用長時間 `FOR UPDATE` 凍結整批來源資料 |
| **資源預留** | 庫存、資金、座位等可消耗能力 | 超賣、重複扣減，或失敗後能力永久占用 | 鎖住業務物件或任務，就等於保住可消耗額度 |
| **有序狀態** | 同一 aggregate 的合法狀態遷移 | 晚到事件或舊命令覆蓋較新的合法狀態 | 只要消息有順序或處理端加鎖，狀態遷移自然合法 |
| **跨服務收斂** | 多個服務各自提交的本地結果 | 永久部分成功，且無法判定、補償或解釋最終結果 | 一個 DB transaction、queue 或「exactly-once」名稱可以涵蓋所有服務 |

這五類問題可能同時出現在一條業務流程中，但它們的保護對象與恢復單位不同。例如，「只有一個 worker」只能處理執行權競爭，不能自動固定批次版本，也不能保證外部副作用只發生一次。反過來，穩定批次可以允許多個 worker 重算，只要發布邊界只接受同一版本的合法結果。

因此，需求應先寫成可驗證的禁止條件，例如「已確認的預留總量不得超過可售能力」或「狀態版本只能單調前進」。寫不出 invariant，就無法判斷鎖住了正確對象，還是只把競爭移到別處。

**鎖是機制，不是需求；先說 invariant，再談工具。**

## Part B · 一致性邊界階梯

### 五層邊界

```text
單條原子操作
→ 本地短事務
→ 單服務 durable state
→ 跨服務 workflow
→ 外部不可控系統
```

協調總範圍擴大時，單一同步 ACID 邊界能覆蓋的端到端比例下降；設計必須把無法納入同一 transaction 的完成狀態、重試依據與恢復責任寫成 durable data（可持久恢復的資料）。

| 層級 | 原子邊界 | 主要失敗 | 恢復單位 | 附加機制 |
|---|---|---|---|---|
| **單條原子操作** | 一個儲存引擎可原子判斷並提交的單一操作 | 條件不成立、唯一衝突；回應遺失時 caller 不知道是否已提交 | 單次業務命令 | 唯一約束、條件式寫入、明確結果檢查；有重試時加入 idempotency key 或結果查詢 |
| **本地短事務** | 同一資料庫 transaction 內的一組讀寫 | lock wait、deadlock、transaction rollback；連線中斷造成 commit outcome unknown | 整個本地 transaction | 小鎖面、固定加鎖順序、有限重試、idempotency 與提交後狀態查詢 |
| **單服務 durable state** | 每次只原子提交一個本地狀態遷移；完整任務跨越多個短事務 | 進程在步驟間 crash、工作停滯、重複執行、舊 worker 晚到 | 一個 task 或 aggregate | durable state machine、owner/lease/fencing、heartbeat、reclaim 與審計歷史 |
| **跨服務 workflow** | 每個服務只有自己的本地 transaction，沒有隱含的全域提交 | dual write、消息重複或亂序、部分成功、補償失敗 | 一個 workflow instance | Outbox、idempotency、Saga/TCC、durable workflow、compensation 與 reconciliation |
| **外部不可控系統** | 本地提交與外部副作用分屬不同控制域 | timeout 後結果未知、對方不支援冪等或查詢、人工操作改變結果 | 一筆端到端業務請求或對帳案件 | 穩定請求識別、結果查詢、不可變審計事實、reconciliation、manual review 與可解釋修復 |

表中的「附加機制」不是把更高層重新變成一個大 transaction。它們的作用是保存足夠事實，讓重複、晚到與部分成功可以被識別，並讓系統在同步原子邊界之外繼續收斂。

### 短事務與長任務不是秒數分類

固定秒數只能作監控門檻，不能定義正確性邊界。同樣是 500 毫秒，若 transaction 在等遠端系統且進程 crash 後需要另一個 worker 接管，它已具備長任務的故障形態；同樣是數秒的本地批量更新，若延遲有上界、鎖面可控並在單一 transaction 內完成，仍可能屬於本地短邊界。

| 檢查維度 | 本地短事務可接受的邊界 | 必須離開長 DB transaction 的訊號 |
|---|---|---|
| **外部 I/O** | 不包含 HTTP、RPC、MQ 確認或其他控制域回應 | transaction 正等待或依賴外部結果 |
| **延遲上界** | 路徑與工作量有界，能設定合理的 lock/statement/transaction timeout | 受排隊、網路、人工或資料量影響，完成時間不可預測 |
| **進程生命週期** | 同一 request/process 在 transaction 結束前持續存活即可完成 | 工作需要跨 deploy、restart、worker 消失或長時間暫停 |
| **接管需求** | transaction 成功提交或整體回滾，不需要另一個 owner 接續中間狀態 | crash 後必須從 durable checkpoint 由新 owner 繼續 |
| **鎖住的稀缺資源** | DB connection、row/index lock、undo 與熱點容量的占用短且有界 | 長時間占用連線、鎖、undo、庫存或其他共享能力，阻塞無法接受 |

只要流程跨出本地 transaction 的生命週期，就要提升到對應的一致性層級；不能藉由調大 timeout，把缺少的 durable state 與恢復協議藏起來。

## Part C · 本地短邊界

本地 OLTP 邊界先選能直接表達 invariant、鎖面最小的機制，再隨著約束複雜度與衝突成本往下走：

```text
唯一約束／原子條件更新
→ Optimistic CAS
→ Pessimistic Lock
→ 固定順序的短事務
```

這是選型順序，不是強弱排名。越早的機制越容易把「判斷與寫入」壓縮進單一原子操作；後面的機制用更大的臨界區換取跨欄位、跨行或跨表的判斷能力。

### 四種本地方案的 binding contract

| 方案 | Invariant／保護對象 | 原子邊界 | 保證與不保證 | Crash／接管 | Stale owner | 高併發退化 | 驗證與修復 |
|---|---|---|---|---|---|---|---|
| **唯一約束／原子條件更新** | 業務識別唯一，或單次 predicate 保護的 row／可消耗能力 | 儲存引擎檢查約束或 predicate 並提交的單一操作 | 保證衝突寫入只有符合約束者成功；不保證多行、多步驟或外部副作用 | 未提交操作隨 session 失效而回滾，原 transaction 不能接管；新 session 重讀 durable business state 後重判。commit outcome unknown 時先按業務鍵查結果，再決定是否以同一 idempotency key 重試 | 沒有 owner 語義；只會拒絕違反唯一性或 predicate 的舊嘗試。需要拒絕舊 owner 時，必須把 version／fence 納入 predicate | 熱點 row 形成 lock wait；唯一鍵衝突與失敗寫入放大負載 | 檢查 affected rows／constraint conflict，按業務鍵重讀提交結果；邊界外結果靠 audit 與 reconciliation 修復 |
| **Optimistic CAS** | aggregate 的版本化合法遷移 | 以 expected version 為 predicate，把值與 version 一次推進 | 保證同一 expected version 只有一個寫入成功；不保證跨 aggregate 或外部副作用 | 未提交 CAS 隨 session 失效而回滾，原 transaction 不能接管；新 session 重讀 durable value／version 後重判。commit outcome unknown 時先查目前 version 與命令結果，再決定是否冪等重試 | 舊 version 會被拒絕；CAS 不是 lease，若 version 未推進就無法單憑 CAS 辨識過期 owner | 熱點 version 反覆 conflict，無界重試形成 retry storm | 檢查 affected rows、目前 version 與 transition history；重新讀取、重算並有限重試，邊界外結果靠 reconciliation 收口 |
| **Pessimistic Lock** | 被鎖定 row／index 範圍內的 read-modify-write invariant | locking read、判斷與寫入所在的同一本地 transaction | 保證衝突 transaction 在鎖範圍內等待或失敗；不保證未鎖資料、commit 之後或外部副作用 | session 失效後未提交 transaction 回滾且不能接管；新 session 必須重讀 durable business state 後重判。commit outcome unknown 時先查業務結果，再決定是否冪等重試 | 鎖只代表當前 session／transaction；釋放後晚到 worker 以新 transaction 回來時不會自動被辨識，需另加 business version／fence | 熱點排隊與串行、lock timeout、deadlock；鎖面或持鎖時間放大阻塞 | 查 transaction outcome、durable business state 與 lock-wait evidence；deadlock 後整個 transaction 有限重試，不能只補跑後半段 |
| **固定順序短事務** | 同一資料庫內跨多行／多表的完整 invariant | 依固定全序取得必要鎖並一次 commit／rollback 的本地 transaction | 保證本地變更 all-or-nothing，且所有路徑遵守全序時避免反向取鎖造成的循環等待；不保證無一般鎖等待、跨資料庫或外部結果 | session 失效後未提交 transaction 回滾且不能接管；新 session 重讀全部 durable business state 後重判。commit outcome unknown 時先查完整業務結果，再決定是否冪等重試 | transaction 結束後沒有 owner 身分延續；要拒絕晚到命令，需在狀態遷移中加入 business version／fence | 鎖面擴大、熱點串行與等待鏈；其他路徑或範圍鎖仍可能造成 deadlock | 以 constraints、跨行狀態與 audit facts 驗證整體提交；失敗時重跑整個 transaction，邊界外偏差交給 reconciliation |

### 1. 唯一約束／原子條件更新

如果 invariant 可以寫成資料庫直接拒絕的條件，先讓儲存引擎在提交點判斷。例如，唯一約束保護「同一業務識別只能建立一次」；原子條件更新則把前置條件與狀態變更合成一次不可分割的操作，並以是否實際更新作為競爭結果。

這種設計縮短 read-modify-write window（先讀、在應用判斷、再寫之間的競爭窗口）。若先讀剩餘量，再在應用中判斷，另一個 transaction 可以在兩步之間修改它；把「剩餘量足夠才扣減」放進同一原子條件更新，失敗者會在提交邊界得到明確的未更新結果。

它只保證條件能完整落在同一原子操作內的 invariant。若判斷依賴多行、多表或外部狀態，就不能把一次更新成功誤稱為端到端完成。

### 2. Optimistic CAS

Optimistic CAS（optimistic compare-and-set，樂觀比較後設定）讀取值與版本，寫入時要求版本仍等於預期值；只有一個 contender 能推進版本，其他 contender 得到可辨識的 conflict。它適合衝突低、重新讀取與重算成本可接受的場景，因為無衝突路徑不必先長時間等待鎖。

CAS 的 conflict 是控制流程的一部分，不是可以無限立即重試的例外。當大量請求集中在同一熱點，成功者每次推進版本都會讓其他請求失敗；無界重試會放大資料庫負載、延遲與排隊，形成 retry storm。高衝突時應限制重試、加入退避，並重新評估是否改用等待式串行、按 key 分區或資源拆分，而不是只增加 worker。

CAS 保護的是「從預期版本到下一版本」這一次本地遷移；它不保證讀取之後發生的外部副作用，也不會自行恢復 caller 在成功提交後遺失回應的 unknown outcome。

### 3. Pessimistic Lock

Pessimistic Lock（悲觀鎖）先取得資料庫鎖，再在鎖保護下完成必要的讀取、判斷與寫入。它適合重算不可接受、競爭者等待比反覆衝突更便宜，而且臨界區延遲有界且短的情況。

DB 鎖是 OLTP 正確性的基礎，不是「大型系統不用鎖」。InnoDB 的 locking read 可以讀取最新可用資料並鎖住讀到的記錄與相關索引項；鎖會在 transaction commit 或 rollback 時釋放。這個保證精確地止於該本地 transaction，詳見 [MySQL 8.4 Locking Reads](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)。

因此，Pessimistic Lock 要同時滿足三個條件：鎖定條件能走合適索引、鎖面只覆蓋 invariant 必需的資料、transaction 內只保留有界的本地工作。鎖範圍過大會降低無關請求的並發，持鎖時間過長會把等待、deadlock 與連線占用推向整個系統。

### 4. 固定順序的短事務

當 invariant 橫跨多行或多表，單條更新與單一 row lock 無法完整表達時，把必要變更放進同一本地短事務，所有程式路徑都依固定順序取得鎖。例如，跨多個 aggregate key 時採用一致的全序，而不是讓不同請求依輸入順序任意加鎖。

固定全序避免由取鎖順序相反造成的循環等待，小鎖面則減少競爭者被牽連的範圍；兩者必須一起使用。固定全序不消除一般鎖等待，資料庫也仍可能因其他路徑、範圍鎖或引擎選擇而中止 transaction，所以 caller 必須把 deadlock/serialization failure 視為整個 transaction 失敗，只做有界且安全的重試，不能只補跑後半段。

### 離開 DB transaction 的明確界線

外部 I/O、人工等待、不可預測計算或 crash 接管一旦出現，就離開 DB transaction。先用短事務提交可恢復狀態，再由邊界外的協調機制推進；不能在持有 row/index lock 與 DB connection 時等待遠端世界。

原因不是「transaction 超過幾秒」這個數字本身，而是本地資料庫無法原子控制外部結果，進程 crash 後原 transaction 也不能交給新 worker 繼續。延長 lock timeout 只延長資源占用，不會增加跨系統原子性或接管能力。

## Part D · 單服務長任務方案

長任務不是把 Part C 的 transaction 拉長，而是把生命週期拆成多個可提交、可辨識、可重試的短邊界。每一步只原子保存一個狀態遷移或資源決定；步驟之間的等待、計算與外部 I/O 都在 transaction 之外。

以下六類方案不是互斥選項。一個批次任務可以同時使用 Durable State Machine 保存進度、Immutable Batch 固定輸入、Lease/Fencing 管理 owner，最後以 Shadow Build 發布結果。無論如何組合，每個方案都必須回答同一份 binding contract：

1. **Invariant**：哪個非法結果絕不能出現？
2. **保護對象**：真正被保護的是任務狀態、輸入版本、可消耗能力、resource key，還是發布指標？
3. **原子邊界**：哪一次本地操作能共同提交或拒絕？
4. **保證**：該邊界能證明什麼？
5. **不保證**：哪些步驟、資料或外部副作用仍在邊界外？
6. **Crash／接管**：原 worker 消失後，新 owner 從哪個 durable fact 繼續？
7. **Stale owner**：舊 owner 晚到時，哪個寫入邊界會拒絕它？
8. **高併發退化**：競爭集中時，會變成衝突、排隊、backlog、掃描壓力，還是 hot partition？
9. **驗證與修復**：以哪些不可變事實證明結果；偏差如何重試、重建、補償或人工處理？

只寫「用了 queue／lock／workflow」仍未完成設計；若上述任一題沒有 owner 與 durable data，crash 後就只能靠猜測恢復。

### 1. Durable State Machine

Durable State Machine 把任務生命週期保存成 durable state，而不是只存在 worker 記憶體。典型狀態會表達待處理、執行中、等待外部結果、完成、失敗或需要人工處理；具體名稱不重要，重要的是每個 transition 都有合法前置狀態、穩定 task id 與可審計結果。

| Binding contract | 回答 |
|---|---|
| **Invariant** | 任務只能沿合法 transition 前進；crash 後不得把「沒有證據」當成完成，也不得遺失已提交進度。 |
| **保護對象** | task 的生命週期、目前 step、輸入／結果引用、重試與人工處理狀態；不是某個 worker process。 |
| **原子邊界** | 以 expected state／version 為前置條件，在一次本地短事務內提交單一步驟結果、下一狀態與必要 audit fact。完整任務不是一個 transaction。 |
| **保證** | 已提交 checkpoint 可跨 process restart 保存；新 worker 能由 durable state 判斷已完成與待執行步驟。 |
| **不保證** | 不保證每個 step 只執行一次，也不會把本地狀態遷移與外部副作用變成同一原子提交；外部 timeout 仍可能是 unknown outcome。 |
| **Crash／接管** | 以 state、version、最近 checkpoint 與穩定 task id 重建上下文；新 owner 先原子 claim，再重做可冪等步驟或查詢不確定的外部結果。不能從舊 worker 的 stack 接續。 |
| **Stale owner** | transition 必須同時檢查 expected state／version 與 owner token；舊 owner 即使醒來，也不能覆蓋已由新 owner 推進的 task state。外部資源另需 idempotency 或 fence。 |
| **高併發退化** | 熱門 task 反覆 CAS conflict；大量到期任務造成 claim 掃描、retry 與 recovery storm；下游變慢時 durable backlog 持續增加。 |
| **驗證與修復** | 檢查 transition history、狀態停留時間、重試次數與 unknown outcome；卡住任務依 checkpoint 重領，外部結果先查詢再重試，無法自動判定者進 manual review。 |

Durable State Machine 的價值是保存「現在知道什麼、下一步允許做什麼」，不是保證邊界外的世界已依照流程狀態完成。若狀態寫成 `SUCCEEDED`，卻沒有可指向業務結果的 evidence，這個狀態本身不能證明 invariant。

### 2. Lease、Heartbeat 與 Fencing

`owner token` 是一次持有關係的唯一身分；lease 給這個 owner 一段有界的所有權判斷；heartbeat 在任務仍有進展時更新 lease 活性；fencing token 則提供可比較且單調前進的 owner generation。Kubernetes 公開的 [Lease](https://kubernetes.io/docs/concepts/architecture/leases/) 物件就被用於 node heartbeat 與 leader election，node heartbeat 會更新 `renewTime`。這說明 Lease 是協調與活性訊號，不等於被保護資源已接受某個業務寫入。

SQS 的 [visibility timeout](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html) 提供相似的有界處理權：消息在期限內對其他 consumer 暫時不可見，處理者可延長期限；未刪除且期限到期後，消息會重新可見。官方也明確說明 at-least-once 模型下，即使期限尚未到，也不能絕對保證沒有重複投遞。因此，visibility timeout 可以幫助避免同時重工，不能代替 handler idempotency 或 resource-side validation。

| Binding contract | 回答 |
|---|---|
| **Invariant** | 被保護資源一旦接受較新的 fencing token，之後不得再接受更舊 token；過期 owner 不得覆蓋新 owner 已提交的資源狀態。 |
| **保護對象** | lease 保護的是有界執行權；fencing 保護的是資源寫入順序。任務鎖 key 本身不是錢、庫存或帳本。 |
| **原子邊界** | claim／renew／expire 是 owner registry 的短原子更新；真正的正確性邊界在被保護資源：比較 fencing token，拒絕較舊 token，並與資源寫入一起原子提交。兩個邊界不能互相冒充。 |
| **保證** | lease expiry 讓系統能在 owner 失聯後有界等待並接管；heartbeat 延長活性判斷；resource-side fencing 會以有效 generation 或已接受的最高 fence 拒絕舊 token。 |
| **不保證** | lease 到期不會讓舊 worker 自動停止；GC pause、網路延遲或 timeout 後，它仍可能繼續執行。若資源不驗證 fence，lock／lease 單獨不能保證資金、庫存或外部副作用正確。 |
| **Crash／接管** | 期限到且 durable state 仍未完成時，新 worker 原子取得新 owner token 與更高 fence，從已提交 checkpoint 繼續；舊嘗試的 unknown outcome 先查詢，不直接重做不可冪等副作用。 |
| **Stale owner** | owner registry 只會讓舊 token 失去續租資格；被保護資源必須在每次寫入時驗證有效 generation，至少記住已接受的最高 fence 並拒絕更小 token。無法加 fence 的外部系統改用穩定 idempotency key、結果查詢與 reconciliation。 |
| **高併發退化** | 熱門 lease 形成 renew／claim 寫入熱點；同時到期會引發 thundering herd，過密 heartbeat 也會消耗協調儲存。採用有界退避、jitter、分片掃描與合理租期，但不能藉此省略 fence。 |
| **驗證與修復** | 審計每次 owner token、fence 發放、renew、接管與資源接受／拒絕結果；監控雙 owner 痕跡、過期後寫入與 lease churn。無 fence 資源以業務帳、外部查詢和對帳辨認重複副作用。 |

所以，owner token、lease、heartbeat、fencing 是四個不同責任：身分、期限、活性更新與資源端拒絕。Redis 鎖的過期、續期、failover 與 fencing 失敗窗口可繼續閱讀 [分布式鎖](../redis-handson/07-distributed-locks/README.md)。

### 3. Immutable Batch

穩定批次要分別固定 **membership** 與 **value**。membership manifest 保存哪些資料屬於批次；value snapshot 保存完整輸入，或保存能永久解析到同一內容的 immutable version。只保存一串 mutable row ID，只能重建成員名稱，不能保證接管重算時仍讀到相同值。

`cutoff`／source version 是捕獲邊界：它定義「這個批次看見哪個時間或版本以前的事實」，不代表來源資料從此停止演進。來源可以繼續接受新寫入；舊批次仍靠 sealed manifest 與 immutable value reference 重現同一輸入。

| Binding contract | 回答 |
|---|---|
| **Invariant** | 同一 batch 的所有輸出必須由同一份 membership 與同一組 value／version 推導，不得混入捕獲邊界兩側的資料。 |
| **保護對象** | sealed batch manifest、每個 item 的不可變輸入或 immutable version、cutoff 與輸出所屬 batch id。 |
| **原子邊界** | 建立並 seal manifest 是一次本地提交；每個 item 以 `(batch_id, item_id)` 短事務記錄結果；完成驗證後再以一個短邊界發布該 batch。計算過程不在同一 transaction。 |
| **保證** | 保存 membership 能固定成員；保存完整值或不可變版本才能讓 retry／接管重算同一輸入。 |
| **不保證** | 只存 ID 不會固定 value；cutoff 不會凍結來源；manifest 正確也不保證計算程式、外部依賴或輸出一定正確。 |
| **Crash／接管** | 新 worker 依 sealed manifest 找出缺少或 outcome unknown 的 item，以同一 batch id 與輸入版本冪等重算；不重新查詢「目前符合條件的資料」來替換原 membership。 |
| **Stale owner** | 每個結果必須綁定 batch id、item id 與 input version；發布時檢查 expected active version／generation，拒絕舊 batch 晚到覆蓋新發布結果。 |
| **高併發退化** | 大 manifest 造成建立、儲存與掃描壓力；單一 batch 的完成計數成為熱點；大量 item fan-out 可能壓垮下游。以 immutable partition、分段進度與有界 admission 控制。 |
| **驗證與修復** | 比對 manifest count、input hash／version、item 完成集合與輸出 checksum；缺項只補算同一版本，混合版本則隔離整批、重建並重新發布，不能局部宣告成功。 |

### 4. Reservation

Reservation 保護的是可消耗能力，不是凍結整個業務物件。庫存、資金或座位在 Hold／Try 時被暫時占用，成功流程再 Confirm，放棄或逾期則 Release／Cancel。Stripe 公開的 [authorization 與 capture](https://docs.stripe.com/payments/place-a-hold-on-a-payment-method) 就呈現這種資源語義：先保留可之後 capture 的資金，必須在 authorization 到期前 capture，否則資金會釋放且付款狀態轉為 canceled。

| Binding contract | 回答 |
|---|---|
| **Invariant** | active hold 加 confirmed consumption 不得超過可消耗能力；同一 reservation 不能同時成為已確認與已釋放。 |
| **保護對象** | 可消耗額度與具穩定 reservation id 的 Hold／Confirm／Release 生命週期；不是商品、帳戶或座位物件的全部欄位。 |
| **原子邊界** | Hold 以條件式更新同時扣除可用能力並建立 reservation；Confirm／Release 分別以 reservation state 為 predicate 做冪等短 transition。等待客戶或遠端結果期間不持有 DB lock。 |
| **保證** | 成功 Hold 在有效期內保留指定能力；idempotent Confirm／Release 讓重複命令收斂到同一 terminal result；expiry 提供遺棄預留的恢復入口。 |
| **不保證** | 不凍結整個物件，不等於 DB 長鎖，也不保證跨服務流程一定完成。expiry 只是可回收條件；若沒有執行 reclaim／reconciliation，能力仍可能長期占用。 |
| **Crash／接管** | 新 worker 以 reservation id 查詢 durable state；active 且流程仍有效時續辦，已 confirmed／released 時回傳原結果，逾期或 unknown 時依業務事實執行 release、結果查詢或人工處理。 |
| **Stale owner** | Confirm／Release 必須檢查 reservation state、expiry 與 version；舊 owner 對已釋放或已確認 reservation 的相反動作被拒絕。若外部 provider 已受理，另以 provider request id 查詢。 |
| **高併發退化** | 熱門 SKU／帳戶／場次形成條件更新熱點；短 expiry 帶來重試與回收 churn，長 expiry 降低可用能力；大量逾期掃描會集中負載。可按資源 key 分區並限制排隊。 |
| **驗證與修復** | 驗證 `available + active holds + confirmed` 與權威 capacity 的守恆關係，掃描逾期與不合法 terminal 組合；漏釋放要 reclaim，外部結果不一致則 reconciliation 或 manual review。 |

Reservation 只有在資源真的具備 Try／Hold、Confirm、Cancel／Release 語義時才成立；若 Hold 沒有實際減少可用能力，它只是流程標記，不能防止超賣或超額使用。

### 5. Per-Key Serialization

Per-Key Serialization 只讓同一 `resource key` 的命令局部串行，其他 key 仍可平行。例如，同一 account／order／aggregate 的 transition 依 durable sequence 處理，不相關 key 可由其他 partition 或 worker 同時推進。等待中的命令保存在 durable queue，不占用 DB connection，也不長時間持有 row lock。

| Binding contract | 回答 |
|---|---|
| **Invariant** | 同一 resource key 的命令必須依已定義順序套用合法 transition，舊 sequence 不得覆蓋新狀態。 |
| **保護對象** | 每個 key 的 durable command order、目前 aggregate version 與處理結果；不是全系統的總順序。 |
| **原子邊界** | durable enqueue 保存命令；consumer 每次以 key、expected sequence／version 在本地短事務提交一個 command result。排隊時間與完整 queue 不在同一 DB transaction。 |
| **保證** | 同一 key 可以局部等待式串行，其他 key 保有並行；durable queue 讓 worker crash 時等待命令仍可重新交付。 |
| **不保證** | 不保證跨 key 順序、單次投遞或外部副作用 exactly-once；queue 順序也不能代替 aggregate 自身的合法 transition 與 version 檢查。 |
| **Crash／接管** | 未確認命令留在或回到 durable queue；新 consumer 依 command id、key、sequence 與 aggregate version 判定重做、回傳既有結果或送入例外流程。 |
| **Stale owner** | 舊 consumer 的 expected sequence／version 會在 aggregate 寫入被拒絕；若同一 key 的執行權會過期，再加 owner token／fence，外部呼叫則用 idempotency key。 |
| **高併發退化** | hot key 形成不可水平拆散的 backlog、tail latency 與 hot partition；長命令造成 head-of-line blocking，partition 間也可能不公平。需 backpressure、配額、公平排程與隔離慢命令。 |
| **驗證與修復** | 監控 per-key lag、sequence gap／duplicate、最老消息年齡與 poison command；重播前核對 aggregate version，無法處理者進 DLQ／manual review，不能跳過後假裝順序完整。 |

Per-Key Serialization 是把競爭成本從 CAS retry 移成可觀測 backlog。它適合高衝突且順序本身有業務意義的 aggregate；若所有請求共用一個過粗 key，結果只是把服務退化成單線程。

### 6. Shadow Build

Shadow Build 讓在線舊版本持續服務，在背景以獨立版本建立新索引、配置、讀模型或大型轉換結果。新版本完成一致性驗證後，再以很短的原子邊界切換 active pointer；不在原資料上逐段覆寫，也不要求讀者在半成品上工作。

Elasticsearch 官方的 [alias API](https://www.elastic.co/guide/en/elasticsearch/reference/current/aliases.html) 公開支持在單一原子操作執行多個 alias actions，並以 alias 切換實現 reindex without downtime。這是「背景建新版本，最後切換名稱」的具體公開行為；它不代表任意外部系統或任意多資源切換都自動具有相同原子性。

| Binding contract | 回答 |
|---|---|
| **Invariant** | 線上讀者只能看到已完整驗證的舊版本或新版本，不得把兩個版本的部分內容混成 active result。 |
| **保護對象** | immutable build version、驗證證據與 active pointer／alias；舊版本在切換與觀察期內仍可服務或回退。 |
| **原子邊界** | 背景 build 與驗證各自跨多個短提交；只有最後 pointer／alias swap 是單一短原子操作。若有多個無法共同切換的 consumer，就沒有隱含的全域原子發布。 |
| **保證** | 在 pointer 邊界內，讀者不會看見已發布版本的半成品；舊版本可在新 build 期間持續服務，驗證失敗可以不發布。 |
| **不保證** | 不保證 build 計算正確、增量追趕沒有漏資料，也不適合必須原地產生不可逆副作用的流程；alias 原子性不會涵蓋 alias 之外的 cache 或外部系統。 |
| **Crash／接管** | 新 worker 以 build id、source cutoff／version 與 checkpoint 續建或重建；未通過完整驗證的 build 永不成為 active，孤兒版本可延後清理。 |
| **Stale owner** | 發布必須檢查 expected active version 與 build generation；舊 build 晚到只能被拒絕或保留為非 active，不能把較新的 active pointer 換回去。 |
| **高併發退化** | 同時維持新舊版本增加儲存與背景寫入；高變更率使 catch-up lag 無法收斂；多個 build 競爭發布，切換後 cache warm-up 可能造成尖峰。需限制 concurrent build 與 admission。 |
| **驗證與修復** | 切換前比較 count、checksum、抽樣查詢、source version 與 catch-up lag；切換後監控錯誤與語義差異。異常時原子切回已知良好版本，修正後重建，不在 active 半成品上補丁。 |

Shadow Build 適合能建立成獨立版本、讀者能經由 indirection 取得 active version 的結果。若流程的核心是「寄出通知、扣除外部款項」等原地副作用，就應保存 durable workflow state、使用 idempotency／reservation 並對帳，而不是把它包裝成 shadow copy。

## Part E · 跨服務長流程

跨服務流程沒有一個本地 transaction 能同時控制所有參與者。生產設計是把不同責任組合起來，而不是在 Outbox、Saga、TCC、workflow framework 之間選一個名字：

```text
本地事務
+ Outbox 解決 dual write
+ Idempotency 吸收重複
+ Saga/TCC 協調業務結果
+ Durable Workflow 保存控制狀態
+ Reconciliation 收口
```

這是一條依賴關係，不是成熟度排行榜。下層沒有守住 invariant，上層重試得越可靠，只會越可靠地重複錯誤。

### 組合邊界與責任

| 組件 | 保護對象與原子邊界 | 保證 | 不保證與恢復責任 |
|---|---|---|---|
| **本地事務** | 單一服務擁有的業務狀態、帳本、reservation 與同庫 audit／outbox fact | 在自己的 data store 內共同 commit／rollback，直接拒絕違反 service invariant 的寫入 | 不涵蓋 broker、其他服務與外部 provider；commit outcome unknown 時按業務鍵查詢，不盲目重做 |
| **Outbox** | 已提交業務事實與待傳播 event，在同一本地 transaction 寫入 | 消除「業務資料已提交、事件卻沒有留下 durable fact」的 dual write 窗口 | relay 仍可能重送，consumer 仍需 idempotency；Outbox 不保存完整流程進度、timer、compensation，所以不是 workflow engine |
| **Idempotency** | 穩定 request／command id 對應的業務意圖與已提交結果；handler 在本地把 dedupe record 與 effect 一起提交 | 相同 key、相同意圖的 retry 回到同一語義結果，吸收 transport／caller duplicate | 不修復錯誤 key、不同意圖共用 key、跨服務 partial success 或不可查詢的外部結果；需保存足夠久並處理 late request |
| **Saga** | 一個 workflow 的本地 transaction 序列，以及每一步對應的補償狀態 | 以 forward action、retry 與 compensating action 讓多服務流程朝可解釋業務結果收斂 | 不是 ACID rollback；補償可能失敗、與其他合法交易交錯，必須冪等重試、審計並在必要時人工處理 |
| **TCC** | 具有真實資源語義的 Try／Confirm／Cancel reservation | Try 先實際預留資源，Confirm 消耗，Cancel 釋放；每個參與者在自己的本地邊界保護能力 | 不適合沒有可預留資源或無可逆 Cancel 語義的副作用；expiry、idempotency、空回滾／晚到命令與 reconciliation 仍要設計 |
| **Durable Workflow** | workflow instance 的控制進度、timer、retry policy、signal 與 activity outcome | orchestrator crash／restart 後仍能由 durable history 恢復控制流程，安排等待與重試 | 不替代服務內 invariant、帳本、Outbox、handler idempotency 或資源端 fence；workflow state 不是外部業務結果的唯一證據 |
| **Reconciliation** | 各服務 durable fact、帳本、provider result 與 workflow 預期結果之間的差異 | 找出在線協議未能判定或修復的漏單、重複、永久 partial success，並建立可審計修復案件 | 不是只發 alert；若沒有權威來源、修復動作與人工責任人，就不能宣稱流程已收口 |

AWS 的 [Transactional Outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html) 公開說明此模式解決 DB write 與 event notification 的 dual write，並提醒 event processing 可能產生 duplicate，consumer 應追蹤已處理消息以保持 idempotent。這正是 Outbox 與 Idempotency 必須同時存在、但責任不同的原因。

AWS Builders' Library 的 [idempotent API](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/) 以唯一 client request identifier 表達同一意圖，使 retry 能得到語義等價結果。idempotency key 因而是業務協議：服務要綁定請求意圖、保存結果並拒絕同 key 的不同意圖；它不是把兩次碰巧相同的 payload 猜成同一請求。

### Saga、TCC 與補償

Saga 把跨服務流程拆成一串本地 transaction，依每一步 outcome 決定下一個 forward action 或 compensating action。AWS 的 [Saga pattern](https://docs.aws.amazon.com/prescriptive-guidance/latest/modernization-data-persistence/saga-pattern.html) 將它描述為協調多個 microservice transaction 的 failure-management pattern，也明確指出參與者增加會提高除錯與補償設計複雜度。

**補償是新的業務動作，不是時間倒流。** 已完成的扣款可能要以退款收斂、已發出的通知可能只能追加更正、已被第三方看見的事實不能從歷史刪除。每個補償都需要自己的 idempotency key、合法前置狀態、重試與審計；若後續合法交易已改變資源，補償還必須重新判斷，不得假設世界停在原步驟之後。

TCC 是 reservation 語義更強的協調方式：Try 必須真的把庫存、資金或席位從可用能力中保留；Confirm 與 Cancel 只能對同一 reservation 做冪等 terminal transition。若所謂 Try 只寫一筆「準備中」流程紀錄，卻沒有保護資源，它不能提供 TCC 的核心 invariant。Saga 可以協調一般可補償業務動作；TCC 只適合參與者能提供真實 Try／Confirm／Cancel 資源協議的場景。

Saga 與 Event Sourcing 的概念邊界、協作式／編排式取捨可繼續閱讀 [Event Sourcing、領域事件與 Saga](../software-architecture/07-EventSourcing-領域事件-Saga.md)；Outbox、TCC、Temporal 與組合驗證則見 [一致性模式與框架選型](../financial-consistency/05-patterns/README.md)。

### Durable Workflow 不是業務真相替代品

Temporal 的公開首頁把 [Durable Execution](https://temporal.io/) 描述為持久保存 workflow running state，並提供 retry、task queue、signal 與 timer，使流程能在故障後恢復。這些是控制平面的 durable capability：保存走到哪一步、何時重試、正在等哪個 signal，以及 activity 回報什麼結果。

它不會自動讓 activity 的外部副作用 exactly-once，也不能替代服務內 constraint、ledger、reservation 與 reconciliation。activity timeout 後，workflow 仍可能只知道「沒有收到成功回應」，不知道 provider 是否已完成；正確恢復仍要使用穩定 request id、查詢外部結果、把本地 effect 設計成 idempotent，並以帳本或對帳證明最終業務結果。

### 三層交付語義：不要直接宣稱端到端 exactly-once

「消息只送一次」「handler 只跑一次」與「業務副作用只成立一次」是三個不同命題：

| 層次 | 能觀察的事實 | 必要機制 | 不能直接推出的結論 |
|---|---|---|---|
| **Transport delivery** | broker 是否投遞、重投、排序與收到 ack | durable message、ack／visibility、retry、DLQ | delivery ack 不代表 handler transaction 已提交，更不代表跨服務流程完成 |
| **Handler processing** | 某個 message／command id 是否已處理，以及本地 transaction 結果 | inbox／dedupe、idempotency key、expected state／version、本地 audit | handler 只提交一次不代表外部 provider 只產生一次 effect，也不代表其他服務都成功 |
| **Business effect** | 帳本、庫存、reservation、provider record 與 workflow outcome 是否符合 invariant | service constraint、ledger、resource-side validation、結果查詢、Saga/TCC 與 reconciliation | 任一 framework 的「exactly-once」名稱都不能自動擴張成所有控制域的端到端保證 |

因此，文件與監控應分別描述 delivery count、handler attempt／commit result 與 business effect。只有最後一層能回答「錢是否只扣一次、庫存是否超賣、流程是否已收斂」；它需要業務鍵與權威事實證明，不能由 broker 指標代答。

### XA／2PC 的位置

XA／2PC 以同步協調參與者換取一個分散式原子提交決定；代價是參與者在協議期間必須耦合於共同 transaction outcome，失敗時可能阻塞並降低可用性。這種 trade-off 可能適合範圍封閉、參與者都支援協議且延遲有界的同步資料操作，但不作跨人工等待、長時間 timer、不可控外部 API 或可持續數小時／數日業務流程的預設。

不用 XA／2PC 並不表示接受無法解釋的 partial success。預設生產路徑是：各服務先用本地短事務守住自己的 invariant，以 Outbox 傳播已提交事實，handler 用 Idempotency 吸收重複，Saga／TCC 協調業務結果，Durable Workflow 保存控制狀態，最後由 Reconciliation 根據權威事實收口。同步原子性縮小之後，恢復協議與證據必須更明確，而不是消失。
