# 並發正確性與長任務協調

## 問題背景

高併發系統中的錯誤，很少只是「兩個請求同時進來」。真正困難的是：任務執行時間可能拉長，worker 會 crash，網路會 timeout，請求與消息會重複，跨服務操作會部分成功，而系統仍要維持業務不變量（business invariant）。例如，同一付款不能重複產生業務副作用、同一批報表不能混入兩個版本、庫存不能被重複消耗、舊事件不能覆蓋新狀態。

只問「要用 MySQL lock、Redis lock、queue，還是 Saga」會把工具當成問題。正確起點是先說出哪個錯誤絕不能發生，再找出能夠原子保護它的最小邊界。

## 本章定位與閱讀契約

本章不是 lock、Saga 或 queue 百科；它負責辨認問題、選型與解釋 failure boundary（失敗邊界），機制細節交給深度專題。全章固定沿著這條推理鏈前進：

```text
業務不變量
→ 保護對象
→ 一致性邊界
→ 競爭程度
→ 故障模型
→ 選擇機制
→ 證明與修復
```

閱讀任何方案時，都要追問：原子邊界在哪裡、邊界外會發生什麼、失敗後以什麼為單位恢復，以及如何證明不變量仍成立。機制名稱不能代替這四個答案。

返回索引：[生產級分布式系統 L0–L9 master 索引](./README.md)。

### 穩定術語

| 術語 | 本章固定含義 |
|---|---|
| **業務不變量（invariant）** | 所有合法執行與恢復路徑都必須成立的業務條件；先描述禁止的結果，不先指定工具。 |
| **保護對象** | 真正不能被並發破壞的資料、可消耗資源、有效 owner、aggregate 狀態或流程結果。 |
| **一致性邊界** | 一組變更能被同一原子機制共同提交或拒絕的範圍；邊界之外沒有隱含的 ACID 保證。 |
| **競爭程度** | 多個 contender 同時修改同一保護對象的頻率與集中度；它決定等待、衝突與重試成本。 |
| **故障模型** | 設計明確承認的 crash、timeout、duplicate、late result、partial success 與 unknown outcome。 |
| **選擇機制** | 為特定 invariant、邊界、競爭與故障組合選出的約束、原子更新、鎖或 durable protocol。 |
| **證明與修復** | 以提交結果、不可變事實、審計與對帳證明結果；發現偏差後能重試、補償或人工修復。 |

## 非目標

- 不提供 SQL、Java、Go 或框架實作範本。
- 不重寫 InnoDB、Redis、queue、Saga、TCC 或 durable workflow 的底層教程。
- 不把 framework capability、消息投遞語義或單一鎖，宣稱成端到端業務正確性。
- 不假設一套方案適合所有問題，也不推測供應商未公開的內部實作。

## Part A · 先從不變量出發

### 五類經常被混稱為「鎖」的問題

| 問題類型 | 真正要保護的東西 | 典型錯誤 | 錯誤工具直覺 |
|---|---|---|---|
| **互斥執行** | 同一任務的有效 owner | 同一任務由兩個 worker 重複產生副作用 | 「取得一把鎖」就等於舊 owner 永遠不能再寫入 |
| **穩定批次** | 同一批輸入的成員與值，且都屬於同一業務版本 | 長任務前半讀到舊值、後半讀到新值，產出混合版本 | 用長時間 `FOR UPDATE` 凍結整批來源資料 |
| **資源預留** | 庫存、資金、座位等可消耗能力 | 超賣、重複扣減，或失敗後能力永久占用 | 鎖住業務物件或任務，就等於保住可消耗額度 |
| **有序狀態** | 同一 aggregate 的合法狀態遷移 | 晚到事件或舊命令覆蓋較新的合法狀態 | 只要消息有順序或處理端加鎖，狀態遷移自然合法 |
| **跨服務收斂** | 多個服務各自提交的本地結果 | 永久部分成功，且無法判定、補償或解釋最終結果 | 一個 DB transaction、queue 或「exactly-once」名稱可以涵蓋所有服務 |

這五類問題可能同時出現在一條業務流程中，但它們的保護對象與恢復單位不同。例如，「只有一個 worker」只能處理執行權競爭，不能自動固定批次版本，也不能保證外部副作用只發生一次。反過來，穩定批次可以允許多個 worker 重算，只要發布邊界只接受同一版本的合法結果。

因此，需求應先寫成可驗證的禁止條件，例如「已確認的預留總量不得超過可售能力」或「狀態版本只能單調前進」。寫不出 invariant，就無法判斷鎖住了正確對象，還是只把競爭移到別處。

**鎖是機制，不是需求；先說 invariant，再談工具。**

## Part B · 一致性邊界階梯

### 五層邊界

```text
單條原子操作
→ 本地短事務
→ 單服務 durable state
→ 跨服務 workflow
→ 外部不可控系統
```

協調總範圍擴大時，單一同步 ACID 邊界能覆蓋的端到端比例下降；設計必須把無法納入同一 transaction 的完成狀態、重試依據與恢復責任寫成 durable data（可持久恢復的資料）。

| 層級 | 原子邊界 | 主要失敗 | 恢復單位 | 附加機制 |
|---|---|---|---|---|
| **單條原子操作** | 一個儲存引擎可原子判斷並提交的單一操作 | 條件不成立、唯一衝突；回應遺失時 caller 不知道是否已提交 | 單次業務命令 | 唯一約束、條件式寫入、明確結果檢查；有重試時加入 idempotency key 或結果查詢 |
| **本地短事務** | 同一資料庫 transaction 內的一組讀寫 | lock wait、deadlock、transaction rollback；連線中斷造成 commit outcome unknown | 整個本地 transaction | 小鎖面、固定加鎖順序、有限重試、idempotency 與提交後狀態查詢 |
| **單服務 durable state** | 每次只原子提交一個本地狀態遷移；完整任務跨越多個短事務 | 進程在步驟間 crash、工作停滯、重複執行、舊 worker 晚到 | 一個 task 或 aggregate | durable state machine、owner/lease/fencing、heartbeat、reclaim 與審計歷史 |
| **跨服務 workflow** | 每個服務只有自己的本地 transaction，沒有隱含的全域提交 | dual write、消息重複或亂序、部分成功、補償失敗 | 一個 workflow instance | Outbox、idempotency、Saga/TCC、durable workflow、compensation 與 reconciliation |
| **外部不可控系統** | 本地提交與外部副作用分屬不同控制域 | timeout 後結果未知、對方不支援冪等或查詢、人工操作改變結果 | 一筆端到端業務請求或對帳案件 | 穩定請求識別、結果查詢、不可變審計事實、reconciliation、manual review 與可解釋修復 |

表中的「附加機制」不是把更高層重新變成一個大 transaction。它們的作用是保存足夠事實，讓重複、晚到與部分成功可以被識別，並讓系統在同步原子邊界之外繼續收斂。

### 短事務與長任務不是秒數分類

固定秒數只能作監控門檻，不能定義正確性邊界。同樣是 500 毫秒，若 transaction 在等遠端系統且進程 crash 後需要另一個 worker 接管，它已具備長任務的故障形態；同樣是數秒的本地批量更新，若延遲有上界、鎖面可控並在單一 transaction 內完成，仍可能屬於本地短邊界。

| 檢查維度 | 本地短事務可接受的邊界 | 必須離開長 DB transaction 的訊號 |
|---|---|---|
| **外部 I/O** | 不包含 HTTP、RPC、MQ 確認或其他控制域回應 | transaction 正等待或依賴外部結果 |
| **延遲上界** | 路徑與工作量有界，能設定合理的 lock/statement/transaction timeout | 受排隊、網路、人工或資料量影響，完成時間不可預測 |
| **進程生命週期** | 同一 request/process 在 transaction 結束前持續存活即可完成 | 工作需要跨 deploy、restart、worker 消失或長時間暫停 |
| **接管需求** | transaction 成功提交或整體回滾，不需要另一個 owner 接續中間狀態 | crash 後必須從 durable checkpoint 由新 owner 繼續 |
| **鎖住的稀缺資源** | DB connection、row/index lock、undo 與熱點容量的占用短且有界 | 長時間占用連線、鎖、undo、庫存或其他共享能力，阻塞無法接受 |

只要流程跨出本地 transaction 的生命週期，就要提升到對應的一致性層級；不能藉由調大 timeout，把缺少的 durable state 與恢復協議藏起來。

## Part C · 本地短邊界

本地 OLTP 邊界先選能直接表達 invariant、鎖面最小的機制，再隨著約束複雜度與衝突成本往下走：

```text
唯一約束／原子條件更新
→ Optimistic CAS
→ Pessimistic Lock
→ 固定順序的短事務
```

這是選型順序，不是強弱排名。越早的機制越容易把「判斷與寫入」壓縮進單一原子操作；後面的機制用更大的臨界區換取跨欄位、跨行或跨表的判斷能力。

### 四種本地方案的 binding contract

| 方案 | Invariant／保護對象 | 原子邊界 | 保證與不保證 | Crash／接管 | Stale owner | 高併發退化 | 驗證與修復 |
|---|---|---|---|---|---|---|---|
| **唯一約束／原子條件更新** | 業務識別唯一，或單次 predicate 保護的 row／可消耗能力 | 儲存引擎檢查約束或 predicate 並提交的單一操作 | 保證衝突寫入只有符合約束者成功；不保證多行、多步驟或外部副作用 | 未提交操作隨 session 失效而回滾，原 transaction 不能接管；新 session 重讀 durable business state 後重判。commit outcome unknown 時先按業務鍵查結果，再決定是否以同一 idempotency key 重試 | 沒有 owner 語義；只會拒絕違反唯一性或 predicate 的舊嘗試。需要拒絕舊 owner 時，必須把 version／fence 納入 predicate | 熱點 row 形成 lock wait；唯一鍵衝突與失敗寫入放大負載 | 檢查 affected rows／constraint conflict，按業務鍵重讀提交結果；邊界外結果靠 audit 與 reconciliation 修復 |
| **Optimistic CAS** | aggregate 的版本化合法遷移 | 以 expected version 為 predicate，把值與 version 一次推進 | 保證同一 expected version 只有一個寫入成功；不保證跨 aggregate 或外部副作用 | 未提交 CAS 隨 session 失效而回滾，原 transaction 不能接管；新 session 重讀 durable value／version 後重判。commit outcome unknown 時先查目前 version 與命令結果，再決定是否冪等重試 | 舊 version 會被拒絕；CAS 不是 lease，若 version 未推進就無法單憑 CAS 辨識過期 owner | 熱點 version 反覆 conflict，無界重試形成 retry storm | 檢查 affected rows、目前 version 與 transition history；重新讀取、重算並有限重試，邊界外結果靠 reconciliation 收口 |
| **Pessimistic Lock** | 被鎖定 row／index 範圍內的 read-modify-write invariant | locking read、判斷與寫入所在的同一本地 transaction | 保證衝突 transaction 在鎖範圍內等待或失敗；不保證未鎖資料、commit 之後或外部副作用 | session 失效後未提交 transaction 回滾且不能接管；新 session 必須重讀 durable business state 後重判。commit outcome unknown 時先查業務結果，再決定是否冪等重試 | 鎖只代表當前 session／transaction；釋放後晚到 worker 以新 transaction 回來時不會自動被辨識，需另加 business version／fence | 熱點排隊與串行、lock timeout、deadlock；鎖面或持鎖時間放大阻塞 | 查 transaction outcome、durable business state 與 lock-wait evidence；deadlock 後整個 transaction 有限重試，不能只補跑後半段 |
| **固定順序短事務** | 同一資料庫內跨多行／多表的完整 invariant | 依固定全序取得必要鎖並一次 commit／rollback 的本地 transaction | 保證本地變更 all-or-nothing，且所有路徑遵守全序時避免反向取鎖造成的循環等待；不保證無一般鎖等待、跨資料庫或外部結果 | session 失效後未提交 transaction 回滾且不能接管；新 session 重讀全部 durable business state 後重判。commit outcome unknown 時先查完整業務結果，再決定是否冪等重試 | transaction 結束後沒有 owner 身分延續；要拒絕晚到命令，需在狀態遷移中加入 business version／fence | 鎖面擴大、熱點串行與等待鏈；其他路徑或範圍鎖仍可能造成 deadlock | 以 constraints、跨行狀態與 audit facts 驗證整體提交；失敗時重跑整個 transaction，邊界外偏差交給 reconciliation |

### 1. 唯一約束／原子條件更新

如果 invariant 可以寫成資料庫直接拒絕的條件，先讓儲存引擎在提交點判斷。例如，唯一約束保護「同一業務識別只能建立一次」；原子條件更新則把前置條件與狀態變更合成一次不可分割的操作，並以是否實際更新作為競爭結果。

這種設計縮短 read-modify-write window（先讀、在應用判斷、再寫之間的競爭窗口）。若先讀剩餘量，再在應用中判斷，另一個 transaction 可以在兩步之間修改它；把「剩餘量足夠才扣減」放進同一原子條件更新，失敗者會在提交邊界得到明確的未更新結果。

它只保證條件能完整落在同一原子操作內的 invariant。若判斷依賴多行、多表或外部狀態，就不能把一次更新成功誤稱為端到端完成。

### 2. Optimistic CAS

Optimistic CAS（optimistic compare-and-set，樂觀比較後設定）讀取值與版本，寫入時要求版本仍等於預期值；只有一個 contender 能推進版本，其他 contender 得到可辨識的 conflict。它適合衝突低、重新讀取與重算成本可接受的場景，因為無衝突路徑不必先長時間等待鎖。

CAS 的 conflict 是控制流程的一部分，不是可以無限立即重試的例外。當大量請求集中在同一熱點，成功者每次推進版本都會讓其他請求失敗；無界重試會放大資料庫負載、延遲與排隊，形成 retry storm。高衝突時應限制重試、加入退避，並重新評估是否改用等待式串行、按 key 分區或資源拆分，而不是只增加 worker。

CAS 保護的是「從預期版本到下一版本」這一次本地遷移；它不保證讀取之後發生的外部副作用，也不會自行恢復 caller 在成功提交後遺失回應的 unknown outcome。

### 3. Pessimistic Lock

Pessimistic Lock（悲觀鎖）先取得資料庫鎖，再在鎖保護下完成必要的讀取、判斷與寫入。它適合重算不可接受、競爭者等待比反覆衝突更便宜，而且臨界區延遲有界且短的情況。

DB 鎖是 OLTP 正確性的基礎，不是「大型系統不用鎖」。InnoDB 的 locking read 可以讀取最新可用資料並鎖住讀到的記錄與相關索引項；鎖會在 transaction commit 或 rollback 時釋放。這個保證精確地止於該本地 transaction，詳見 [MySQL 8.4 Locking Reads](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)。

因此，Pessimistic Lock 要同時滿足三個條件：鎖定條件能走合適索引、鎖面只覆蓋 invariant 必需的資料、transaction 內只保留有界的本地工作。鎖範圍過大會降低無關請求的並發，持鎖時間過長會把等待、deadlock 與連線占用推向整個系統。

### 4. 固定順序的短事務

當 invariant 橫跨多行或多表，單條更新與單一 row lock 無法完整表達時，把必要變更放進同一本地短事務，所有程式路徑都依固定順序取得鎖。例如，跨多個 aggregate key 時採用一致的全序，而不是讓不同請求依輸入順序任意加鎖。

固定全序避免由取鎖順序相反造成的循環等待，小鎖面則減少競爭者被牽連的範圍；兩者必須一起使用。固定全序不消除一般鎖等待，資料庫也仍可能因其他路徑、範圍鎖或引擎選擇而中止 transaction，所以 caller 必須把 deadlock/serialization failure 視為整個 transaction 失敗，只做有界且安全的重試，不能只補跑後半段。

### 離開 DB transaction 的明確界線

外部 I/O、人工等待、不可預測計算或 crash 接管一旦出現，就離開 DB transaction。先用短事務提交可恢復狀態，再由邊界外的協調機制推進；不能在持有 row/index lock 與 DB connection 時等待遠端世界。

原因不是「transaction 超過幾秒」這個數字本身，而是本地資料庫無法原子控制外部結果，進程 crash 後原 transaction 也不能交給新 worker 繼續。延長 lock timeout 只延長資源占用，不會增加跨系統原子性或接管能力。

## Part D · 單服務長任務方案

長任務不是把 Part C 的 transaction 拉長，而是把生命週期拆成多個可提交、可辨識、可重試的短邊界。每一步只原子保存一個狀態遷移或資源決定；步驟之間的等待、計算與外部 I/O 都在 transaction 之外。

以下六類方案不是互斥選項。一個批次任務可以同時使用 Durable State Machine 保存進度、Immutable Batch 固定輸入、Lease/Fencing 管理 owner，最後以 Shadow Build 發布結果。無論如何組合，每個方案都必須回答同一份 binding contract：

1. **Invariant**：哪個非法結果絕不能出現？
2. **保護對象**：真正被保護的是任務狀態、輸入版本、可消耗能力、resource key，還是發布指標？
3. **原子邊界**：哪一次本地操作能共同提交或拒絕？
4. **保證**：該邊界能證明什麼？
5. **不保證**：哪些步驟、資料或外部副作用仍在邊界外？
6. **Crash／接管**：原 worker 消失後，新 owner 從哪個 durable fact 繼續？
7. **Stale owner**：舊 owner 晚到時，哪個寫入邊界會拒絕它？
8. **高併發退化**：競爭集中時，會變成衝突、排隊、backlog、掃描壓力，還是 hot partition？
9. **驗證與修復**：以哪些不可變事實證明結果；偏差如何重試、重建、補償或人工處理？

只寫「用了 queue／lock／workflow」仍未完成設計；若上述任一題沒有 owner 與 durable data，crash 後就只能靠猜測恢復。

### 1. Durable State Machine

Durable State Machine 把任務生命週期保存成 durable state，而不是只存在 worker 記憶體。典型狀態會表達待處理、執行中、等待外部結果、完成、失敗或需要人工處理；具體名稱不重要，重要的是每個 transition 都有合法前置狀態、穩定 task id 與可審計結果。

| Binding contract | 回答 |
|---|---|
| **Invariant** | 任務只能沿合法 transition 前進；crash 後不得把「沒有證據」當成完成，也不得遺失已提交進度。 |
| **保護對象** | task 的生命週期、目前 step、輸入／結果引用、重試與人工處理狀態；不是某個 worker process。 |
| **原子邊界** | 以 expected state／version 為前置條件，在一次本地短事務內提交單一步驟結果、下一狀態與必要 audit fact。完整任務不是一個 transaction。 |
| **保證** | 已提交 checkpoint 可跨 process restart 保存；新 worker 能由 durable state 判斷已完成與待執行步驟。 |
| **不保證** | 不保證每個 step 只執行一次，也不會把本地狀態遷移與外部副作用變成同一原子提交；外部 timeout 仍可能是 unknown outcome。 |
| **Crash／接管** | 以 state、version、最近 checkpoint 與穩定 task id 重建上下文；新 owner 先原子 claim，再重做可冪等步驟或查詢不確定的外部結果。不能從舊 worker 的 stack 接續。 |
| **Stale owner** | transition 必須同時檢查 expected state／version 與 owner token；舊 owner 即使醒來，也不能覆蓋已由新 owner 推進的 task state。外部資源另需 idempotency 或 fence。 |
| **高併發退化** | 熱門 task 反覆 CAS conflict；大量到期任務造成 claim 掃描、retry 與 recovery storm；下游變慢時 durable backlog 持續增加。 |
| **驗證與修復** | 檢查 transition history、狀態停留時間、重試次數與 unknown outcome；卡住任務依 checkpoint 重領，外部結果先查詢再重試，無法自動判定者進 manual review。 |

Durable State Machine 的價值是保存「現在知道什麼、下一步允許做什麼」，不是保證邊界外的世界已依照流程狀態完成。若狀態寫成 `SUCCEEDED`，卻沒有可指向業務結果的 evidence，這個狀態本身不能證明 invariant。

### 2. Lease、Heartbeat 與 Fencing

`owner token` 是一次持有關係的唯一身分；lease 給這個 owner 一段有界的所有權判斷；heartbeat 在任務仍有進展時更新 lease 活性；fencing token 則提供可比較且單調前進的 owner generation。Kubernetes 公開的 [Lease](https://kubernetes.io/docs/concepts/architecture/leases/) 物件就被用於 node heartbeat 與 leader election，node heartbeat 會更新 `renewTime`。這說明 Lease 是協調與活性訊號，不等於被保護資源已接受某個業務寫入。

Fence 必須分成三個可觀察階段：**issued** 是 owner registry 在 claim／reclaim 時原子發出 generation `N`，只授予 contender 嘗試接管的資格，完全不改變業務資源；**activated** 是該資源以自己的原子操作把本地 `fence_floor` 推進到至少 `N`，從此拒絕 `< N`；**accepted** 是資源收到帶 `N` 的業務寫入，在同一原子邊界確認 `N >= fence_floor`、提交寫入並把 floor 推進到至少 `N`。第一次 accepted write 可以同時完成 activation；若 invariant 要求新 owner 開始工作前舊 owner 就再也不能提交，必須先做獨立 resource-side activation。registry 單純 issued `N` 絕不等於資源已 activated `N`。

SQS 的 [visibility timeout](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html) 提供相似的有界處理權：消息在期限內對其他 consumer 暫時不可見，處理者可延長期限；未刪除且期限到期後，消息會重新可見。官方也明確說明 at-least-once 模型下，即使期限尚未到，也不能絕對保證沒有重複投遞。因此，visibility timeout 可以幫助避免同時重工，不能代替 handler idempotency 或 resource-side validation。

| Binding contract | 回答 |
|---|---|
| **Invariant** | 被保護資源一旦 activated generation `N`，或 accepted 一筆帶 `N` 的寫入，之後所有 `< N` 的寫入都必須被拒絕；最新 issued generation 尚未在資源端 activated／accepted 前，不宣稱舊 generation 已失去提交資格。 |
| **保護對象** | lease 保護的是有界執行權；fencing 保護的是資源寫入順序。任務鎖 key 本身不是錢、庫存或帳本。 |
| **原子邊界** | claim／renew／expire 與 generation issuance 是 owner registry 的短原子更新；資源端另以短原子 activation 推高 `fence_floor`，或在 accepted write 中比較 token、提交業務變更並推高 floor。registry issuance 與 resource-side floor 是兩個邊界，不能互相冒充。 |
| **保證** | registry issued 新 generation 只證明 contender 取得**嘗試接管**資格；資源 activated `N` 後會拒絕 `< N`，而 accepted write 會以同一原子提交至少啟用自己的 `N`。若先 activation 再執行受保護工作，可證明 activation 之後舊 generation 無法在該資源提交。 |
| **不保證** | lease expiry 或 issued 新 generation 都不是進度、接管完成或 resource-side activation 保證，也不會讓舊 worker 自動停止；在資源 activated／accepted `N` 前，舊 generation 仍可能提交。registry／quorum 不可用時不能安全發出新 generation，資源不可用時也不能假裝完成 activation。若資源不保存並檢查 floor，lock／lease 單獨不能保證資金、庫存或外部副作用正確。 |
| **Crash／接管** | 期限到且 durable state 仍未完成，只代表 contender 可以向可用 registry 競爭；取得 issued generation `N` 後，新 owner 必須先在每個受保護資源 activated `N`，或讓第一次 accepted write 原子完成 activation，才能依該資源的 fence 保證繼續。舊嘗試的 unknown outcome 先查詢，不直接重做不可冪等副作用。 |
| **Stale owner** | registry 只會讓舊 token 失去續租資格；資源依自己的 `fence_floor` 拒絕更小 token。若採 first-write activation，在新 generation 首次 accepted 前舊 token 仍可能被接受；不能容許這個窗口時必須先獨立 activation。無法加 fence 的外部系統改用穩定 idempotency key、結果查詢與 reconciliation。 |
| **高併發退化** | 熱門 lease 形成 renew／claim 寫入熱點；同時到期會引發 thundering herd，過密 heartbeat 也會消耗協調儲存。採用有界退避、jitter、分片掃描與合理租期，但不能藉此省略 fence。 |
| **驗證與修復** | 分別審計 issued generation、每個資源的 activated floor，以及 accepted／rejected write；監控 activation failure、stale-fence reject、雙 owner 痕跡與 lease churn。無 fence 資源以業務帳、外部查詢和對帳辨認重複副作用。 |

所以，owner token、lease、heartbeat、fencing 是四個不同責任：身分、期限、活性更新與資源端拒絕；fencing 內部還要分清 registry issued 與 resource-side activated／accepted。Redis 鎖的過期、續期、failover 與 fencing 失敗窗口可繼續閱讀 [分布式鎖](../redis-handson/07-distributed-locks/README.md)。

### 3. Immutable Batch

穩定批次要分別固定 **membership** 與 **value**。membership manifest 保存哪些資料屬於批次；value snapshot 保存完整輸入，或保存能永久解析到同一內容的 immutable version。只保存一串 mutable row ID，只能重建成員名稱，不能保證接管重算時仍讀到相同值。

`cutoff`／source version 是捕獲邊界：它定義「這個批次看見哪個時間或版本以前的事實」，不代表來源資料從此停止演進。來源可以繼續接受新寫入；舊批次仍靠 sealed manifest 與 immutable value reference 重現同一輸入。

| Binding contract | 回答 |
|---|---|
| **Invariant** | 同一 batch 的所有輸出必須由同一份 membership 與同一組 value／version 推導，不得混入捕獲邊界兩側的資料。 |
| **保護對象** | batch 的 DRAFT／SEALED 狀態、sealed manifest、每個 item 的不可變輸入或 immutable version、cutoff 與輸出所屬 batch id。 |
| **原子邊界** | 在固定 source snapshot／version 下，以多個短事務把 manifest 分段、冪等寫成 DRAFT；最後一個短事務驗證 expected count、整體 hash 與 source version，並原子完成 `DRAFT → SEALED`。worker 只消費 SEALED manifest；每個 item 再以 `(batch_id, item_id)` 短事務記錄結果，完成驗證後以短邊界發布。大型 manifest 不要求單一 transaction。 |
| **保證** | 保存 membership 能固定成員；保存完整值或不可變版本才能讓 retry／接管重算同一輸入；SEALED gate 防止 worker 消費尚未完整驗證的 DRAFT。 |
| **不保證** | 只存 ID 不會固定 value；cutoff 不會凍結來源；manifest 正確也不保證計算程式、外部依賴或輸出一定正確。 |
| **Crash／接管** | manifest 建立者 crash 時，新 worker 只能在原 source snapshot／version 下依分段 checkpoint 續寫 DRAFT，或丟棄後重建；不能消費未 SEALED 的內容。SEALED 後再找出缺少或 outcome unknown 的 item，以同一 batch id 與輸入版本冪等重算；不重新查詢「目前符合條件的資料」來替換 membership。 |
| **Stale owner** | 每個結果必須綁定 batch id、item id 與 input version；發布時檢查 expected active version／generation，拒絕舊 batch 晚到覆蓋新發布結果。 |
| **高併發退化** | 大 manifest 造成建立、儲存與掃描壓力；單一 batch 的完成計數成為熱點；大量 item fan-out 可能壓垮下游。以 immutable partition、分段進度與有界 admission 控制。 |
| **驗證與修復** | 比對 manifest count、input hash／version、item 完成集合與輸出 checksum；缺項只補算同一版本，混合版本則隔離整批、重建並重新發布，不能局部宣告成功。 |

### 4. Reservation

Reservation 保護的是可消耗能力，不是凍結整個業務物件。庫存、資金或座位在 Hold／Try 時被暫時占用，成功流程再 Confirm，放棄或逾期則 Release／Cancel。Stripe 公開的 [authorization 與 capture](https://docs.stripe.com/payments/place-a-hold-on-a-payment-method) 就呈現這種資源語義：先保留可之後 capture 的資金，必須在 authorization 到期前 capture，否則資金會釋放且付款狀態轉為 canceled。

| Binding contract | 回答 |
|---|---|
| **Invariant** | 在納入供給與調額後的每個有效版本，reservation 與 confirmed flow 不得消耗超過當時可用的能力；同一 reservation 不能同時成為已確認與已釋放。 |
| **保護對象** | 可消耗額度與具穩定 reservation id 的 Hold／Confirm／Release 生命週期；不是商品、帳戶或座位物件的全部欄位。 |
| **原子邊界** | Hold 以條件式更新同時扣除可用能力並建立 reservation；Confirm／Release 分別以 reservation state 為 predicate 做冪等短 transition。等待客戶或遠端結果期間不持有 DB lock。 |
| **保證** | 成功 Hold 在有效期內保留指定能力；idempotent Confirm／Release 讓重複命令收斂到同一 terminal result；expiry 提供遺棄預留的恢復入口。 |
| **不保證** | 不凍結整個物件，不等於 DB 長鎖，也不保證跨服務流程一定完成。expiry 只是可回收條件；若沒有執行 reclaim／reconciliation，能力仍可能長期占用。 |
| **Crash／接管** | 新 worker 以 reservation id 查詢 durable state；active 且流程仍有效時續辦，已 confirmed／released 時回傳原結果，逾期或 unknown 時依業務事實執行 release、結果查詢或人工處理。 |
| **Stale owner** | Confirm／Release 必須檢查 reservation state、expiry 與 version；舊 owner 對已釋放或已確認 reservation 的相反動作被拒絕。若外部 provider 已受理，另以 provider request id 查詢。 |
| **高併發退化** | 熱門 SKU／帳戶／場次形成條件更新熱點；短 expiry 帶來重試與回收 churn，長 expiry 降低可用能力；大量逾期掃描會集中負載。可按資源 key 分區並限制排隊。 |
| **驗證與修復** | 依資源專屬守恆式重放權威 facts，納入期初、供給／補貨／入帳／調額等 adjustment facts，以及 Hold／Confirm／Release／expiry；不同資源不能套用跨資源固定公式。另掃描逾期與不合法 terminal 組合；漏釋放要 reclaim，外部結果不一致則 reconciliation 或 manual review。 |

Reservation 只有在資源真的具備 Try／Hold、Confirm、Cancel／Release 語義時才成立；若 Hold 沒有實際減少可用能力，它只是流程標記，不能防止超賣或超額使用。

### 5. Per-Key Serialization

Per-Key Serialization 只讓同一 `resource key` 的命令局部串行，其他 key 仍可平行。例如，同一 account／order／aggregate 的 transition 依 durable sequence 處理，不相關 key 可由其他 partition 或 worker 同時推進。等待中的命令保存在 durable queue，不占用 DB connection，也不長時間持有 row lock。執行期串行必須靠「每個 key 同時只准一個 active command」的 admission／claim，或帶穩定 ownership epoch 的 partition owner；expected sequence／version 只能拒絕衝突提交，單獨不足以阻止兩個 worker 同時執行或呼叫外部系統。

| Binding contract | 回答 |
|---|---|
| **Invariant** | 同一 resource key 的命令必須依已定義順序套用合法 transition，舊 sequence 不得覆蓋新狀態。 |
| **保護對象** | 每個 key 的 durable command order、唯一 active claim／partition ownership epoch、目前 aggregate version 與處理結果；不是全系統的總順序。 |
| **原子邊界** | durable enqueue 保存命令；執行前以 admission 原子確認該 key 沒有其他 active command 並 claim queue head，或由唯一 partition owner 依 ownership epoch admission。完成時在同一本地短事務提交 command result、aggregate transition、sequence advance 與 active claim terminal／release（若使用 claim）；排隊與執行時間不在 DB transaction。 |
| **保證** | active claim／partition ownership 有效，且 aggregate 的 accepted write 在同一原子邊界比較 fence／epoch、提交 transition 並推高自己的 floor 時，同一 key 只 admission 一個 active command，其他 key 保有並行；durable queue 讓 worker crash 時等待命令仍可重新交付。 |
| **不保證** | expected sequence／version 單獨不保證執行期串行，也不保證跨 key 順序、單次投遞或外部副作用 exactly-once；queue admission 仍不能代替 aggregate 自身的合法 transition。 |
| **Crash／接管** | 未確認命令留在或回到 durable queue；active claim expiry 後，新 consumer 必須取得更高 claim fence／partition epoch，先按 command id 與 aggregate state 查 durable result，外部 effect 再以穩定 idempotency key 查詢結果，才能判定續做或回傳既有結果。 |
| **Stale owner** | 每次 aggregate 寫入都帶 claim fence／partition epoch，資源依本地 floor 接受並原子推高 generation，讓較低 token 的過期 consumer 即使 expected sequence 尚未推進也會被拒絕；claim issuance 本身不會推高 aggregate floor。外部 effect 無法驗 fence 時，必須使用 idempotency key 與結果查詢。 |
| **高併發退化** | hot key 形成不可水平拆散的 backlog、tail latency 與 hot partition；長命令造成 head-of-line blocking，partition 間也可能不公平。需 backpressure、配額、公平排程與隔離慢命令。 |
| **驗證與修復** | 監控 per-key active count、claim fence／partition epoch、lag、sequence gap／duplicate、最老消息年齡與 poison command。sequence gap 或 poison command 必須阻塞該 key；恢復時補回缺少命令、把失敗命令轉成明確 terminal result，或進 manual review，不能跳過後假裝順序完整。 |

Per-Key Serialization 是把競爭成本從 CAS retry 移成可觀測 backlog。它適合高衝突且順序本身有業務意義的 aggregate；若所有請求共用一個過粗 key，結果只是把服務退化成單線程。

### 6. Shadow Build

Shadow Build 讓在線舊版本持續服務，在背景以獨立版本建立新索引、配置、讀模型或大型轉換結果。新版本完成一致性驗證後，再以很短的原子邊界切換 active pointer；不在原資料上逐段覆寫，也不要求讀者在半成品上工作。

Elasticsearch 官方的 [alias API](https://www.elastic.co/guide/en/elasticsearch/reference/current/aliases.html) 公開支持在單一原子操作執行多個 alias actions，並以 alias 切換實現 reindex without downtime。這是「背景建新版本，最後切換名稱」的具體公開行為；它不代表任意外部系統或任意多資源切換都自動具有相同原子性。

| Binding contract | 回答 |
|---|---|
| **Invariant** | 線上讀者只能看到已完整驗證的舊版本或新版本，不得把兩個版本的部分內容混成 active result。 |
| **保護對象** | immutable build version、驗證證據與 active pointer／alias；舊版本在切換與觀察期內仍可服務或回退。 |
| **原子邊界** | 背景 build 與驗證各自跨多個短提交；只有最後 pointer／alias swap 是單一短原子操作。若有多個無法共同切換的 consumer，就沒有隱含的全域原子發布。 |
| **保證** | 在 pointer 邊界內，讀者不會看見已發布版本的半成品；舊版本可在新 build 期間持續服務，驗證失敗可以不發布。 |
| **不保證** | 不保證 build 計算正確、增量追趕沒有漏資料，也不適合必須原地產生不可逆副作用的流程；alias 原子性不會涵蓋 alias 之外的 cache 或外部系統。 |
| **Crash／接管** | 新 worker 以 build id、source cutoff／version 與 checkpoint 續建或重建；未通過完整驗證的 build 永不成為 active，孤兒版本可延後清理。 |
| **Stale owner** | 發布必須檢查 expected active version 與 build generation；舊 build 晚到只能被拒絕或保留為非 active，不能把較新的 active pointer 換回去。 |
| **高併發退化** | 同時維持新舊版本增加儲存與背景寫入；高變更率使 catch-up lag 無法收斂；多個 build 競爭發布，切換後 cache warm-up 可能造成尖峰。需限制 concurrent build 與 admission。 |
| **驗證與修復** | 切換前比較 count、checksum、抽樣查詢、source version 與 catch-up lag；切換後監控錯誤與語義差異。異常時原子切回已知良好版本，修正後重建，不在 active 半成品上補丁。 |

Shadow Build 適合能建立成獨立版本、讀者能經由 indirection 取得 active version 的結果。若流程的核心是「寄出通知、扣除外部款項」等原地副作用，就應保存 durable workflow state、使用 idempotency／reservation 並對帳，而不是把它包裝成 shadow copy。

## Part E · 跨服務長流程

跨服務流程沒有一個本地 transaction 能同時控制所有參與者。生產設計要按實際故障模型條件式疊加責任，而不是在 Outbox、Saga、TCC、workflow framework 之間選一個名字，也不是每條流程都部署全套：

```text
本地事務
+ Outbox 解決 dual write
+ Idempotency 吸收重複
+ Saga/TCC 協調業務結果
+ Durable Workflow 保存控制狀態
+ Reconciliation 收口
```

這張圖是可組合的責任關係，不是成熟度排行榜或必裝清單。所有流程的基線是先以本地事務守住服務內 invariant；只有需要可靠傳播已提交事實時才加 Outbox；caller、transport 或 handler 可能 retry 時才建立 Idempotency contract；存在多步 forward／compensation 時才使用 Saga；資源具有真實 Try／Confirm／Cancel reservation 時才使用 TCC；流程跨長等待、timer 或 signal 時才引入 Durable Workflow；高價值結果或存在 unknown outcome 時，才按風險配置相應 Reconciliation 與 manual handling。下層沒有守住 invariant，上層重試得越可靠，只會越可靠地重複錯誤。

### 組合邊界與責任

| 組件 | 保護對象與原子邊界 | 保證 | 不保證與恢復責任 |
|---|---|---|---|
| **本地事務** | 單一服務擁有的業務狀態、帳本、reservation 與同庫 audit／outbox fact | 在自己的 data store 內共同 commit／rollback，直接拒絕違反 service invariant 的寫入 | 不涵蓋 broker、其他服務與外部 provider；commit outcome unknown 時按業務鍵查詢，不盲目重做 |
| **Outbox** | 已提交業務事實與待傳播 event，在同一本地 transaction 寫入 | 消除「業務資料已提交、事件卻沒有留下 durable fact」的 dual write 窗口 | relay 仍可能重送，consumer 仍需 idempotency；Outbox 不保存完整流程進度、timer、compensation，所以不是 workflow engine |
| **Idempotency** | 穩定 request／command id 對應的業務意圖與已提交結果；handler 在本地把 dedupe record 與 effect 一起提交 | 相同 key、相同意圖的 retry 回到同一語義結果，吸收 transport／caller duplicate | 不修復錯誤 key、不同意圖共用 key、跨服務 partial success 或不可查詢的外部結果；需保存足夠久並處理 late request |
| **Saga** | 一個 workflow 的本地 transaction 序列，以及每一步 forward／compensation outcome | 保存每一步 outcome，提供可從 durable state 恢復、通往 `FORWARD_COMPLETED`、`COMPENSATED` 或 `MANUAL` terminal state 的路徑 | 不保證自動收斂，也不是 ACID rollback；補償可能失敗、與其他合法交易交錯，最終收斂依賴有界 retry、reconciliation 與 manual handling |
| **TCC** | 具有真實資源語義的 Try／Confirm／Cancel reservation | Try 先實際預留資源，Confirm 消耗，Cancel 釋放；每個參與者在自己的本地邊界保護能力 | 不適合沒有可預留資源或無可逆 Cancel 語義的副作用；expiry、idempotency、空回滾／晚到命令與 reconciliation 仍要設計 |
| **Durable Workflow** | workflow instance 的控制進度、timer、retry policy、signal 與 activity outcome | orchestrator crash／restart 後仍能由 durable history 恢復控制流程，安排等待與重試 | 不替代服務內 invariant、帳本、Outbox、handler idempotency 或資源端 fence；workflow state 不是外部業務結果的唯一證據 |
| **Reconciliation** | 各服務 durable fact、帳本、provider result 與 workflow 預期結果之間的差異 | 找出在線協議未能判定或修復的漏單、重複、永久 partial success，並建立可審計修復案件 | 不是只發 alert；若沒有權威來源、修復動作與人工責任人，就不能宣稱流程已收口 |

### 跨服務 binding-contract crosswalk

上一表界定 invariant、保護對象、原子邊界與保證；下表只補齊其餘 binding contract，不重複 Part F–H。`N/A` 表示該組件本身沒有這項語義，不表示整條流程可以省略責任。

| 組件 | Contention／recompute | Crash takeover | Stale owner | Capacity degradation | Proof／repair |
|---|---|---|---|---|---|
| **Outbox** | aggregate 競爭由同一 local transaction／version 仲裁；relay 不重算業務決定（N/A），只重送同一 immutable event。 | relay crash 後，另一 relay 由 durable unpublished record 重送；見 Part F「本地提交成功但通知未發」。 | resource owner 語義 N/A；stale relay 最多重送既有 event，consumer 仍以 idempotency／expected version 拒絕重複或晚到 transition。 | 熱門 aggregate、outbox 掃描、broker 與 consumer 形成 backlog；依 Part G「Queue」與「恢復流量」做 batch、backpressure、quota。 | 對照 business commit、outbox event 與 consumer durable fact；漏發重送、差異交 Part H Reconciliation。 |
| **Idempotency** | 同 key／同意圖必須在權威 effect 邊界原子競爭為一個 durable result；任意重算 N/A，不同意圖共用 key 必須 conflict。 | idempotency record 本身不指派新 owner（N/A）；接管要靠 durable state，外部 outcome 未知時遵守 Part F「外部操作成功但回應丟失」。 | owner 語義 N/A；late duplicate 只有抵達權威去重邊界後才被吸收，不能撤銷尚未抵達該邊界的 stale sender。 | hot key、dedupe row 與 retention 壓力會放大 retry；依 Part G 的 bounded retry、jitter、admission control。 | 保存 key、intent digest、attempt 與 durable result；`UNKNOWN` 不偽裝成失敗，依 Part H 查詢、對帳或人工收口。 |
| **Saga** | 同 aggregate 的 forward／compensation 用 expected version 與 idempotency 仲裁；compensation 是新命令，不是任意重算舊世界。 | 新 coordinator 由 durable Saga history 接續 unresolved step；外部 `UNKNOWN` 不得無執行邊界就 retry，見 Part F「補償失敗或結果未知」。 | Saga generation 不會自動 fence participant 或 provider；各服務檢查 version／key，對外 stale sender 仍受 Part F 的 provider／single-egress contract 約束。 | step fan-out、retry 與 compensation storm 造成 queue／下游壓力；依 Part G per-key admission 與 Backpressure。 | 對照 forward／compensation history、participant fact、帳本與 provider result；偏差交 Part H case／repair／manual review。 |
| **TCC** | Try 在資源端以條件更新競爭真實 capacity；Confirm／Cancel 依 reservation state／version 仲裁，任意重算 N/A。 | 新 owner 以 reservation id 查 durable state／expiry，再決定 Confirm、Cancel 或查詢；不從舊 process stack 接續。 | 舊 Confirm／Cancel 由 reservation terminal state／version 拒絕；若跨外部 provider，另套用 Part F 的 idempotency／stale-sender 邊界。 | hot SKU／account 與 expiry reclaim 形成提交、掃描熱點；依 Part G 分區，只有守恆可證時才用 Escrow。 | 重放 capacity adjustment、Try／Confirm／Cancel／expiry facts 驗證守恆；孤兒 reservation 由 Part H reclaim／reconciliation 修復。 |
| **Durable Workflow** | durable history 仲裁 workflow command／event；replay 只重建 deterministic control state，不重算外部 effect。 | orchestrator 由 history 恢復 timer、signal 與未決 activity；activity retry 仍須 idempotency 與 Part F 的 `UNKNOWN` 邊界。 | workflow 可拒絕 late completion，但不能撤銷已 timeout 的 activity sender 或外部 effect；resource fence／provider contract 仍不可省。 | hot workflow history、task queue、timer 與 retry storm 造成 backlog；依 Part G 隔離 worker、限流並保留下游 backpressure。 | history 只證明控制決定；business proof 仍比對服務／provider facts，偏差交 Part H Reconciliation。 |
| **Reconciliation** | difference 計算基於固定 cutoff／rule version；repair 以 expected version／idempotency 競爭，避免自動與人工重複修復。 | durable case／checkpoint 讓新 worker 接續；不能解析的外部 outcome 保持 `UNKNOWN`。 | scanner owner 語義 N/A；repairer 必須使用 repair fence，共享 business-effect identity，並遵守 Part F「人工修復與自動恢復競爭」的 drain／stale-sender 門檻。 | 大範圍掃描、case backlog 與 repair throughput 會反壓權威 store；依 Part G 分片、quota、隔離與有界重試。 | 保存 difference、case、repair command、approval 與 terminal reason；重跑 invariant checker 後才依 Part H 關案。 |

AWS 的 [Transactional Outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html) 公開說明此模式解決 DB write 與 event notification 的 dual write，並提醒 event processing 可能產生 duplicate，consumer 應追蹤已處理消息以保持 idempotent。這正是 Outbox 與 Idempotency 必須同時存在、但責任不同的原因。

AWS Builders' Library 的 [idempotent API](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/) 以唯一 client request identifier 表達同一意圖，使 retry 能得到語義等價結果。idempotency key 因而是業務協議：服務要綁定請求意圖、保存結果並拒絕同 key 的不同意圖；它不是把兩次碰巧相同的 payload 猜成同一請求。

### Saga、TCC 與補償

Saga 把跨服務流程拆成一串本地 transaction，依每一步 outcome 決定下一個 forward action 或 compensating action。AWS 的 [Saga pattern](https://docs.aws.amazon.com/prescriptive-guidance/latest/modernization-data-persistence/saga-pattern.html) 將它描述為協調多個 microservice transaction 的 failure-management pattern，也明確指出參與者增加會提高除錯與補償設計複雜度。

**補償是新的業務動作，不是時間倒流。** 已完成的扣款可能要以退款收斂、已發出的通知可能只能追加更正、已被第三方看見的事實不能從歷史刪除。每個補償都需要自己的 idempotency key、合法前置狀態、重試與審計；若後續合法交易已改變資源，補償還必須重新判斷，不得假設世界停在原步驟之後。

Saga 的 durable state 必須保存每個 forward 與 compensation outcome，讓接管者知道下一個安全動作，並明確提供 `FORWARD_COMPLETED`、`COMPENSATED` 或 `MANUAL` terminal path。這是可恢復路徑，不是自動收斂保證；永久錯誤、補償失敗或語義衝突仍要由有界 retry、reconciliation 與 manual handling 收口。

TCC 是 reservation 語義更強的協調方式：Try 必須真的把庫存、資金或席位從可用能力中保留；Confirm 與 Cancel 只能對同一 reservation 做冪等 terminal transition。若所謂 Try 只寫一筆「準備中」流程紀錄，卻沒有保護資源，它不能提供 TCC 的核心 invariant。Saga 可以協調一般可補償業務動作；TCC 只適合參與者能提供真實 Try／Confirm／Cancel 資源協議的場景。

Saga 與 Event Sourcing 的概念邊界、協作式／編排式取捨可繼續閱讀 [Event Sourcing、領域事件與 Saga](../software-architecture/07-EventSourcing-領域事件-Saga.md)；Outbox、TCC、Temporal 與組合驗證則見 [一致性模式與框架選型](../financial-consistency/05-patterns/README.md)。

### Durable Workflow 不是業務真相替代品

Temporal 的公開首頁把 [Durable Execution](https://temporal.io/) 描述為持久保存 workflow running state，並提供 retry、task queue、signal 與 timer，使流程能在故障後恢復。這些是控制平面的 durable capability：保存走到哪一步、何時重試、正在等哪個 signal，以及 activity 回報什麼結果。

它不會自動讓 activity 的外部副作用 exactly-once，也不能替代服務內 constraint、ledger、reservation 與 reconciliation。activity timeout 後，workflow 仍可能只知道「沒有收到成功回應」，不知道 provider 是否已完成；正確恢復仍要使用穩定 request id、查詢外部結果、把本地 effect 設計成 idempotent，並以帳本或對帳證明最終業務結果。

### 三層交付語義：不要直接宣稱端到端 exactly-once

「消息只送一次」「handler 只跑一次」與「業務副作用只成立一次」是三個不同命題：

| 層次 | 能觀察的事實 | 必要機制 | 不能直接推出的結論 |
|---|---|---|---|
| **Transport delivery** | broker 是否投遞、重投、排序與收到 ack | durable message、ack／visibility、retry、DLQ | delivery ack 不代表 handler transaction 已提交，更不代表跨服務流程完成 |
| **Handler processing** | 某個 message／command id 是否已處理，以及本地 transaction 結果 | inbox／dedupe、idempotency key、expected state／version、本地 audit | handler 只提交一次不代表外部 provider 只產生一次 effect，也不代表其他服務都成功 |
| **Business effect** | 帳本、庫存、reservation、provider record 與 workflow outcome 是否符合 invariant | service constraint、ledger、resource-side validation、結果查詢、Saga/TCC 與 reconciliation | 任一 framework 的「exactly-once」名稱都不能自動擴張成所有控制域的端到端保證 |

因此，文件與監控應分別描述 delivery count、handler attempt／commit result 與 business effect。只有最後一層能回答「錢是否只扣一次、庫存是否超賣、流程是否已收斂」；它需要業務鍵與權威事實證明，不能由 broker 指標代答。

### XA／2PC 的位置

XA／2PC 以同步協調參與者換取一個分散式原子提交決定；代價是參與者在協議期間必須耦合於共同 transaction outcome，失敗時可能阻塞並降低可用性。這種 trade-off 可能適合範圍封閉、參與者都支援協議且延遲有界的同步資料操作，但不作跨人工等待、長時間 timer、不可控外部 API 或可持續數小時／數日業務流程的預設。

不用 XA／2PC 並不表示接受無法解釋的 partial success。條件式組合仍從各服務的本地 invariant 開始：需要傳播才加 Outbox，存在 retry 才建立 Idempotency contract，多步補償才加 Saga，真實 reservation 才用 TCC，長等待／timer／signal 才用 Durable Workflow，高價值或 unknown outcome 才配置相應 Reconciliation。同步原子性縮小之後，所選機制的恢復協議與證據必須更明確，而不是把未出現的故障模型也包進固定全套。

## Part F · 完整故障矩陣

正常路徑只能證明系統在沒有中斷時能走完；故障矩陣要證明每個中斷點都留下足夠的 durable state，讓下一個執行者能辨認「尚未開始、已完成、可以安全重試，還是結果未知」。以下每一列都同時寫出非法結果、在線控制與離線收口，不能用單一 `retry` 或「交給人工」掩蓋 unknown outcome。

| 失敗時點 | 可能出現的錯誤結果 | 必要控制 | 恢復與驗證 |
|---|---|---|---|
| **認領前 crash** | 任務一直停在待處理，或 queue 重新投遞後多個 worker 都把自己當 owner；若任務只存在原 process 記憶體，則直接遺失。 | task durable state 是待處理工作的權威來源，建立 task 與 `PENDING` transition 在本地一次提交；若另需 queue 通知，則同 transaction 寫 outbox。claim 使用 expected state／version 的原子 transition，寫入 owner、lease deadline 與 issued generation，而不是先讀再改；這次 issuance 不替其他資源 activation。 | dispatcher 重送 outbox，或 sweeper 掃描到未認領 task 後再次 claim；以 task history 驗證只有一個 claim transition 成功，並監控 pending aging，避免「可恢復」變成永久無人處理。 |
| **認領後、執行前 crash** | task 長期卡在 `PROCESSING`；若新 worker 直接重設狀態，晚到的舊 worker 可能與新 worker 同時執行。 | claim 結果與 owner／lease／issued generation 一起持久化；task store 可在同一 claim transaction 完成該 generation 的 activation，其他受保護資源則必須各自 activation／accepted write。副作用使用穩定 task id 派生的 idempotency key。 | lease 過期後由 reclaimer 取得更高 issued generation；在每個資源 activated／accepted 後才依其 floor 拒絕舊 fence，並從 durable checkpoint 續行。驗證 reclaim chain、各資源 floor 與 effect idempotency record，不能只驗 registry 發號。 |
| **外部操作成功但回應丟失** | caller 把 timeout 誤判為失敗並以新 key 重做，造成重複扣款、重複通知或重複建立資源；反過來若直接標記成功，也可能把真正失敗當完成。 | 首次呼叫前持久化穩定 business-effect identity、意圖摘要與 `UNKNOWN` outcome。安全 retry 必須有能序列化新 attempt 的執行邊界：provider 對同 business-effect key 原子去重；provider 提供原子 query-and-execute；或所有 provider call 只能通過可驗證 drain、並能在 dispatch boundary 拒絕 stale effect generation 的單一 egress。terminal `NOT_EXECUTED` 只解析舊 attempt，不會序列化新 attempt；只有 request id、「可查詢」或當下無 in-flight 都不構成 retry contract。 | 權威結果為 terminal success 時只提交既有結果。provider 原子去重時可以同 key retry；否則 terminal `NOT_EXECUTED` 只能作為原子 query-and-execute 或 fenced single-egress protocol 的輸入，由該邊界原子放行唯一新 generation。沒有這種執行邊界，即使查詢為 `NOT_EXECUTED` 也維持 `UNKNOWN`、不得 retry，改由 reconciliation／manual review 收口。 |
| **本地提交成功但通知未發** | 下游永久看不到已提交事實，流程形成部分成功；若補發時生成新 event id，下游還可能重複產生 effect。 | 在同一本地 transaction 內提交業務變更與 outbox record，event id 與 aggregate version 固定；relay 可 retry，但 consumer 必須以 message／command id 做 idempotent transition。 | relay 掃描未發布 outbox 並重送，收到 broker ack 後才更新 relay 狀態；以業務 row、outbox event、broker／consumer 收據與下游 durable fact 對照，不能只看「relay 已呼叫 send」。 |
| **lease 過期後舊 worker 復活** | 舊 worker 仍持有過期世界觀，覆蓋新 owner 的 checkpoint、釋放新 reservation，或發布舊版本結果；只檢查本地時間上的 lease 不足以阻止晚到寫入。 | claim／reclaim 只在 registry issued 單調遞增 token；每個 task、resource 或 active pointer 必須另以 resource-side atomic activation 推高 `fence_floor`，或在 accepted write 中比較 token、提交變更並推高 floor。要求接管開始前就阻斷舊 owner 時，先 activation 再做受保護工作。 | 只有資源 activated／accepted `N` 後，舊 worker 的 `< N` 提交才必須得到 stale-fence conflict；驗證 issued history、各資源 activated floor、accepted／rejected write。外部系統不接受 fence 時，仍靠 idempotency、結果查詢與 reconciliation 收口。 |
| **新舊 worker 同時嘗試完成** | 兩者都宣稱完成、重複發布結果，或一方完成後另一方把狀態回寫成失敗；單看「最後寫入者」會丟失合法完成事實。 | completion 是帶 expected state、owner／fence、result version 的單次原子 transition；外部 effect 綁同一 idempotency key，結果發布使用 immutable version 與 expected active pointer。 | 唯一成功的 completion 成為 durable outcome，失敗者重讀後若已是相同結果就安全結束，若結果不同則進 conflict／manual review；驗證 task terminal history、effect record 與 active version 只指向獲接受的 result。 |
| **補償失敗或結果未知** | Saga 永久停在半補償狀態，重試造成重複退款／重複釋放，或把未證明成功的補償標成 `COMPENSATED`。 | compensation 是有獨立 business-effect key、合法前置狀態、attempt history 與 outcome 的新業務命令；retry 必須有界並退避。對外 compensation 只能由 provider 原子去重／原子 query-and-execute，或能 drain 舊 generation 且拒絕 stale sender 的單一 egress 放行；單獨的 `NOT_EXECUTED` 查詢不是新 attempt 的許可。狀態機保留 `COMPENSATING`／`UNKNOWN`／`MANUAL`。 | provider 原子去重時可以原 business-effect key retry；否則必須由原子 query-and-execute 或 fenced single egress 根據 terminal `NOT_EXECUTED` 放行唯一新 generation。若無法序列化 sender，就保留 `UNKNOWN`、不 retry，由 reconciliation 建案及 manual review。關案前驗證 forward effect、compensation effect、帳本／reservation 與審批記錄能互相解釋。 |
| **人工修復與自動恢復競爭** | 人工已退款，自動 compensator 又退款；人工改成可繼續，自動流程卻用舊狀態覆蓋，形成二次事故與無法解釋的歷史。 | aggregate version 只能仲裁本地 transition，擋不住已送往 provider 的自動退款。人工接管先原子進入 `MANUAL`、提高 repair fence 並禁止排程新的自動 attempt；但 repair fence 不能撤銷接管前已獲准、暫停在 provider call 前的 sender。自動與人工共享同一 business-effect identity。provider 原子去重／原子 query-and-execute 可直接序列化兩者；否則必須先關閉新自動入口，drain 或撤銷所有舊 egress generation，並驗證任何已獲准但尚未 send 的 sender 都無法到達 provider，才能考慮人工 effect。 | provider 原子去重時，人工以同 business-effect key 回到既有結果或唯一 effect；provider 原子 query-and-execute 也可放行唯一 effect。沒有這兩種 provider contract 時，只有已驗證 drain／fenced egress，並由該 egress 根據 terminal `NOT_EXECUTED` 原子放行唯一 manual generation，才可產生人工副作用。未驗證 drain／fenced egress 或仍可能存在 paused sender，必須維持 `UNKNOWN`；人工只能處理案件與本地記錄，不得呼叫退款 provider。關案前驗證 provider effect、帳本、aggregate transition、repair fact、審批與 terminal reason 能互相解釋。 |

矩陣中的「可重試」必須落到具體協議：重試哪個穩定 business command、用哪個 idempotency key、由哪個 durable state 判斷前置條件，以及完成後查哪個權威 fact。若回答不出來，retry 只是再次下注，不是恢復策略。

## Part G · 高併發與容量

### 先分清 correctness 與 capacity

**Correctness** 問的是所有競爭、重試與接管路徑是否仍維持 invariant；**capacity** 問的是在給定工作負載與資源下，吞吐、排隊、延遲與恢復速度能否接受。兩者互相關聯但不能互相替代：增加 worker 可能提高非熱點步驟的容量，卻不會修復缺少 fence 的 stale write；constraint 能拒絕超賣，卻不代表衝突集中時仍有足夠吞吐。

因此先建立能拒絕非法結果的最小 correctness boundary，再量測該邊界的 capacity。當容量不足時，可以縮短臨界區、分區或拆分能力，但不能拿掉 invariant check 來換吞吐。

### 熱點 invariant 的天然串行點

只要多個 contender 必須共同決定同一份不可分割事實，例如「同一版本只能前進一次」或「同一份可售總量不能被重複消耗」，提交點就存在天然串行。DB lock、CAS、actor 或 queue 只是在等待、失敗重算與排隊之間選擇，不能讓互相衝突的決定同時合法提交。增加 worker 可以加速 key 之間的工作，卻無法突破單一熱點資源的序列化上限，反而可能增加等待者、衝突與 context switching。

在其他條件近似不變時，hot-key throughput 對 lock hold time 有反比的量級直覺：臨界區占用時間若增加約一個數量級，同一資源可完成的序列化操作量通常也會下降相近量級。這不是通用 SLA，也沒有跨硬體、schema、workload 都成立的固定 RPS；真實容量還受鎖面、I/O、索引、排隊政策、transaction abort 與下游延遲影響，必須用代表性負載量測。

### Optimistic CAS：衝突會放大工作

Optimistic CAS 在低衝突時避免先等待，但每次成功推進 version，都會使其他基於舊 version 的計算失效。若一次嘗試的讀取與重算成本為 `C`，同一輪有大量 contender 時，系統消耗的工作接近「所有 attempt 的 `C`」，而不是只有成功者的 `C`；立即且無界的 retry 又把失敗流量回灌，形成 retry amplification，最終演變成 retry storm。

控制手段是限制單命令的 attempt／總時間，使用 exponential backoff 與 jitter，為過載提供 admission control；當衝突持續偏高時，改用 per-key 排隊、等待式短事務或能力拆分。這些手段改善容量與穩定性，但 CAS predicate／constraint 仍是 correctness guard，不能因重試昂貴就繞過。

### Queue：削峰不是消除工作

Queue 把突發到達與下游可服務速率解耦，使 producer 不必同時占用 worker、DB connection 或熱點鎖，也能為相同 resource key 安排可控順序。但當長期 arrival rate 高於 service rate，工作只會累積成 backlog；結果是端到端延遲與資料新鮮度惡化，重送與保存成本上升，而不是容量憑空增加。

排隊政策還決定公平性。全域 FIFO 可能被單一 hot tenant 占滿；只偏好短任務可能讓長任務 starvation；嚴格 per-key FIFO 會讓 key 內慢任務造成 head-of-line blocking。生產設計要量測 queue depth、oldest age、per-key／tenant lag 與 drop／deadline outcome，並明確定義 weighted fairness、priority、deadline 或 tenant quota，而不是只看 consumer 數。

### 把競爭縮到真正共享的範圍

**resource-key partitioning** 依 resource key 路由命令，只縮小 contender 範圍；routing 本身不保證局部串行。同一 key 還需要唯一 active partition owner（帶 ownership epoch）或 ordered admission，確保同時最多一個 active command；即使執行入口已串行，resource-side version／constraint 仍要拒絕非法 commit。這才把全域鎖或單一 queue 的串行範圍縮小；hot key 仍是 hot partition，錯誤的 routing key 或 split-brain owner 都可能破壞 correctness。

**Reservation／Escrow** 則改變保護對象：先在強邊界把一份總量拆成數個有上限、可獨立消耗的 allocation，再讓各 partition 在自己的額度內並行。局部消耗不必每次競爭全域總量，但 allocation、轉移、expiry、回收與總額守恆仍需原子控制與 reconciliation。它只適合可切分、可預留的能力，不能把不可分割的唯一決定硬拆成數份。

### 恢復流量也要受控

故障恢復常同時釋放 timeout retry、expired lease reclaim、outbox replay 與 queue backlog。如果所有來源立即滿速重放，原事故雖已消失，恢復流量仍可能再次壓垮依賴。**Backpressure** 應沿 producer、queue、worker pool 與下游 admission 傳回；bounded retry 限制單命令與全局重試預算，jitter 打散同步喚醒，必要時依 tenant／operation 分流並保留人工與對帳通道的容量。

容量估算、排隊、池隔離與過載控制的公式及實驗，繼續閱讀 [並發容量工程](../concurrency-capacity/README.md)；本章只保留它們如何影響 correctness 選型的決策邊界，不重寫容量專題。

## Part H · 正確性閉環

線上協議的目標不是宣稱永不出錯，而是讓錯誤盡量在提交點被拒絕、殘餘偏差能被發現，並有可審計的恢復路徑。完整閉環分為三層：

```text
預防：constraint / atomic transition / short lock / fencing / idempotency
檢測：metric / immutable audit fact / history / invariant checker / aging alarm
恢復：retry / reclaim / compensation / reconciliation / manual repair
```

### 預防：讓非法結果在最小邊界被拒絕

constraint 與 atomic transition 直接表達 invariant；short lock 把需要共同判斷的本地資料放進有界臨界區；fencing 在資源寫入點拒絕 stale owner；idempotency 把相同業務意圖的 retry 綁回同一結果。這一層必須同時保存穩定業務識別與足夠的 outcome，否則 caller 在 timeout 後仍無法判斷是否可以重試。

### 檢測：以事實發現偏差，不以流程綠燈代替證明

metric 用於發現 conflict、stale-fence reject、unknown outcome、queue age 與 reconciliation difference 的趨勢；immutable audit fact 與 state／workflow history 回答「哪個命令基於什麼版本改了什麼」；invariant checker 直接比較帳本、reservation、active version 或跨系統權威 fact；aging alarm 找出長時間未前進的 task、outbox、compensation 與 manual case。

Metric 與 log 是線索，不是唯一業務真相。一次 activity 成功、消息已 ack 或 workflow 顯示 completed，都不能單獨證明外部 effect 與本地帳本一致；檢測要回到 durable business fact，且能重跑同一檢查得到可解釋差異。

### 恢復：讓偏差收斂到可解釋 terminal state

retry 只重做具有穩定 key、可判定前置狀態的命令；跨出本地邊界時，還必須有能序列化 sender 的執行邊界：provider 對同 business-effect key 原子去重／提供原子 query-and-execute，或所有對外呼叫經過能 drain 舊 generation 並 fence stale sender 的單一 egress。權威查詢即使返回 terminal `NOT_EXECUTED`，也只是舊 attempt 的 evidence，不能單獨允許 retry。reclaim 只讓新 fence 的 owner 接手；compensation 以新業務動作抵銷已發生 effect；reconciliation 比對權威事實並建立 repair case；manual repair 則以審批、expected version 與追加 audit fact 執行自動化無法安全決定的動作。恢復完成的標準不是 job 不再報錯，而是 invariant checker 通過，且 terminal reason、修復命令與外部結果能互相解釋。

三種機制的確定邊界不同，不能一概描述成「降低出錯機率」：**DB lock** 在同一本地 transaction 的鎖範圍內確定排除特定競爭，直到 commit／rollback，但不保護 transaction 外的 effect；**lease** 協調哪個 process owner 可嘗試工作與何時接管，卻不能撤銷暫停後復活的舊 owner，因此資源端仍需 fencing；**workflow** 以 durable history 保存跨服務控制狀態、timer 與 retry 決定，但不會把 activity 與外部 effect 原子化。它們都只能在各自邊界內提供保證；邊界外的 unknown／partial result 仍由 **Reconciliation 與可解釋的 Manual repair 負責最後收口**。這不是放棄在線保護的藉口；沒有預防產生的穩定識別與不可變事實，離線修復同樣只能猜測。

完整的 Difference → Case → Repair → Review → Close 模型，見 [統一對帳閉環](../financial-consistency/07-reconciliation/README.md)。

## Part I · 決策樹與反模式

### 選型決策樹

依序回答以下問題；前一層未釐清，就不要直接跳到工具名稱：

1. **只需要有效執行者，還是需要保護業務資料？**
   - 只需避免同一 task 多個有效 owner：使用 durable claim、owner／lease／heartbeat，並以 fencing 保護 owner 能寫入的 checkpoint。
   - 業務資料本身不能出現非法結果：先把 invariant 放進 resource side 的 constraint、atomic transition、version／fence；worker lock 只能當調度優化。
2. **只需穩定輸入，還是來源資料也必須禁止修改？**
   - 只要求同一次計算讀到同一業務版本：建立 immutable batch／snapshot，保存成員、值或可重建的 source version／cutoff。
   - 來源確實不可修改：把 logical freeze 寫成來源資料的合法狀態 transition，所有寫入路徑都必須檢查；不要用長 DB transaction 假裝業務 freeze。
3. **保護完整物件，還是可預留的稀缺能力？**
   - 完整 aggregate 的合法 transition：以 constraint、CAS 或短 pessimistic transaction 保護版本與狀態。
   - 庫存、資金、席位等可消耗能力：使用 reservation／TCC 的 hold、confirm、release 與 expiry；可切分且規模需要時再評估 Escrow。
4. **衝突頻率與重算成本如何？**
   - 低衝突且重算便宜：Optimistic CAS 加 bounded retry／backoff。
   - 高衝突或重算昂貴：短 pessimistic lock、per-key serialization 或 queue；再以量測判斷 hot-key capacity，不能只增加 contender。
5. **是否跨服務／資料庫／外部副作用？**
   - 都在同一本地 store 且延遲有界：保持單一短 transaction。
   - 跨出本地邊界：每個服務先守住自己的 invariant；需要可靠傳播用 Outbox，多步結果用 Saga／TCC，長等待、timer 或 signal 才使用 durable workflow。
6. **timeout 後能否查詢結果，副作用能否冪等重試？**
   - provider 若對同一 business-effect key 原子去重並返回原 terminal result，才可用同一 key retry；穩定 request id 本身不是去重保證。
   - provider 若提供原子 query-and-execute，可把「舊 attempt 未執行」與「只放行這一次新 effect」合成同一操作。
   - 沒有上述 provider contract 時，必須讓所有 provider call 經過單一 egress；該 egress 以 durable effect generation 原子選出唯一 sender，可 drain 舊 generation，並在 dispatch boundary 拒絕 stale sender。terminal `NOT_EXECUTED` 只能作為這個 protocol 放行新 generation 的輸入。
   - 查到 terminal success 就接受既有結果，不能 retry。查詢延遲、結果非終局，或雖查得 `NOT_EXECUTED` 但 provider 不去重、也沒有原子 query-and-execute／fenced single egress：保留 `UNKNOWN`，不得自動 retry，進 reconciliation／manual review；若業務無法承受 unknown outcome，應在整合前重新設計執行邊界。
7. **是否要求審計、重放、對帳與人工修復？**
   - 低風險且結果完全可由本地權威狀態判定，也仍需最小 transition history 與 aging alarm。
   - 高價值、跨控制域或可能 unknown／partial success：保存 immutable facts、workflow／command history、replay key、reconciliation rule、repair approval 與 terminal reason；把值班 owner 與 Manual path 當正式協議。

### 常見反模式

| 反模式 | 為何失敗 | 應改成什麼 |
|---|---|---|
| **用長 DB transaction 包住長任務** | 長時間占用 connection、lock 與 undo，不能涵蓋外部 I/O，也無法讓新 worker 接管原 transaction。 | 本地短事務提交 durable state／checkpoint，邊界外計算；以 immutable batch、reservation 或 workflow 處理長生命週期。 |
| **把 Redis lock 當完整正確性保證** | lock 過期、failover 或 pause 後可能出現多個自認 owner，且 lock 不會讓業務資料自動拒絕 stale write。 | lock／lease 只做協調；在資源端用 fencing、version、constraint 與 idempotency 保護 effect。 |
| **`PROCESSING` 無 owner／lease／fencing** | 無法判斷誰仍有效、何時可接管，也無法阻止舊 worker 在 reclaim 後晚到寫入。 | 持久化 owner、lease deadline、heartbeat、遞增 fence 與 reclaim history，所有關鍵 transition 檢查 fence。 |
| **retry 無 idempotency** | timeout 或 duplicate 會把同一意圖執行多次，副作用次數取決於網路與重試政策。 | 穩定 key 綁定意圖摘要與 durable result；在權威執行邊界以 provider 原子去重／原子 query-and-execute 或 fenced single egress 保證同 key 同意圖只能放行一個 effect generation，不同意圖必須拒絕。 |
| **snapshot 只存 ID** | 後續按 ID 回讀會取得新值，批次仍混合版本；也可能無法重建已刪除或變更的輸入。 | 保存 immutable value／version，或保存能由版本化資料源精確重建的 cutoff 與 schema／rule version。 |
| **Saga 無補償失敗處理** | compensation 本身可能 timeout、永久失敗或與後續交易衝突，流程會卡在不可解釋的半完成狀態。 | 為補償建立 idempotency、outcome history、bounded retry、查詢、reconciliation 與 `MANUAL` terminal path。 |
| **只存當前狀態** | 無法判斷狀態如何到達、哪個 owner／命令已提交，也不能安全重放、查 duplicate 或解釋人工修復。 | 保存 immutable transition／command／effect facts，當前狀態只是由合法歷史推進的 projection。 |
| **沒有對帳與修復** | 在線協議漏掉的 unknown outcome、外部人工變更與永久 partial success 只會累積，告警也不能使 invariant 恢復。 | 建立差異規則、aging scan、repair command、審批復核、重跑驗證與可審計 close reason。 |

### 四個場景演練

#### 1. 批次統計：stable batch

1. **Invariant**：同一份統計不得混入不同業務版本；只有覆蓋完整 batch 的結果才能成為 active result。
2. **保護對象**：保護 batch 的 immutable inputs／version、schema／rule version，以及結果對 batch id／generation 的綁定；不保護 worker 生命週期。只要能精確重建輸入就不必凍結來源；業務真的要求禁止修改時，才另建 logical freeze transition。
3. **Correctness boundary**：以短本地事務建立 batch、封存成員與值，或封存可重建的 source version／cutoff；長計算在 transaction 外執行，結果以 expected batch state 切換 active pointer。**跨服務分支**：本場景假定輸入已落在本地 immutable batch，所以計算過程不需要跨服務一致性；若來源在外部服務，必須先以版本化 export／ingestion 形成 batch，不能讓長事務跨服務讀取。
4. **競爭程度／重算成本**：不同 shard 可並行，同一 shard／generation 的 checkpoint 與最終 active pointer 才會競爭。重算便宜時用 expected version 與有界重試；重算昂貴時用 per-batch ordered admission 與更細 checkpoint，不讓多個 contender 反覆重做同一片。
5. **Failure model**：crash 可留下缺片，reclaim 後的舊 generation 可能 late write，來源變更或刪除則可使只存 ID 的 batch 無法重建。**timeout 分支**：純計算 timeout 沒有產生外部業務副作用，因此可對同 batch／shard／generation 冪等重算；它不是 provider outcome 不明的 `UNKNOWN` effect。
6. **Mechanism**：partial result 攜帶 batch id／generation 並寫成 immutable version；checkpoint 幫助 crash 後續算，fence／version 拒絕舊 generation，最後在 input count／checksum 與 coverage 驗證通過後原子綁定 active result。
7. **Proof／recovery**：比較 source cutoff、input count／checksum、partial coverage 與 result checksum；缺片冪等重算，已發布錯誤則切回已知良好版本後以同 batch 證據重建。**審計分支**：即使不需外部對帳，仍保留 batch／generation／active-pointer transition 與 aging alarm；高風險報表再保留完整輸入版本、規則與發布審批。

#### 2. 庫存預留：scarce capacity

1. **Invariant**：confirmed 加上仍有效的 held quantity 不得超過可售能力，同一 reservation 只能由 held 進入一個 terminal state。
2. **保護對象**：保護可預留的 scarce capacity 與 reservation 狀態，不需鎖住商品整個 aggregate，更不是保護訂單 worker。
3. **Correctness boundary**：hold／confirm／release／expiry 在庫存服務內以 atomic condition／short transaction 保護 quantity 與 expected state。**跨服務分支**：訂單與付款參與時此分支適用；各服務只在本地提交 invariant，用 outbox 與 Saga／TCC 傳播命令與結果，不用長 transaction 跨服務持鎖。
4. **競爭程度／重算成本**：hot SKU 的 confirm／expiry 在同一能力提交點高度競爭；雖然重算數量廉價，無界 CAS retry 仍會放大負載。低衝突用 bounded CAS，高衝突用短鎖／per-key ordered admission；能力可切分且總額守恆可驗證時才使用 Escrow。
5. **Failure model**：duplicate hold，confirm 與 expiry／release 競爭，以及付款成功但回應遺失，都可使訂單與能力分歧。**timeout 分支**：本地 reservation 命令以同 reservation id／idempotency key 返回既有結果；provider effect 只在 provider 原子去重／原子 query-and-execute，或 fenced single egress 能 drain 舊 generation 並放行唯一新 sender 時才能 retry。`NOT_EXECUTED` 單獨不足；沒有執行邊界就保留 `UNKNOWN`。
6. **Mechanism**：以 reservation id、expected state、idempotency key 建立真實扣住能力的 `hold → confirm／release／expiry`；expiry 也是帶版本的 transition，不刪除歷史，confirm 與 expiry 競爭時只有一方能提交。
7. **Proof／recovery**：reconciliation 比對庫存總量、有效 hold、confirmed consumption、expired／released history 與訂單／付款事實；孤兒 hold 依規則釋放，unknown effect 在解析前不重做。**審計分支**：庫存影響可售數與訂單，因此必須保留 reservation transition／business-effect identity／reconciliation difference；無法自動證明的高風險差異進 manual case。

#### 3. 單 worker 任務：effective owner

1. **Invariant**：任一資源 activated generation `N` 或 accepted 帶 `N` 的寫入後，都拒絕 `< N`；registry 最新 issued generation 尚未到達該資源前，不宣稱舊 generation 已被 fence。
2. **保護對象**：保護每個資源自己的 `fence_floor`、accepted generation、checkpoint 與 result transition，不是保證只有一個 process 正在執行；短暫並行可存在，但 activated floor 以下的 stale owner 不能提交。
3. **Correctness boundary**：claim／heartbeat／reclaim 在 owner registry issued generation；task store 與每個業務資源分別以自己的原子 activation 或 accepted write 推高 floor。registry issuance 不能替資源完成 fencing。**跨服務分支**：「單 effective owner」本身是調度契約，純本地 task 不適用跨服務機制；若 task 呼叫遠端服務，該 effect 另以對方的 idempotency／result contract 保護，fence 不會自動穿越邊界。
4. **競爭程度／重算成本**：競爭集中在首次 claim、lease expiry 附近的 reclaim 與 completion；原子條件更新讓失敗 contender 重讀，不無界自旋。重算成本以 checkpoint 間隔上界控制；如果重算昂貴，縮短 durable checkpoint 間隔，不是延長 lease 來隱藏失去 worker。
5. **Failure model**：worker crash／pause 可使 lease 過期，新舊 owner 並行，舊 worker 復活後可能 late write；duplicate delivery 也可重做已完成 step。**timeout 分支**：只寫本地 checkpoint 時 outcome 可由 task store 權威查詢，所以不存在外部 effect unknown；若 step 有外部副作用，task owner fence 不會自動穿越 provider 邊界，只有 provider 原子去重／原子 query-and-execute，或所有 call 通過能 drain 舊 owner generation 的 fenced single egress，才允許 retry。查得 `NOT_EXECUTED` 仍不能自行換 key 重做。
6. **Mechanism**：claim 在 registry 原子寫入 owner、lease deadline 並 issued 遞增 token；heartbeat 有條件續租，lease expiry 後 reclaimer 取得更高 issued generation。新 owner 在開始受保護工作前先讓資源 activated 該 generation，或由第一次 accepted checkpoint／completion 原子推高 floor；外部 effect 另綁定 task／step 派生的 business-effect key。
7. **Proof／recovery**：分別驗證 claim／heartbeat／reclaim 的 issued history、各資源 activated floor，以及 checkpoint／completion 的 accepted／rejected result；卡住 task 可 reclaim，不可判定的外部 effect 交 reconciliation／Manual review。**審計分支**：即使 task 低風險，仍需最小 ownership、resource-side floor 與 terminal history 才能證明接管正確；只有產生高價值外部 effect 時才升級為完整 effect fact、對帳與人工審批。

#### 4. 跨服務訂單：local transaction 到收斂

1. **Invariant**：每個服務的帳本、訂單狀態與 reservation 必須合法；端到端結果必須收斂為已完成、已補償或可審計的人工處理，不能永久部分成功。
2. **保護對象**：保護各服務自己的 aggregate／ledger／reservation transition，以及每個外部副作用的 business-effect identity；不把整條 Saga 當成一個可跨服務持鎖的物件。
3. **Correctness boundary**：order service 在同一 local transaction 提交訂單 transition 與 outbox，consumer 也以 command id／aggregate version 進行本地冪等提交。**跨服務分支**：此場景明確適用；服務間靠 outbox 傳播不可變事實，由 Saga／workflow 保存進度，不宣稱外部 effect 與所有 local transaction 原子提交。
4. **競爭程度／重算成本**：同一 order／reservation／payment intent 的 duplicate／late command 高度競爭，不同 aggregate 可並行；依 aggregate key ordered admission 來降低衝突，但各資源仍用 version／constraint 拒絕非法提交。workflow step 可由 durable history 重放，外部付款不是可以任意「重算」的動作。
5. **Failure model**：local commit 後未發事件、duplicate delivery、forward 部分成功、compensation 失敗，以及付款成功但回應遺失，都可使服務間分歧。**timeout 分支**：此場景明確適用；provider 對同 business-effect key 原子去重時可 retry，否則必須使用原子 query-and-execute 或能 drain 舊 generation／fence stale sender 的單一 egress。無上述邊界時，即使查得 `NOT_EXECUTED` 也保留 `UNKNOWN`、不產生第二次 effect。
6. **Mechanism**：local transaction／Outbox 避免 dual write，Saga／durable workflow 保存每個 forward／compensation outcome、timer 與下一步；只有真實 reservation 才使用 TCC。compensation 是具有獨立 key 的新業務命令；外部 effect 共享穩定 identity，workflow 不取代服務內 constraint。
7. **Proof／recovery**：reconciliation 比對訂單 history、outbox／consumer fact、庫存 reservation、付款帳本與 provider terminal result；差異生成 repair case，修復以 expected version 與審批命令追加事實，重跑 checker 後才關案。**審計分支**：此場景橫跨多個權威來源且可能 unknown／partial success，因此完整 command／effect／workflow history、repair approval 與 terminal reason 是必要契約，不是選配 log。
