# 05 · 配置讓它真的吐(Py/Go/Java 各自的坑)

> 治的症狀:**「沒有日誌」**(程式明明 log 了卻沒輸出)、**「等級看不到」**(門檻擋掉)、**「同一條重複」**(配置造成重複發射)。
> 前面四章是「**寫**對」,這章是「**配**對」—— 寫得再好,配置沒接上,一行都吐不出來。三語言各有一個經典陷阱。

---

## 一、共同心智模型:日誌怎麼從一行程式碼走到你眼前

不管哪個語言,一條日誌都要經過這條管線:

```
log.info(...)  →  [logger:檢查 level 門檻]  →  [handler/appender:格式化 + 寫到哪]  →  輸出(stdout/檔案/遠端)
```

「沒輸出」一定是這條管線斷在某處:**要嘛被 level 擋,要嘛根本沒接 handler,要嘛 handler 寫到你沒在看的地方。** 「重複」則是這條管線**接了兩條**。三語言的差異,就在「logger 怎麼組織」和「handler 怎麼掛」。

---

## 二、Python:`logging` 階層 + propagate(雙重發射的元兇)

### 階層與傳播

Python 的 logger 是一棵**樹**,用名字的點號分層:`getLogger("a.b")` 是 `getLogger("a")` 的子,最上面是 root。

```python
log = logging.getLogger(__name__)   # 慣例:用模組名,自動形成階層
```

關鍵機制 **propagate(預設 True)**:一條紀錄在某個 logger 產生後,會**往上冒泡**,依序交給**每一個祖先的 handler** 處理,直到 root。

### 🔬 坑 1:沒有 handler → 你的 INFO/DEBUG 靜默消失(「沒日誌」)

如果整棵樹**都沒有任何 handler**,Python 會啟用一個 `lastResort` 後備 handler —— 但它**只印 WARNING 以上到 stderr**。於是:

```python
log = logging.getLogger("myapp")
log.info("started")     # ❌ 沒配 handler → lastResort 不收 INFO → 人間蒸發
log.warning("careful")  # 這條才會(以陽春格式)出現
```

這就是無數人「為什麼我的 INFO 都不見」的答案:**不是程式錯,是根本沒配輸出。**

### 🔬 坑 2:handler 掛兩處 / 重複註冊 → 同一條印兩三次(「重複」)

因為 propagate 會走訪祖先的 handler,如果你**同時在子 logger 和 root 掛 handler**,一條 log 就被印兩次:

```python
logging.getLogger("myapp").addHandler(h1)   # 子
logging.getLogger().addHandler(h2)          # root
logging.getLogger("myapp").info("hi")       # ❌ h1 印一次,冒泡到 root 又被 h2 印一次
```

更常見的是**重複執行 setup**(在每個請求、模組重載、notebook 重跑時又 `addHandler`),handler 越疊越多,一條變 N 條。

### 正解:一次設好,只在 root 掛唯一 handler

```python
import logging.config

logging.config.dictConfig({
    "version": 1,
    "disable_existing_loggers": False,
    "formatters": {"json": {"()": "myapp.log.JsonFormatter"}},
    "handlers": {"stdout": {"class": "logging.StreamHandler", "formatter": "json"}},
    "root": {"handlers": ["stdout"], "level": "INFO"},   # ✅ 唯一 handler 在 root
    "loggers": {
        "myapp": {"level": "DEBUG"},   # ✅ 子 logger 只設 level,不掛 handler,靠 propagate
        "uvicorn.access": {"level": "WARNING"},  # 馴服框架 logger
    },
})
```

口訣:**業務 logger 只 `getLogger(__name__)` + 設 level,不要自己 `addHandler`;handler 統一掛 root。** 這樣杜絕雙重發射,也保證一定有輸出。

> `basicConfig()` 的陷阱:它**只在 root 還沒有 handler 時**生效一次,第二次呼叫是 no-op(除非 `force=True`)。所以混用 `basicConfig` + 自己 `addHandler` 很容易出意外。生產用 `dictConfig` 一次到位。

### 真實場景:FastAPI 不同模塊,不只靠 level

#### 先分清 severity 與 policy

不同模塊可以有不同的**日誌 policy**,但不應有不同的 **severity 語意**。`ERROR` 在 payment、order、auth 都表示「某項功能未能完成,需要處理」;不能因為 payment 比較重要,就把正常成功事件升成 `ERROR`。

真正需要分開控制的是:

| 差異或問題 | 首選機制 | FastAPI 場景 | 不該怎麼做 |
|---|---|---|---|
| 診斷細節不同 | logger namespace + selective level override | 只把 `app.payment` 臨時開到 `DEBUG` | 全服務永久 `DEBUG` |
| access log 流量太大 | filter + sampling/rate limit | 2xx 採樣,5xx 與慢請求全留 | 把正常 request 改記成 `WARNING` |
| 第三方 library 太吵 | dependency logger threshold | `httpx`、`sqlalchemy.engine` 設 `WARNING` | 修改第三方事件 severity |
| 日誌去向不同 | named logger + handler/collector routing | `app.audit` 送受保護 index | 靠 message 字串猜來源 |
| 保存期限不同 | channel + backend retention | audit 長期、access 短期 | FastAPI request path 自管 rotation |
| 資料敏感 | allowlist + redaction + ACL | token、cookie、密碼永不輸出 | 以關閉 `DEBUG` 代替遮罩 |
| 單次事故排障 | scoped override / trace filter | 放大指定 namespace 或 `trace_id` | 公開、永久的 `setLevel` endpoint |

一句話:**level 只控制 verbosity;filter 控制哪些事件留下;handler/collector 控制送去哪;backend 控制保存與權限。**

#### 1. 業務模塊:用 namespace 表達來源

每個模塊只取得自己的 logger,提交正確 severity、穩定事件名與必要 context:

```python
# app/payment/service.py
import logging

log = logging.getLogger(__name__)  # app.payment.service


def mark_payment_succeeded(order_id: str, gateway: str) -> None:
    log.info(
        "payment succeeded",
        extra={
            "event_name": "payment_succeeded",
            "order_id": order_id,
            "gateway": gateway,
        },
    )
    log.debug(
        "payment decision details",
        extra={
            "event_name": "payment_decision_debug",
            "order_id": order_id,
        },
    )
```

`app.order` 等其他業務模塊沿用 `getLogger(__name__)`,平時繼承 root 的 `INFO`。只有事故範圍已確認在 payment 時,才用版本化配置把 `app.payment` 改成 `DEBUG`:

```python
LOGGING_CONFIG = {
    "version": 1,
    "disable_existing_loggers": False,
    "handlers": {
        "stdout": {
            "class": "logging.StreamHandler",
            "level": "DEBUG",
            "stream": "ext://sys.stdout",
        }
    },
    "root": {"handlers": ["stdout"], "level": "INFO"},
    "loggers": {
        "app.payment": {"level": "INFO"},  # 事故期間才改 DEBUG
        "httpx": {"level": "WARNING"},
        "sqlalchemy.engine": {"level": "WARNING"},
    },
}
```

注意 handler 的門檻是 `DEBUG`:child logger 顯式開 `DEBUG` 後,record 冒泡到 root handler 時才能輸出。root logger 的 `INFO` 不會重新過濾已由 child logger 接受的 record;祖先 handler 自己的 level 才會再過濾(見本章第六節)。

#### 2. Access log:按事件特性採樣,不扭曲 severity

需要結構化欄位、慢請求規則或 sampling 時,可停用 Uvicorn 預設 access log,由 middleware 發出一條 `app.access` request summary:

```python
# app/logging.py
import hashlib
import logging


class AccessPolicyFilter(logging.Filter):
    def __init__(self, sample_rate: float = 0.1, slow_ms: float = 1000.0):
        super().__init__()
        self.sample_rate = sample_rate
        self.slow_ms = slow_ms

    def filter(self, record: logging.LogRecord) -> bool:
        status_code = int(getattr(record, "status_code", 0))
        duration_ms = float(getattr(record, "duration_ms", 0.0))
        route = str(getattr(record, "route", ""))

        if status_code >= 500 or duration_ms >= self.slow_ms:
            return True
        if 400 <= status_code < 500:
            return True
        if not 200 <= status_code < 300:
            return True
        if route in {"/healthz", "/readyz"}:
            return False

        request_id = str(getattr(record, "request_id", ""))
        if not request_id:
            return True  # 缺採樣鍵時保守保留,避免靜默丟失

        digest = hashlib.blake2b(
            request_id.encode("utf-8"), digest_size=8
        ).digest()
        bucket = int.from_bytes(digest, "big") / 2**64
        return bucket < self.sample_rate
```

```python
# app/main.py
import logging
import time

from fastapi import FastAPI, Request

app = FastAPI()
access_log = logging.getLogger("app.access")


@app.middleware("http")
async def access_summary(request: Request, call_next):
    started = time.monotonic()
    status_code = 500
    try:
        response = await call_next(request)
        status_code = response.status_code
        return response
    finally:
        route_object = request.scope.get("route")
        route = getattr(route_object, "path", request.url.path)
        access_log.info(
            "request completed",
            extra={
                "event_name": "http_request_completed",
                "request_id": getattr(
                    request.state,
                    "request_id",
                    request.headers.get("x-request-id", ""),
                ),
                "method": request.method,
                "route": route,
                "status_code": status_code,
                "duration_ms": round(
                    (time.monotonic() - started) * 1000, 1
                ),
            },
        )
```

> 邊界:此 `@app.middleware("http")` 的 `duration_ms` 只量到 `call_next()` 回傳 response。`StreamingResponse` body 完整傳輸時間與 late exception 不在此 summary 的保證範圍。若需完整 streaming timing 或 late failure,使用 pure ASGI middleware 攔截最後一個 `http.response.body`,或由 server/telemetry 量測。

Filter 只掛 `app.access` 的 handler,不能掛 root,否則會誤採樣業務、exception 與 audit:

```python
"filters": {
    "access_policy": {
        "()": "app.logging.AccessPolicyFilter",
        "sample_rate": 0.1,
        "slow_ms": 1000.0,
    }
},
"handlers": {
    "access_stdout": {
        "class": "logging.StreamHandler",
        "level": "INFO",
        "filters": ["access_policy"],
        "formatter": "json",
        "stream": "ext://sys.stdout",
    }
},
"loggers": {
    "app.access": {
        "handlers": ["access_stdout"],
        "level": "INFO",
        "propagate": False,
    }
},
```

此 middleware 的 500 summary 只涵蓋 `call_next()` 回傳前拋出的 exception,仍是 access 事件,不取代全域 exception handler 的 `ERROR + stack trace`。部署時二選一:

- 保留 `uvicorn.access`,在中央配置單獨調整它;
- 使用 `uvicorn --no-access-log`,改由上述 middleware 產生結構化 access event。

兩者同時開會讓每個 request 記兩次。

#### 3. 第三方 library:只調它的 namespace

`httpx`、`sqlalchemy.engine` 等第三方 logger 在中央 `dictConfig` 設門檻,不在業務模塊呼叫 `setLevel()`。SQLAlchemy 已由 logging config 管理時,保持 `echo=False`;`echo=True` 會額外配置輸出,容易產生重複日誌。

事故若需要 SQL 細節,只調 `sqlalchemy.engine`;事故結束恢復原值。不要把 root 改成 `DEBUG`,否則所有 framework/library 一起放大。

#### 4. Audit/security:分流,但別冒充可靠帳本

普通安全事件可用獨立 logger 與 allowlist 欄位:

```python
import logging

audit_log = logging.getLogger("app.audit")


def record_refund_approved(
    actor_id: str, order_id: str, refund_id: str
) -> None:
    audit_log.info(
        "refund approved",
        extra={
            "event_name": "refund_approved",
            "channel": "audit",
            "actor_id": actor_id,
            "order_id": order_id,
            "refund_id": refund_id,
        },
    )
```

```python
"handlers": {
    "audit_stdout": {
        "class": "logging.StreamHandler",
        "level": "INFO",
        "formatter": "json",
        "stream": "ext://sys.stdout",
    }
},
"loggers": {
    "app.audit": {
        "handlers": ["audit_stdout"],
        "level": "INFO",
        "propagate": False,
    }
},
```

Collector 依 `channel=audit` 路由到受限 index,backend 設獨立 retention 與 ACL。欄位採 allowlist;token、cookie、密碼、完整 request body 不得進日誌。

若 audit 是法規、財務或「業務成功必須留下證據」的記錄,不能只靠 best-effort application log。這類事件應寫 transactional outbox 或 durable append-only audit store,日誌只作查詢副本。

#### 處理流程與失敗邊界

```text
FastAPI module
  → named logger
  → effective severity threshold
  → filter(sampling / redaction)
  → handler / stdout
  → collector routing
  → index / retention / ACL
```

- 業務代碼負責 severity、`event_name` 與 context;
- logging config 負責 level、filter、handler;
- collector/backend 負責 routing、retention 與 ACL;
- filter 使用 `getattr(record, field, default)`,缺欄位不可令 request 失敗;
- exception、5xx、慢請求與 audit 不進一般 2xx sampling;
- 不在 request path 使用同步 remote handler;collector 丟失或積壓另用 metric/alert 監控。

#### 動態調級:可選事故工具,不是基線

基線做法是版本化 config/env 加 rolling restart。只有不能重啟且排障 SLA 確有需要,才提供 runtime override;此時必須具備 logger/level allowlist、管理權限、審計、TTL 自動恢復與手動回滾。

Uvicorn 多 worker 與多個容器副本各有獨立進程記憶體。單次 `logger.setLevel()` 只修改收到請求的 worker,不會自動同步其他 worker/副本;沒有集中配置或廣播時,不能宣稱已完成生產級動態調級。

#### 常見反例

- 每個模塊自己掛 handler、自己 `setLevel()`;
- 用 `ERROR` 表達「這個模塊很重要」;
- 為壓低成本而採樣 5xx、exception 或 audit;
- 用關閉 `DEBUG` 代替敏感資料遮罩;
- 同時保留 `uvicorn.access` 與自訂 access middleware;
- 把普通 application log 當成法規 audit 的唯一證據。

#### 官方依據

- [Python Logger Objects](https://docs.python.org/3/library/logging.html#logger-objects):logger hierarchy、`getLogger(__name__)`、effective level 與 propagation。
- [Python logging.config](https://docs.python.org/3/library/logging.config.html#logging-config-dictschema):逐 logger 的 level、handler、filter 與 `propagate` 配置。
- [Uvicorn Logging Settings](https://www.uvicorn.org/settings/#logging):`--log-config`、`--log-level` 與 `--no-access-log`。
- [Uvicorn Deployment](https://www.uvicorn.org/deployment/#built-in):`--workers` 啟動多個獨立進程。

以上官方資料支撐 logging 機制;sampling、routing、retention 與 audit 邊界是本章基於這些機制整理的工程治理建議。

## 三、Go:從「沒等級」的老 `log` 到 `slog`

### 🔬 坑:標準庫老 `log` 套件**沒有等級概念**

```go
import "log"
log.Println("something")   // 就一行,沒有 level,無法「prod 只看 WARNING 以上」
```

這是很多 Go 服務「等級不夠 / 沒法過濾」的根源 —— 用了一個**根本沒有 level** 的工具。正解是 Go 1.21(2023)才進標準庫的 **`log/slog`**。

### 正解:全域設好一個 leveled handler

```go
import (
    "log/slog"
    "os"
)

func init() {
    h := slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{Level: slog.LevelInfo})
    slog.SetDefault(slog.New(h))   // ✅ 設全域:之後任何 slog.Info 都走這個 handler
}
```

`slog.SetDefault` 還有一個好處:它會把**老 `log` 套件的輸出也接管**到 slog,讓第三方庫用老 `log` 打的東西也統一格式。

### Go 為什麼幾乎不會有 Python 那種「重複」

Go 的 slog **沒有階層、沒有 propagate** —— 一個 logger 就一個(或一串顯式包裝的)handler,不會自動往上冒泡。所以 Go 的「重複」通常是你自己造的:**多次 `SetDefault`、或把 handler 包了兩層都會寫**、或你又 `slog` 又用老 `log` 各寫一份。排查方向跟 Python 不同。

> 另一個 Go 專屬坑:用 `slog.Info(...)`(不帶 ctx)時,你那個「從 context 取 request_id」的自訂 handler **拿不到 ctx** → request_id 不見。要用 `slog.InfoContext(ctx, ...)`(呼應 `03`)。

## 四、Java:SLF4J 是門面,真正輸出要綁一個後端

### 🔬 坑 1:沒綁 backend → 全部靜默(「沒日誌」)

SLF4J(`org.slf4j`)**只是介面(facade)**,自己不會輸出任何東西。真正幹活的是後端實作(**Logback** / Log4j2)。classpath 上:

- **沒有任何 provider** → 啟動印 `SLF4J: No SLF4J providers were found`,所有 log 走 NOP(什麼都不做)→ 全部靜默。
- **有多個 provider**(同時混進 logback + log4j + slf4j-simple)→ 印 `Class path contains multiple SLF4J providers`,隨機挑一個 → 行為詭異。

這就是 Java「明明 log 了卻沒輸出 / 格式怎麼變了」的頭號原因:**binding 沒接好。** 正解:只留**一個**後端(Spring Boot 預設給你 `logback-classic`,別再手動拉別的進來)。

### 🔬 坑 2:additivity → 同一條印兩次(「重複」)

Logback 的 logger 也是**階層 + 冒泡**,機制和 Python propagate 一模一樣,叫 **additivity(預設 true)**:一條 log 會交給自己的 appender,**再交給祖先(root)的 appender**。如果你在某個 logger 和 root **都掛了 appender**:

```xml
<logger name="com.myapp" level="INFO">
    <appender-ref ref="STDOUT"/>     <!-- 自己印一次 -->
</logger>
<root level="INFO">
    <appender-ref ref="STDOUT"/>     <!-- 冒泡到 root 又印一次 ❌ -->
</root>
```

→ 每條 `com.myapp` 的 log 印兩次。修法:要嘛**只在 root 掛 appender**,要嘛在該 logger 設 `additivity="false"` 切斷冒泡。

### 正解(Spring Boot):`logback-spring.xml`,appender 只掛 root

```xml
<configuration>
  <appender name="STDOUT" class="ch.qos.logback.core.ConsoleAppender">
    <encoder class="net.logstash.logback.encoder.LogstashEncoder"/>  <!-- 輸出 JSON -->
  </appender>
  <logger name="com.myapp" level="INFO"/>   <!-- 只設 level,不掛 appender,靠冒泡 -->
  <root level="WARN">
    <appender-ref ref="STDOUT"/>            <!-- ✅ 唯一 appender 在 root -->
  </root>
</configuration>
```

## 五、把「重複」一次講清楚:兩個完全不同的根因

你說的「同一條重複」其實有**兩個來源,住在兩章**,面試常考你能不能分清:

| 重複的種類 | 根因 | 在哪章 | 怎麼認 |
|---|---|---|---|
| **配置重複發射** | propagate(Py)/ additivity(Java)/ 多次 SetDefault(Go):handler 掛多處 | 本章 `05` | 重複的內容**一模一樣**(同一行、同 timestamp),只是輸出兩三份 |
| **程式碼 cascade** | 每層 `catch → log → rethrow` | `04` | 重複的是**堆疊**,出現在不同 logger、訊息不同(`dao failed` / `service failed`) |

看到重複先分這兩類:內容完全一樣 → 查配置;堆疊在不同層 → 查 catch-rethrow。

---

## 六、🔬 內幕:階層 + 冒泡的精確機制(Python/Java 共通)

一條 log 產生時的判定順序(以 Python 為例,Java additivity 同理):

1. **產生與否**:看「你 log 在哪個 logger」的**有效等級**(沿樹往上找第一個有設 level 的祖先)。被擋就此打住,連 record 都不建。
2. **若產生**:交給**該 logger 自己的 handler**;
3. **若 propagate=True**:再依序交給**每個祖先的 handler**(一路到 root)。
4. 注意:冒泡時**不再重新檢查祖先 logger 的等級**,但**每個 handler 自己**還有一層 level 過濾。

所以「沒輸出」可能卡在:logger 有效等級擋掉(第 1 步)、或沒有任何 handler(第 2/3 步沒人收)、或 handler 自己的 level 又擋一層(第 4 步)。「重複」則是第 2 步和第 3 步**都有 handler**。Go 沒有第 3 步,所以結構簡單、也少這類坑。

- [ ] **Go**:用 `log/slog`(不用老 `log`);啟動時 `slog.SetDefault` 設好 leveled JSON handler;一律 `InfoContext(ctx, ...)`。
- [ ] **Java**:classpath 只有**一個** SLF4J 後端;appender **只掛 root**(或 `additivity="false"`);Spring 用 `logback-spring.xml`。
- [ ] 遇到「重複」先分類:**內容全同**→查配置(本章);**堆疊分層**→查 cascade(`04`)。
- [ ] 確認 prod 真的有輸出:啟動後 `curl` 打一條,確認 stdout 有結構化 JSON。
