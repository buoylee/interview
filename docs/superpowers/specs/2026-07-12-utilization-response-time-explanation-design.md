# 利用率与响应时间非线性关系补充设计

## 目标

补足 `performance-tuning-roadmap/01-methodology/04-performance-laws.md` 中从 M/M/1 公式直接跳到倍率结论的问题，让读者理解响应时间为何按 `1 / (1 - ρ)` 非线性增长，而不只是记住公式。

## 放置位置

在“利用率与响应时间的非线性关系”一节中，放在平均响应时间公式及符号定义之后、现有利用率倍率表之前。阅读顺序调整为：公式、原因、数字验证、工程启示。

在倍率图之后、工程启示之前补充适用边界，避免打断核心推导。

## 内容结构

新增“为什么会非线性增长”小节，依次包含：

1. 定义无排队时的平均服务时间 `S = 1 / μ`。
2. 解释利用率升高不只增加忙碌时间，还会压缩消化随机积压的剩余处理能力；当 `ρ → 1` 时，余量趋近于零。
3. 结合 Little 定律给出简短推导：`L = λW`，到达请求平均需要等待系统中已有的 `L` 个请求再加自身，因此 `W = (L + 1)S`；代入并整理得到 `W = S / (1 - ρ)`。
4. 使用 `μ = 100 req/s` 的例子说明：`ρ = 80%` 时 `W = 50 ms`，`ρ = 90%` 时 `W = 100 ms`。利用率只增加 10 个百分点，平均响应时间却翻倍。

## 准确性修正

- 将“CPU 80% 时延迟就开始飙升”限定为 M/M/1 近似场景，不把 80% 描述为所有系统的固定拐点。
- 说明 M/M/1 假设包括泊松到达、指数服务时间、单服务台和稳态 `ρ < 1`；70%–80% 是容量规划经验余量，不是普适定律。
- 将“利用率 60%，流量翻倍到 90%”修正为“流量增加 50%，利用率从 60% 升至 90%”。
- 将后文“100 线程”容量示例中的 70% 安全系数表述为简化的容量预算，而非由 M/M/1 严格推导出的结论。

## 验收标准

- 读者能从正文回答分母 `1 - ρ` 的来源，以及它为何造成非线性增长。
- 公式、数值示例和倍率表彼此一致。
- 正文明确模型边界，不将单服务台模型直接等同于多核 CPU 或线程池。
- 保持现有章节的简洁、直觉优先风格，不引入超出解释所需的排队论细节。
