# MySQL ES CDC Hands-on M4 Reconciliation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox - [ ] syntax for tracking.

**Goal:** Add an implementation-independent verifier that can prove the current MySQL-to-Elasticsearch projection is exact, classify every mismatch, repair bounded drift from current MySQL facts, and expose a truthful pipeline state.

**Architecture:** The verifier owns its own source query, expected-document model, canonicalizer, Elasticsearch reader, and diff engine; it never imports the consumer projector. A verification run first proves that its MySQL snapshot did not move by reading a transaction-wide source watermark before and after the scan, then merge-compares source and target pages by product_id. Repair reloads current MySQL state and writes only after a second stable-source check. Normal CDC keeps strict `version_type=external`; controlled missing or same-revision repair alone uses `external_gte`, because strict external versioning correctly rejects an equal revision when stored fields are corrupt or Elasticsearch still retains a recently deleted document's version.

**Tech Stack:** Java 21, Spring Boot 4.1.0, Spring JDBC JdbcClient, Spring RestClient, Jackson 3 JsonMapper, Spring Kafka AdminClient, MySQL 8.4.8, Kafka 4.1.2, Elasticsearch 8.17.0, Micrometer, JUnit 5, AssertJ.

## Global Constraints

- Execute only after the M2-M3 completion gate passes.
- Work only in branch `codex/mysql-es-cdc-handson` and its isolated worktree.
- `consistency-verifier` must not depend on, import, reflect over, or copy generated bytecode from `search-sync-consumer`.
- The two modules may agree only through documented field names, HTTP contracts, MySQL tables, Kafka metadata, and Elasticsearch data.
- Compare every managed field, `source_revision`, Elasticsearch `_version`, and tombstone searchability; document counts alone never prove equality.
- Read all active and inactive source products. An inactive source row expects a persisted tombstone in every index generation.
- Verify the current generation through unfiltered `products_write`, never the filtered serving alias `products_search`; rebuild verification targets the physical generation directly.
- A verification run is conclusive only when the global source watermark is unchanged across its source scan and target scan.
- Never repair an inconclusive run, a confirmed log gap, or a difference set larger than the configured bounded-repair limit.
- The normal consumer remains on `version_type=external`. Only verified missing or same-revision field repair may use `external_gte`, after reloading current source and proving the source watermark stayed fixed.
- A stale target is repaired with `version_type=external`; a missing target or equal-revision field/tombstone mismatch is repaired with `external_gte`; an extra document is deleted with its observed `if_seq_no` and `if_primary_term`.
- Repair is idempotent and produces a durable action record before a run can be marked repaired.
- A persisted active rebuild reports `REBUILDING`; otherwise `REBUILD_REQUIRED` outranks catch-up, DLQ, and reconciliation states. Reconciliation must not disguise a log gap as ordinary drift.
- No metric label may contain `product_id`, run ID, document ID, raw exception text, or Kafka offset.
- Command context: run build, Compose, script, and Git commands from `mysql-es-cdc-handson/`; file lists in this plan remain repository-worktree-relative.

~~~java
private void advanceSourceWatermark() {
    int changed = jdbcClient.sql("""
            UPDATE source_change_watermark
            SET value = value + 1
            WHERE singleton_id = 1

    if (changed != 1) {

}
~~~

~~~sql
SELECT
  r.product_id AS expected_product_id,
  r.revision AS expected_revision,
  r.active AS expected_active,
  CASE WHEN r.active = 1 THEN p.sku END AS expected_sku,
  CASE WHEN r.active = 1 THEN p.name END AS expected_name,
  CASE WHEN r.active = 1 THEN p.description END AS expected_description,
  CASE WHEN r.active = 1 THEN p.category_id END AS expected_category_id,
  CASE WHEN r.active = 1 THEN c.name END AS expected_category_name,
  CASE WHEN r.active = 1 THEN p.price_cents END AS expected_price_cents,
  CASE WHEN r.active = 1 THEN i.available_quantity END AS expected_available_quantity,
  GREATEST(r.updated_at, p.updated_at, c.updated_at, i.updated_at) AS expected_updated_at
FROM product_search_revision r
INNER JOIN products p ON p.id = r.product_id
INNER JOIN categories c ON c.id = p.category_id
INNER JOIN inventory i ON i.product_id = r.product_id
WHERE r.product_id > :exclusiveProductId
~~~

~~~java
while (expected.hasNext() || actual.hasNext()) {
    if (!actual.hasNext()) {
        differences.add(DocumentDifference.missing(expected.next()));
    } else if (!expected.hasNext()) {
        differences.add(DocumentDifference.extra(actual.next()));
    } else if (expected.peek().productId() < actual.peek().productId()) {
        differences.add(DocumentDifference.missing(expected.next()));
    } else if (actual.peek().productId() < expected.peek().productId()) {
        differences.add(DocumentDifference.extra(actual.next()));
    } else {
        compareSameId(expected.next(), actual.next()).ifPresent(differences::add);
    }
}
~~~

The production implementation writes differences page-by-page to `verification_difference`; it must not retain the entire catalog in memory. `ConsistencyReport` contains run ID, source watermarks, counts by type, expected count, actual count, and conclusive flag.

- [ ] **Step 2: Implement the verification transaction**

`VerificationRunService.run` performs this exact order:

~~~text

5. Close the target PIT.
6. Read source watermark W_end.
7. If W_end != W_start, mark INCONCLUSIVE and retain differences only as diagnostics.
8. Else mark PASS when difference_count=0, otherwise DIFF.
9. On exception, close resources and mark FAILED with a bounded message.
~~~

~~~markdown
# Independent reconciliation

MySQL is the fact source; Elasticsearch is a repairable current-state projection.

## What a PASS proves

A PASS proves that, during one stable source watermark, every source product has exactly one managed Elasticsearch document, every managed field matches, every inactive product is a latest-revision tombstone, and Elasticsearch external version metadata equals source_revision.
~~~
