# 03 Saga

## 解决的问题

Saga 解决长流程跨服务一致性问题。它把一个大流程拆成多个本地事务，每一步提交自己的事实；当后续步骤失败时，系统执行业务补偿动作，让流程进入可解释终态。

Saga 不提供强原子提交。它的目标不是让所有参与者同时成功或同时失败，而是在部分成功、未知、不可逆和人工处理下保持事实可解释。

## 基本模型

```text
Step 1 local transaction
-> Step 2 local transaction
-> Step 3 local transaction
-> success

if Step N fails:
-> compensate Step N-1
-> compensate Step N-2
-> manual review when compensation is unsafe
```

补偿是业务动作，例如释放库存、void 授权、退款、取消供应商保留、收取罚金、补差、替代供应商或创建人工工单。补偿不是数据库回滚，不能撤销已经提交到外部系统或账本中的事实；补偿也不是删除历史记录。

## 为什么有时只能选择 Saga

TCC 要求每个参与者都能先预留资源，再可靠地确认或释放。但是现实中的外部供应商通常不把自己的资源预留生命周期交给调用方控制，只提供正式业务接口及其后续取消接口，例如：

```text
createOrder：正式创建供应商订单
cancelOrder：取消已经存在的供应商订单
```

这两个接口不等于 TCC 的 Try 和 Cancel。`createOrder` 成功后，订单已经成为不可删除的外部事实；`cancelOrder` 是另一笔业务交易，可能产生取消记录、退款、罚金，甚至失败或需要人工处理。因此系统不能假装第一个事实从未发生，只能保存它并追加补偿事实：

```text
供应商订单已创建
-> 后续步骤失败
-> 发起取消或退款
-> 记录取消成功、退款处理中、结果未知或人工处理
```

机票出票、保险生效、物流发运和外部供应商正式下单都常有这种边界。它们已经产生票号、保单、运单或供应商订单；后续的退票、退保、拦截或取消是补偿，不是释放尚未生效的预留。这时不是“更喜欢 Saga”，而是参与者没有提供 TCC 所要求的可控 Try/Confirm/Cancel 语义，只能按 Saga 保存事实并推动补偿收敛。

| 条件 | 选择 | 原因 |
| --- | --- | --- |
| 所有资源可在一个本地事务中原子更新 | 本地事务 | 不需要额外的分布式协调 |
| 资源支持真实、排他的预留，Confirm/Cancel 可靠且幂等 | TCC | 可以先占住全部资源，再统一确认或释放 |
| 供应商只支持正式执行，以及取消、退款等补偿动作 | Saga | 已产生的事实不能回滚，只能追加补偿事实 |
| 同一流程中的资源能力不同 | Saga 或 Durable Workflow 编排，局部使用 TCC-like | 例如支付用 authorize/capture/void，出票失败则走退票或人工处理 |

真实系统经常采用最后一种混合方式：整个订单由 Saga 或 Durable Workflow 编排，支付步骤使用 `authorize/capture/void`，库存步骤使用 `reserve/consume/release`；但已经出票或正式生效的供应商步骤仍然按 Saga 执行退票、退款、对账或人工处理。

## 适用场景

- 电商下单、库存预留、支付、确认库存和退款。
- 旅行组合预订、供应商确认、扣款、附加项失败和人工处理。
- 充值提现中的渠道请求、查询、回调、对账和人工处理。
- 任何单个数据库事务无法覆盖的长流程。

## 不适用或高风险场景

- 要求强一致同步提交的内部账本更新。
- 没有补偿动作的不可逆外部动作。
- 没有子状态、幂等键和审计记录的总状态流程。
- 把供应商超时直接当失败的流程。

## 设计规则

- 每一步都必须有本地状态机。
- 每一步都必须有幂等键。
- 每一步都必须记录已知事实、未知状态和补偿状态。
- 成功事实不能被失败回调覆盖。
- 补偿失败必须进入重试、对账或人工处理。
- 总状态必须能解释每个子步骤的最终状态。

## 典型失败

| 失败 | 错误处理 | 正确处理 |
| --- | --- | --- |
| 库存确认成功但支付失败 | 删除库存记录 | 释放库存或创建人工工单 |
| 支付成功但库存失败 | 本地订单改失败 | 创建退款和账本分录 |
| 机票已出票但酒店失败 | 删除机票事实 | 替代酒店、退票、罚金、退款或人工处理 |
| 供应商超时 | 直接失败补偿 | 标记 `SUPPLIER_UNKNOWN`，查询、回调、对账或人工处理 |

## 验证方法

- 随机生成步骤成功、失败、超时、重复回调和乱序回调。
- 检查已成功步骤不会被本地删除。
- 检查每个补偿动作都有幂等键和审计记录。
- 故障注入任意步骤宕机，验证恢复后流程继续或进入人工处理。
- 对账每个终态是否能解释本地事实、外部事实、资金事实和账本事实。

## 面试表达

Saga 是长流程一致性模式，不是分布式锁，也不是跨库事务。它允许中间状态和部分成功，但要求每一步事实可审计、补偿可解释、未知状态可收敛。
